# structured survey の下書き評価の記録（Issue #440）

本番の **通常生成**（Natural LLM Realizer・`src/lib/draft/structured/realizer.ts`）と **safe fallback** の実測の記録である。測り方・成功条件・人手の採点の手順は `../README.md` の「structured survey の評価」にある（`pnpm --filter @fwlm/survey-web run eval:structured`）。

実 Gemini の出力そのものはリポジトリに入れない（`EVAL_OUT` はリポジトリの外）。ここに残すのは集計だけである。

## 1. 方針の変更（2026-10-11）

以前は A（legacy の生成器へ平らにした素材）・B（素朴な claim の箇条書き）・C（Natural LLM Realizer）・D（safe fallback）の 4 方式を比べ、「C が A・B より良いこと」を release の条件にしていた。**方式比較そのものは目的ではない** ので、評価の対象を本番の通常生成と safe fallback の 2 つに整理した。

同時に、通常生成の方針を「選ばれていない意味はほぼ一切足さない」から **「新しい具体的事実は創作しない。ただし回答から自然に導ける主観的・意味を保った膨らませ方は許す」** へ緩めた。きっかけは、ローカルで実 Gemini が次のような下書きを返したことである。

> 入店までの待ち時間が気になりましたが、料理の量は満足できました。接客は丁寧でした。

事実性は高いが、アンケートの項目を順に読み上げた回答の要約に見え、文のリズムが機械的だった。変更の中身:

- プロンプト: 禁止の列挙を先頭に置く形から、自然に書く指示（読み上げない・まとめる・言い換える・弱い主観はよい・一言の口調を活かす）を前面に出す形へ。禁止は「足しがちな具体的事実」の型に絞った。legacy の生成器から、文体の候補と、星からの抽象的な全体の印象を取り込んだ（字数の下限は創作を呼ぶので取り込んでいない）。
- runtime hard gate: 弱い主観の程度（少し・やや・ちょっと・若干・多少・少々）を `intensity` から外した。強い程度（とても・最高・絶対 など）は止めたまま。「待ち時間」「過ごしやすい」を facet の手がかりへ足した。人物の様子（笑顔・〜そう）と原因（予約客が多かった・スタッフが足りなかった）を止める語を足した。
- fixture: ケース K（量・接客と入店の待ち時間）を足し、許す言い換えと止める例で境界を固定した。

### 再生成のバリエーションと定型の抑制（2026-10-11・同日）

実 Gemini で、同じ回答（予約・接客の丁寧さ・料理の量 / ドリンクの種類）の再生成 3 本がすべて「予約 → 接客 → 料理の量 → ドリンク → 総評」の順で、語尾だけが違った。「料理の量も満足できるものでした」「満足できる内容でした」の抽象語のまとめと、星由来の「全体として満足です」がほぼ毎回付いた。

- 生成ごとにサーバーが文章の組み立て（`COMPOSITIONS`）・回答の行の並び・文体・総評の有無（約 35%）を選ぶ。再生成では「前とは違う組み立てにする」決まった指示だけを足し、前回の下書きは渡さない
- プロンプトで「内容」「もの」のまとめ方と、総評が必須でないこと・複数の気になったことへの「〜だけ」を名指した。文体の候補から常体（会話調を呼んだ）を外した
- 診断に抽象語のまとめ・総評の頻度・「〜だけ」・再生成の構成の偏り（書き出し・主題の順・文の数・文の組み立て）を足し、`styleWarnings` で警告する（hard fail にしない）
- hard gate は変えていない。coverage の極性の手がかりに「スムーズ」「しやす」を足しただけ（「予約もスムーズでした」を予約の positive として数える）。safe fallback も変えていない
- fixture にケース L（上の回答）を足した

### safe fallback へ落ちすぎる問題（2026-10-11・同日）

実 Gemini で同じ回答（全体と焼き鳥5種盛りの量・入店までの待ち時間が良く、接客の丁寧さが両面、料理の価格が気になった）を 4 回作ったところ、1 本目と 4 本目が safe fallback の文（「量が良かったです。焼き鳥5種盛りは量が良かったです。…」と一字一句同じ）で、3 本目は「予約のおかげか待ち時間も少なく」と原因を作ったまま通った。コードで同じ回答を再現すると、自然な下書きを hard gate が誤って落とす形が 2 つあった（本番のログは無いので、実際の 2 回の違反の種類はこの記録では確かめていない）。

- 「入店までの待ち時間は気になりませんでした」: 「気にな」を concern の手がかりに数え、positive の claim の極性の反転と誤検出した → 否定（気にならない・気になりませんでした）は positive の手がかりへ
- 「料理の量に満足できたものの、料理の価格は…」: exact overlap のある回答で、overlap と無関係な文の「ものの」を両面の理由と数えた → 理由の語は overlap の主題の文（と直後の主題を名指さない文）でだけ数え、「ものの」は語彙から外した
- 原因: 「おかげ」「〜からか」を足した（「予約のおかげか」を止める。予約と待ち時間を両方回答していても因果の根拠は無い）
- style（「満足できる内容」・同じ文末の 3 連続）を factuality から分け、style だけでは safe fallback へ落とさない
- safe fallback の定型を最低限直した（「料理全体の量に満足でき、焼き鳥5種盛りの量も良かったです。」「入店まではスムーズでした。」「〜については、良かった点と気になる点の両方がありました。」）
- ローカル検証用に最終の結果のログ（`survey-web.structured_draft_result`・`STRUCTURED_DRAFT_DEBUG_LOG=1` のときだけ）を足した
- fixture にケース M（上の回答）を足した

### 読み方

- safe fallback は claim から決定的に作るテンプレートで、**事実性の対照** である。hard gate を構造的にすべて通るので、ここが 0 でなければ検出器か safe fallback が壊れている（実測はこれを assert する）。
- 一方で safe fallback は「良かったです」の反復・入力の順のまま・項目名のままの羅列で、**通常生成が避けたい文章の典型** である。通常生成の `fallbackLike` は、この形へ寄った率を測る。

## 3. 既知の限界（known failure）

- hard gate は語彙で判定するので、**測っているのは違反の下限** である。語彙に無い言い回しの属性・理由・強い強度は拾えない。
- 弱い主観（少し・やや）を許したので、「少し」を positive の文に付けた不自然な言い方（「少しおいしかった」）は gate では止めない。自然さの採点で見る。
- 「満足」「印象に残った」は、回答した主題の文でだけ coverage の手がかりになる。主題を省いた文が続くと、直前の文の Target を引き継いだものとして判定する。全体の印象の文（「全体として」「総じて」）は引き継がない。
- coverage と極性は文単位の手がかりで判定する。主題の省略が 2 文以上続く・代名詞（「それ」「こちら」）で受ける形は拾えないことがある。
- 星は全体の印象（★4〜5 は満足・★1〜2 は不満が残った）にだけ使い、具体的な理由・強い言葉へは広げていない。
- 再生成の類似度は文字 bigram の Jaccard で、意味の違いは見ない。語尾だけを変えた組は別に数える（`sameExceptEndingPairs`）。
