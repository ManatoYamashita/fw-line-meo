# Requirements Document

## Project Description (Input)

**Source**: GitHub Issue #4 (https://github.com/ManatoYamashita/fw-line-meo/issues/4) ／ requirements.md §3.3

> この節は Issue #4 の起票時の文をそのまま写したものである。届け方は #256 で改訂したので、本節の「毎朝の配信」「配信時刻はオーナー設定可」は現在の仕様ではない（Introduction の注記と Requirement 3 を参照）。

**(a) 誰が抱える課題か**
飲食店オーナー（IT に不慣れ、日次で自店の市場ポジションを把握する手段を持たない）。

**(b) 現状**
オーナーは自店が近隣の同カテゴリ競合と比べてどのような評価・順位にあるかを知る手段がなく、LINE 以外のツール（Google ダッシュボード等）を使いこなす前提のサービスは定着しない。現時点でこの機能は未実装（実装コード未着手）。

**(c) 何を変えるべきか**
毎朝、Go バッチが Cloud Scheduler 起動で全店舗 × 競合5店の評価・クチコミ数・新着クチコミを Google Places API から並行取得し、順位・前日比を算出したうえで、結論ファーストの LINE Flex Message を各店へ配信する。オーナーは LINE を開くだけで自店の市場ポジションを把握できるようにする。

### スコープ（Issue #4 より）
- 競合自動抽出（半径1km・同カテゴリ・上位5店、システムが自動抽出）
- Places API による自店＋競合の評価・クチコミ数・新着クチコミ取得（Go による並行バッチ）
- コスト最適化（競合リストは固定し指標のみ日次更新、約6回/日/店に抑制）
- 評価・順位の時系列保存と前日比算出
- Flex Message 生成（結論ファースト：順位＋前日比、星・クチコミ数、競合一覧）
- 配信時刻：デフォルト7:00・オーナー設定可
- アクション「詳細を見る」（LIFF で自店・競合の詳細を閲覧のみ表示。書込権限＝OAuth 不要、Places API の範囲で完結）

### 完了条件（Issue #4 より）
Cloud Scheduler で日次起動し、対象店舗へ Flex Message が配信される。

## Introduction

本機能(機能1: 競合ポジショニング日次サマリー)は、店舗特定を完了した飲食店オーナーに対し、LINE で「自店が近隣の同カテゴリ競合の中でどのポジションにいるか」を結論ファーストで届ける MVP 機能である。システムは店舗特定時に競合5店を自動抽出して固定し、以後は自店＋競合の星評価・クチコミ総数を日次で取得・時系列保存し、順位と前日比を算出する。データ源は Google Places API のみとする(プロダクト不可侵制約: スクレイピング禁止)。

> **届け方の改訂（Issue #256・`line-on-demand-report`）**: 当初の「毎朝 1 通の Flex カードを全オーナーへ配信する」届け方は廃止した。現在は、変化があった日だけ短文の通知を送り、詳しい内容はオーナーがリッチメニューから求めたときに Reply で返す。**日次の取得・算出・保存（Requirement 1・2）と表示の規則（AC 3.12〜3.14）は変わらない。** 通知の条件・中身・リッチメニューからの3レポート・複数店舗の選択の正典は `.kiro/specs/line-on-demand-report/` にあり、本書で「配信」と書いてある箇所はその通知とレポートを指す。

**要件確定の根拠**: GitHub Issue #4 ／ ルート `requirements.md` §3.3・§4・§6・§8 ／ ユーザー確認事項(2026-07-11): 順位基準＝星評価降順・同率はクチコミ総数降順、配信対象＝店舗特定済み全員(停止機能なし)、競合リスト＝店舗特定時に自動抽出し以後固定、新着クチコミ＝自店分のみ表示。

## Boundary Context

- **In scope**: 競合の自動抽出と固定／自店＋競合の指標の日次取得・時系列保存／順位・前日比の算出／LINE への通知(オーナーごとの配信時刻に、`line-on-demand-report` が定める条件を満たした日だけ送る)／「詳細を見る」閲覧画面。
- **Out of scope**(第2フェーズ以降): 配信停止(オプトアウト)設定／競合範囲・店数・リストのオーナー調整／クチコミ返信・Google 投稿作成(OAuth 連携全般)／詳細分析画面／収益化。
- **Adjacent expectations**:
  - オーナーの LINE 友だち登録・店舗特定(Place 確定)までのオンボーディングは **LINE 基盤(Issue #6)** の責務であり、本機能はその完了状態を配信開始の前提として参照する(本機能は所有しない)。
  - 4階層データモデルおよび競合・評価時系列の保存構造は **`four-tier-data-model` spec** で確立済みであり、本機能はそれを唯一の真実として参照する。
  - 日次バッチの起動・失敗検知の基盤は **`gcp-infra-foundation` spec** で構築済みであり、本機能はその上で動作する。

## Requirements

### Requirement 1: 競合の自動抽出と固定

**Objective:** As a 飲食店オーナー, I want 自店の競合となる近隣同カテゴリ店をシステムが自動で選んでくれること, so that IT 知識がなくても比較対象を自分で調べ・設定する必要がない

#### Acceptance Criteria

1. When オーナーの店舗特定(Place 確定)が完了した, the system shall 自店から半径 1km 以内かつ Google 店舗カテゴリが自店と一致する店舗のうち、自店に近い順に最大 5 店を競合として自動抽出し、競合リストとして固定する
2. If 条件を満たす店舗が 5 店未満しか見つからない, the system shall 見つかった店舗のみで競合リストを構成する
3. If 条件を満たす店舗が 1 店も見つからない, the system shall 競合なしの状態で自店指標のみの日次サマリーを記録し、比較のレポートで競合が見つかっていない旨を表示する
4. The system shall 固定した競合リストの再抽出・追加・削除の手段を MVP では提供しない(オーナーによる調整は第2フェーズ)
5. If 固定済みの競合店舗が閉店等により指標を取得できなくなった, the system shall 当該店舗を以後の順位算出・配信の比較対象から除外し、過去の時系列記録は保持する

### Requirement 2: 指標の日次取得と時系列保存

**Objective:** As a 飲食店オーナー, I want 自店と競合の評価指標が毎日自動で記録されること, so that 順位や前日比といった「変化」を知りたいときに把握できる

> 但し書き（Issue #255）: Google の星評価は 1.0〜5.0 で定義されており、クチコミが 0 件の店舗には星評価そのものが存在しない（Places API は評価を返さない）。AC 2.4 の比較集合と順位は、星評価の存在する店舗だけで構成する（AC 2.8・2.9）。

#### Acceptance Criteria

1. The system shall 店舗特定が完了した全店舗について、自店および固定済み競合の星評価・クチコミ総数を Google Places API から 1 日 1 回取得する
2. The system shall 競合データの取得を Google Places API のみで行い、スクレイピング等の規約外手段を用いない
3. When 日次取得が完了した, the system shall 取得した星評価・クチコミ総数を店舗ごと・日付ごとの時系列として保存する
4. When 日次取得が完了した, the system shall 自店＋当日有効な競合の集合内で、星評価の降順(同率の場合はクチコミ総数の降順)により自店の順位を算出し記録する
5. If 一部店舗の指標取得に失敗した, the system shall 取得に成功した店舗の処理を継続し、失敗した店舗と理由を運用者が検知できるよう記録する
6. When 同一日に日次処理が再実行された, the system shall 同日分の記録を重複させない
7. The system shall 外部 API の呼び出しを 1 店舗あたり約 6 回/日(自店 1 ＋競合最大 5)に抑える(競合リスト固定・指標のみ日次更新によるコスト最適化)
8. If 自店または競合に Google の星評価が存在しない(クチコミ 0 件), the system shall その店舗の星評価を 0 などの数値で代替せず「評価なし」として記録する
9. When 日次取得が完了した, the system shall 評価なしの店舗を順位の比較集合から除き(「近隣 N 店中」の N にも数えない)、自店が評価なしの場合は自店の順位を記録しない

### Requirement 3: 日次サマリーの LINE への届け方

**Objective:** As a 飲食店オーナー, I want 変化があった日に LINE で知らせが届き、詳しい内容は求めたときに返ること, so that アプリや Web 管理画面を開かなくても LINE を見るだけで自店の状況がわかる

> 改訂（Issue #256）: AC 3.1・3.3〜3.7 は当初「毎朝 1 通の Flex カードを全オーナーへ配信する」ことを定めていた。通知の条件・中身・3つのレポートの正典は `.kiro/specs/line-on-demand-report/` にあり、本要件は日次集計の側が満たすべき前提だけを残す。AC 3.8〜3.14 は通知とレポートの双方に引き続き適用する。

#### Acceptance Criteria

1. The system shall 店舗特定が完了した全オーナーに対し、当日の日次集計に `line-on-demand-report` が定める変化(新着クチコミまたは順位の変動)があった日だけ、店舗ごとの短文通知を LINE Flex Message で 1 通送る
2. The system shall 配信時刻のデフォルトを朝 7:00 とする
3. The system shall LINE 上で配信時刻を変更する手段を提供しない(`owners.delivery_hour` の値は運用側でのみ変更しうる)
4. The system shall 結論ファーストの優先順位: (1) 自店の順位(近隣 N 店中 △位)、(2) 自店の星評価・クチコミ総数、(3) 競合との星差・競合一覧(簡潔に) を、オーナーが要求したときに返す比較のレポートで構成する
5. When 自店のクチコミ総数が前日より増加している, the system shall 新着件数と、取得可能な場合はその内容を新着のレポートに含める(表示は自店の新着のみとし、競合の新着は表示しない)
6. If 自店に新着クチコミがない, the system shall 新着のレポートで「新着なし」として表示する
7. If 前日の記録が存在しない(初回等), the system shall 前日比を根拠とする通知を送らず、レポートでは前日比を表示しない
8. If 特定オーナーへの配信が失敗した, the system shall 他オーナーへの配信を継続し、失敗を運用者が検知できるよう記録する
9. When 同一日に配信処理が再実行された, the system shall 同一店舗へ同日の通知を重複送信しない
10. The system shall 配信停止(オプトアウト)手段を MVP では提供しない
11. The system shall 通知とレポートを日本語で提供する
12. The system shall 競合との星差を「自店の星評価 − 競合の星評価」とし、小数 1 桁・正の値には「+」を付けて表示する(自店と競合のどちらかが評価なしの場合は星差を表示しない)
13. If 競合一覧に評価なしの店舗が含まれる, the system shall その店舗の星評価を「評価なし」と表示して一覧の末尾に置き、評価なしの店舗を順位に含めていない旨を一覧に添える
14. If 自店が評価なし, the system shall 順位の代わりに Google の評価が無いため順位を出せない旨を表示し、自店の星評価を「評価なし」と表示する(取得失敗の表示と区別する)

### Requirement 4: 「詳細を見る」閲覧画面

**Objective:** As a 飲食店オーナー, I want リッチメニューから 1 タップで自店・競合の詳細を確認できること, so that 気になった変化の背景を LINE から離れずに確認できる

> 但し書き（Issue #61）: 確定済み店舗を複数持つオーナーは、どの店舗を指すかが ID トークンだけでは決まらないため店舗選択が 1 回挟まる（AC 4.5）。「1 タップ」は単一店舗オーナーの体験を指す。多店舗オーナーの 1 タップ復帰は第2フェーズの課題（design.md Open Questions）。

#### Acceptance Criteria

1. When オーナーが完了後リッチメニューの「詳細を見る」をタップした, the system shall LINE 内で自店および競合の詳細(星評価・クチコミ総数・順位の推移を含む)を閲覧画面として表示する
2. The system shall 詳細画面を閲覧のみとし、クチコミ返信・投稿作成等の書込操作を一切提供しない(Google アカウントの書込権限・OAuth 認可を要求しない)
3. While オーナーの店舗で競合が 1 店も固定されていない, the system shall 詳細画面で自店の指標のみを表示する
4. The system shall 詳細画面を日本語で提供する
5. When オーナーが確定済み店舗を複数持つ, the system shall いずれかの店舗を推測で表示せず、当該オーナーが所有する確定済み店舗の一覧を提示し、選択された店舗の詳細を表示する
6. The system shall 表示対象の店舗指定を、ID トークンの検証済み識別子から導いた所有店舗の集合内でのみ有効なものとして扱い、当該集合に含まれない指定は無視して未指定時と同一の応答を返す
7. The system shall 詳細画面に現在表示している店舗の名称を表示する
8. The system shall 詳細画面の星評価・星差・評価なしの表示を、LINE の通知・レポートと同じ規則(AC 3.12〜3.14)で行う

### Requirement 5: 運用可観測性

**Objective:** As a 運営者, I want 日次処理と通知の成否が検知できること, so that オーナーが「レポートの数字が古い」と気づく前に異常へ対処できる

#### Acceptance Criteria

1. If 日次処理全体が起動しなかった、または異常終了した, the system shall 運用者が当日中に検知できるよう失敗を記録・通知可能にする
2. The system shall 日次処理の実行ごとに、対象店舗数・取得成功/失敗数・配信成功/失敗数を運用者が確認できるよう記録する
