## Implementation Notes

- 1.1 旧制約の実名は隔離 DB（PG 16.14）で `audit_logs_action_check` と再実測した（audit_logs の CHECK はこの 1 本のみ）。赤化の対照（0009 の変異→実行→元へ戻して一致を確認）:
  - 値を 1 つ落とす（`dashboard_user_agency_updated`）→ 集合一致テストと SQL 8.1b が赤。
  - 既存値を落とす（`owner_created`）→ 集合一致テストだけが赤。
  - DROP を消して新旧を共存させる → SQL 8.1a だけが赤。
  - DROP の名前を違える → migration の適用自体が失敗する。
  - `as const` を外す → 型検査が赤（TS2578）。
  - 既存 12 値の欠落は TS 側、旧制約の残存は SQL 側が捕まえる（役割分担）。独立レビューで同種の対照を再現済み。
- 1.1 `scripts/check-db-ordinals.sh` は追跡下（`git ls-files --cached`）しか見ない。新規 migration は `git add` の後に流さないと検査されない。
- 1.2 「差分が無ければ更新しない」は、指定列だけを SET し、WHERE に `IS DISTINCT FROM` の述語を付けた UPDATE の 0 行更新で実現した。
  - 比較は DB の型（uuid）で行う。
  - 0 行のときは、取得済みの行を現状として返す。
  - 行を書き換えないことは、テストで `xmin` の一致を assert して固定した（値の一致だけでは「同じ値で UPDATE する」実装が素通りする）。
  - 評価順・残数・差分の述語・戻り値の変異は、実装担当と独立レビューがそれぞれ当てて赤を確認した。ロックの除去は逐次テストでは検出されないので、1.3 が対照を取る。
