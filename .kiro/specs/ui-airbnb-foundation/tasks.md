## 段階 2 の実装メモ（2026-09-02）

### 「プローブを外すと赤になる」は成り立たなかった（タスク 7.1・要件 7.5）

タスク 7.1 の完了条件は「プローブ追加を外すと赤になることを確認した記録を残す」だった。
**実測すると緑のままだった。** 両方向の対照を取って原因を確定した。

| 条件 | 結果 |
|---|---|
| プローブを外す × 部品が新しい段を使う（最終形） | **緑**（3 面すべて） |
| プローブを外す × 部品も新しい段を使わない | **赤**（3 面すべて・「トークンは 1rem だが生成 CSS は 未出力」） |

理由は Tailwind の走査経路にある。プローブは `@source inline(...)` で生成を強制する仕掛けだが、
その段を使う部品が居れば `@source` 経由の走査でも同じ変数が出力される。値の照合は通ってしまう。

**しかし外して良いわけではない。** 角丸のキー集合はプローブから導出されているため、
足し忘れた段は「段の重複」検査と「生成側の網羅」検査の対象から**静かに外れる**。
検出力が落ちたことはどの検査にも現れない。そこで**プローブ集合とトークンのキー集合を
両方向で照合する検証を新設**し、追随を機械強制した。この検証を入れた状態でプローブを外すと
1 件赤くなることを確認した（余白トークンの対応表と同じ流儀）。

### 影の照合を立て直した（段階 1 タスク 4.2 からの申し送り）

段階 1 は「影の名前空間プローブの注記が事実でなくなった。部品が入る #174 で対照ごと立て直す」を
残していた。撤去済みの段が同名上書きの対照として残っており、その名前は `@theme` から消えていた。

立て直しの内容:

- 影のプローブを独立した集合へ分け、**越境衝突の対照ではないこと**を注記に明記した
  （影のユーティリティは実値を内部変数へ展開するため、解決先の判定は構造的に何も検出できない）
- **影のトークンと生成 CSS を突き合わせる検証を新設した。** これまで影の値を照合するものは
  1 つも無かった。色集合を見る検査は、色が同じまま距離やぼかしだけが変わった場合を検出できない

実装にあたり生成 CSS を実測した。**影は角丸と違い、テーマ変数として現れない**:

```
.shadow-raised { --tw-shadow: 0 0 0 1px var(--tw-shadow-color, <色>), ... }
```

値は内部変数へ展開され、各色は `var()` の既定値として包まれる。`--shadow-{key}` を引く方式では
常に「未出力」になり照合が成立しない（最初にそう書いて赤になった）。包みを外してから比べる。

### 影そのものは消費していない（要件 3.3・タスク 6.1 の境界）

段階 1 の申し送りは「部品が入る時点で出力を伴う検証を行う」としていたが、**タスク 6.1 が
表の容器について「面の分離は輪郭で表現し、影は使わない」と定めている**。段階 2 の 5 部品に
影の置き場は無い。出典で影が付くのは重畳時に浮くカード・検索窓・ドロップダウン・写真上の帯であり、
いずれも面適用（後続 spec）の領域である。発火ゼロの装飾を先回りで置くことはしない。
生成 CSS への出力はプローブが強制しており、値の照合は上記の新設検証が担う。

### 検証面のルートを部品へ置き換えた

ページ枠の部品は主要領域を描く。検証面へ**入れ子で**足すと主要領域が 2 つになり、
それを 1 つに解決している複数の実描画検証が同時に壊れる。したがってルートそのものを
置き換えた。見出しと説明文も同じ理由でページ見出しの部品へ寄せてある（この面の見出し 1 は 1 つ）。

版面は狭い側（576px）へ移ったが、**端末幅 393px では従来値ともども上限に届かないため実効幅は変わらない**。

### 選択部品を操作領域の検査の射程へ入れた

指で操作する部品を新設したのに、ラベルを伴う行の要求寸法の検査対象が一行入力だけのままだと、
**部品を足すたびに検査対象が静かに減る**。選択部品を含むよう対象条件を広げた（実測で緑）。

### レビュー指摘への対応（PR #180・2026-09-02）

3 件とも**是正の前にガードを入れ、赤になることを実測してから直した**（要件 7.5 の流儀）。

#### 指摘 1: 判定の射程が 2 箇所に分かれ、片方だけ追随していた

選択部品を要件 4.7（`LABELLED_ROW_SELECTOR`）へは足したが、要件 4.5（`OPERABLE_SELECTOR`）へは
足していなかった。4.5 は「拡張した操作領域が隣接部品の**視覚領域**を覆わない」判定であり、
被覆される側の集合でもあるため、選択部品が覆われても緑のまま通る。**縮んだことはどの検査にも
現れない**（覆う側が居なければ 4.5 は自明に成立するため）。

対象条件を追記して済ませず、**両方の選択子を 1 つの `data-slot` 集合から導く形へ変えた。**
ラベルを伴う構成の部分集合を `satisfies` でその集合へ束縛したので、4.7 として数えた部品が
4.5 から漏れると型検査が落ちる。

| 変異 | 結果 |
|---|---|
| `OPERABLE_SLOTS` から `'select'` を抜く（指摘時点の状態の再現） | **赤**（`TS2322: Type '"select"' is not assignable to ...`） |
| 戻す | 緑 |

型検査は「宣言から漏れた部品」を捕まえるが、「宣言はあるが検証面に実在しない部品」は捕まえない
（0 件は強制の外へ出る）。そこで 4.5 の本体へ、宣言した種別がすべて実測できたことを要求する
空振り防止を足した。

#### 指摘 2: 「行に面塗りが無い」の判定が半透明を素通りしていた

`readRenderedColors` は **alpha < 1 を一律 null** で返す契約（「その要素では色が決まらない」の意・
`ui-foundation.spec.ts` の同関数の注記が「無音で 0 と比較して緑になるのを防ぐ」と明言している）。
その null を「塗られていない」の証明に使っていたため、`odd:bg-muted/50` のような半透明の縞模様は
検出できない。しかも `bg-muted/50` は CardFooter 由来で `USAGE_PAIRS` に登録済みであり、
色ユーティリティの網羅ガードは**ユーティリティ単位**なので、そちらにも掛からない。

合成前のレイヤの alpha を直接見る形へ変えた。**旧 assert を新 assert の直前へ一時的に復元し、
同一実行で両者の判定を対照した。**

| 条件 | 旧 assert（`backgroundColor` が null） | 新 assert（`alpha` が 0） |
|---|---|---|
| 行へ `odd:bg-muted/50` を注入 | **緑**（通過して次行へ到達） | **赤**（実測 `#F7F7F7` / alpha 0.5019607843137255） |
| 注入なし | 緑 | 緑 |

#### 指摘 3: 横溢れの捲りを担う容器が焦点を取れなかった

`TableContainer` はリポジトリで唯一のスクロール領域（`ts/apps`・`ts/packages` 全体で
`overflow-*-auto` の出現はこの 1 件）になったが、`tabindex` を持っていなかった。スクロール領域を
自動で焦点可能にしないブラウザでは、溢れて隠れた列へ到達する手段が他に無い（WCAG 2.1.1）。
**セルの中に焦点可能な要素があるとは限らない**ため、「行のどれかを辿れば横にも動く」は成り立たない。

容器を常に焦点可能にした。名前は任意の `label` で受け、**名前が与えられたときだけ** `role="region"`
を宣言する（名前を持たない region をランドマークとして公開しない実装があるため）。到達性は
名前の有無で変わらない。

| 変異 | 実描画（E2E） | 宣言（単体） |
|---|---|---|
| `tabIndex` 無し（指摘時点） | **赤**（`activeElement` の `data-slot` が null） | **赤** 2 件 |
| `tabIndex={0}` を入れる | 緑 | 緑 |

宣言だけを見る単体テストでは「実際に焦点が載るか」は言えないため、E2E 側は `tabindex` 属性では
なく `document.activeElement` を見る（`focus()` は焦点可能でない要素には何も起こさない）。

**残る宿題（申し送り）**: この容器が実際に横へ溢れる状態は、どの検証からも発火していない
（検証面の表は 2 列で溢れない）。表を実面へ適用する時点で、`ui-design-foundation` 要件 3.3
（端末幅を超える要素を作らない）と衝突しうる。

#### 衝突範囲を実測で確定した（2026-09-02）

検証面へ 6 列の溢れる表を一時的に置き、`expectNoHorizontalScroll` の全項目を実測した。
**衝突するのは 4 本の assert のうち 1 本だけである。**

| 実測項目 | 値（端末幅 393px） | 判定 |
|---|---|---|
| `innerWidth` | 393 | OK |
| `docScrollWidth` / `docClientWidth` | 393 / 393 | OK（ページは横スクロールしない） |
| `bodyScrollWidth` | 393 | OK |
| `maxRight`（最右端の要素） | **964**（`TABLE`） | **NG ← 唯一の衝突** |
| 容器の幾何 | `right=377` / `clientWidth=361` / `scrollWidth=948` | 容器は端末幅の内側に収まる |

溢れているのは**容器の内側で捲られる `<table>` だけ**で、面そのものは横に動いていない。
要件 3.3 が本当に禁じたい「面が横へ動く」は起きていない。

#### 方針は後続 spec が独立に確定させた

`ui-airbnb-surfaces` の要件（起票時点・#41 配下）が同じ結論を持つ。

- 要件 2「一覧と空状態」: 一覧の幅が表示領域を超えたとき、**一覧の内部だけを横方向にたどれる
  状態にし、ページ全体を横に溢れさせない**
- 要件 4「アクセシビリティ水準の維持」: 表示幅が携帯端末相当のとき、**ページ全体の**横方向の
  スクロールを発生させない

「ページ全体の」という限定が両方に置かれており、上の実測と一致する。**方針を改めて決める必要は無い。**

#### 実装時の罠（要件からは導けないので、ここに残す）

1. **除外は `data-slot` 名で判定してはならない（fail-open になる）。** 容器が `overflow-x-auto`
   を失っても名前は残るため、名前で除外すると「本当に面を押し広げている状態」を除外対象として
   見逃す。走査中の各要素について**祖先を辿り、計算済みの `overflow-x`** で判定すること。
   こうすれば容器が捲りを失った瞬間に除外から外れて赤くなる。
   - **免除してよいのは `auto` / `scroll` の 2 値だけである（#53 で実装時に是正）。**
     当初この項は「`visible` 以外」と書いていたが、**そのまま実装すると網が消滅する。**
     判定は `!== 'visible'` の否定形ではなく、**列挙**で書くこと（`overlay` のような値が
     将来増えたときに免除が黙って広がらないようにするため）。詳細は下の「除外の広さ」を見よ。
2. **スクロール領域そのもの**の右端が端末幅以内であることを別途要求すること（実測 377 ≤ 393）。
   内側を免除するなら、外側の箱は必ず測る。
3. **`overflow-x: clip` により `docScrollWidth <= docClientWidth` は構造的に常に真である**
   （段階 1 タスク 7.1 の実装メモが「clip は scrollWidth 検査を空振りさせる」と記録している）。
   内側を免除した後、**面レベルの溢れを検出する実質的な網は `maxRight` 1 本だけ**になる。
   だからこそ除外は狭く、fail-closed に作る必要がある。
4. 除外の空振り検出は「**呼び出し側が捲れる領域の件数を宣言し、実測との一致を要求する**」形で行う
   （#53 で具体化）。**「除外 0 件なら赤」を大域の assert にしてはならない。** 捲れる領域を
   持たない面では 0 が正当であり、正しい面が赤くなる。宣言方式なら、容器が捲りを失った瞬間に
   `maxRight` と件数の 2 本が同時に赤くなる。
5. スクロール領域はキーボードで焦点を得られること（`TableContainer` は PR #182 で担保済み）。

#### 除外の広さ ― 「`visible` 以外」は網を弱めるのではなく消滅させる（#53・2026-09-03 実測）

検証面 `/ui-check` へ意図的に溢れる表を常設し、規則ごとに全要素を走査して実測した（端末幅 393px）。

| 免除の規則 | `maxRight` | 免除された要素数 | 測られた最右端 | 判定 |
|---|---|---|---|---|
| 免除しない | **671**（`TABLE`） | 0 | `TABLE` | 赤（偽陽性・是正前） |
| `auto` / `scroll` のみ | 393 | 29 | `MAIN` | 緑（採用） |
| `visible` 以外すべて | **0** | **145（全要素）** | **`(none)`** | **常に緑** |

**`visible` 以外をすべて免除すると、測られる要素が 1 つも残らない。** 3 面の `globals.css` が
`html, body { overflow-x: clip }` を持つため **`body` 自身が免除の根拠になり**、`body` 配下から
始まる走査の全要素が「領域の内側」に落ちる。罠 3 が言う「網は `maxRight` 1 本だけ」の、その 1 本が
`0 <= 393` で恒久的に緑を返すようになる。

`body` に至らずとも同じ型の穴が一段手前にある。`ts/packages/ui/src/components/card.tsx` と
`badge.tsx` は `overflow-hidden` を持つため、**Card 配下の全要素が母数から消える**。

免除してよいのは**利用者が捲れる領域**（`auto` / `scroll`）だけである。`hidden` と `clip` は
捲れる領域を作らず、はみ出した中身は到達不能なまま失われる — 面の側の `overflow-x: clip` を
免除しないのとまったく同じ理由である。

#### 実測で見つかった 3 件目の捲れる領域: `<textarea>`

`<textarea>` の既定の `overflow` は `auto` であり、上の規則に素直に当てはまる。子要素を持たないので
免除の効果は無いが、**領域そのものの右端を測る対象**にはなる。宣言する件数は
`/ui-check` が 3（表の容器 2 + textarea 1）、`/s/` の 2 画面がそれぞれ 1 である。
**宣言を実測へ合わせたのであって、逆ではない。**

#### 赤化の対照（`ui-foundation.spec.ts` の `describe('スクロール領域の除外')`・6 件）

| 対照 | 期待 | 固定している性質 |
|---|---|---|
| 免除しない規則 + 溢れる fixture | 赤（671 > 393） | 是正前が本当に赤い（偽陽性の実在） |
| `auto`/`scroll` + 同 fixture | 緑 | 是正が効く |
| 容器から `overflow-x` を実行時に剥がす | 赤（`maxRight` と件数の 2 本） | 捲りを失えば除外から外れる |
| `data-slot` 名の規則 + 同じ剥がし | 緑 | **fail-open の実証**（上の赤が緑へ化ける） |
| `visible` 以外の規則 + Card 配下へ溢れを注入 | 緑（`widest` が `(none)`） | **除外が広すぎると網が消える実証** |
| `auto`/`scroll` + 同じ注入 | 赤 | 狭い規則なら `hidden` の内側も捕らえる |

注入位置は Card の先頭と末尾の 2 通りで試す（1 箇所での赤化は位置依存の穴を隠す）。

対照群そのものが空振りしていないことは、実装への変異 3 種で確かめた。

| 変異 | 落ちた対照 |
|---|---|
| 免除する値へ `hidden` を足す | 6 件中 4 件が赤 |
| 本番規則へ `data-slot` 名の判定を足す（fail-open の採用） | 「捲りを失うと赤くなる」1 件が赤 |
| 祖先の走査を親 1 段に縮める | 6 件中 4 件が赤 |

現在の `expectNoHorizontalScroll` が掛かるのは `/s/` の 2 画面と検証面 `/ui-check` である。
**管理ダッシュボードと店舗詳細の実面へ広げるには、まず実ブラウザで幅を測る足場が要る**
（両面とも Playwright を持たず、LIFF / Firebase Auth の突破が前提になる）。それは #53 に残っている。

### E2E の赤を変更起因と読み違えかけた 2 つの環境要因

段階 1 のメモは DB の不足だけを挙げていたが、実際にはもう 1 つある。**両方とも
「自分の変更が壊した」ようにしか見えない形で現れる。**

1. **別アプリが同じポートを占有していた。** Playwright の webServer は既存のサーバーがあれば
   それを使い回す設定であり、他セッションが起動していた別アプリの画面を測って **25/28 が赤**になった。
   失敗の中身は「区切り線が 0 件」「Alert が無い」等で、検証面の欠陥にしか見えない。
   切り分けは失敗記録に残る**画面の内容**を見るのが速い（別アプリのログイン画面が写っていた）。
   基準 URL を明示して別ポートのサーバーへ向けると解消する
2. **DB と鍵の env が無いと `/s/<storeId>` 系の 3 件だけが落ちる**（段階 1 と同じ）。
   常駐 DB へ接続情報・署名鍵・生成モックを与えると 28 件すべて緑になる

### 実装で判明したこと（後続 spec への申し送り）

- **`@fwlm/design-tokens` は dist 配布なので、値を変えたら `pnpm --filter @fwlm/design-tokens build`
  を先に走らせないとテストが古い値を見る。** これを踏むと「theme.css に design-tokens が知らない色が
  混入している」という、実際とは違う失敗メッセージが出る

  パス位置を問わず一致し、追跡対象から静かに外れる。`docs/design/upstream/` にした
- **原典の逐語コピーは既存の文書規約ガードとトークンガードを無改変で通った**ため、除外規則は

- **見出しの太さと行間は、`app-integration.test.ts` の既存検査が一切見ていなかった**
  （`font-weight` は「数値であること」、`font-size` は「トークン参照であること」しか要求せず、
  `line-height` は無検査）。N2 はこの空白を埋めるものであり、**既存の検査が緑であることは
  一致の証拠になっていなかった**

### 目視確認（要件 1.2, 2.2, 2.4, 4.1・Chromium・検証面）

実測値はブラウザの `getComputedStyle` から読んだ。目視の印象だけで済ませていない。

| 確認項目 | 実測 | 判定 |
|---|---|---|
| アクション色と危険色が並んだとき CTA が「危険」に読まれないか | CTA は `rgb(224, 11, 65)` の不透明なベタ塗りに白文字、危険は淡い面に `rgb(179, 37, 5)` の濃い文字 | **混同しない。** 色相が近くても**描画形状が違う**ことが緩衝になっている（設計 D3 の想定どおり） |
| 成功通知が緑のままか | `rgb(21, 128, 61)`・role=status | **緑のまま。** アクション色の差し替えに巻き込まれていない（D2 が効いている証拠） |
| 危険通知が別色か | `rgb(179, 37, 5)`・role=alert | 成功と明確に別の色相 |
| 輪郭がインクで、アクション色で塗ったボタンの周囲でも見えるか | キーボードで到達した CTA で `outline: 2px solid rgb(34, 34, 34)` / `offset: 2px` / `:focus-visible` が真 | **見える。** 2px の隙間を挟んで黒い輪郭が明瞭に出る |
| 見出しの階層 | h1 = 24px / 700 / 行間 30px（1.25）、h2 = 20px / 600 / 行間 25px（1.25） | 設計 D7 のとおり。本文と区別できる |

**プログラム的な `focus()` では `:focus-visible` は立たない**（実測で `focus-visible=false`・輪郭も出ない）。
実キー入力の Tab で到達させて初めて立つ。目視確認をスクリプトで代替すると、
**輪郭が出ていないのに「出ている」と読む**ことになる。
