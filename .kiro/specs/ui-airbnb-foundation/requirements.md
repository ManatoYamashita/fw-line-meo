### なぜ今やるか

**本 spec は #42 / #43 / #44 / #45（各面のデザイン整備）のゲートである。**
アクセント色・見出し階層・角丸・余白の律・共通部品は、どの面でも必ず使われる。
面を組んでから意匠を差し替えると全面の再調整になる。とくにアクセント色は、
現在アクセント色で描かれている満足度の星が差し替え後に危険色系へ変わるため、
面を組む前に決着させないと満足度 UI として成立しない配色のまま各面へ伝播する。

### 何が変わるべきか

1. Web 3 面のアクセントが Airbnb Rausch 系になり、CTA の文字と背景が WCAG AA を満たす。
2. LINE Flex Message の色は 1 バイトも変わらない。
3. 成功通知とフォーカス指標が、アクセント色から独立した意味役割を持つ。
4. 見出しの階層が、共通部品を使っても素のタグを使っても同一に描画される。
5. 影が 1 段になり、面の分離は 1px の輪郭が担う。
6. 各面が共通で必要とする部品（表・ページ枠・ページ見出し・空状態・選択）が `@fwlm/ui` から使える。
7. 上記が失われたときに CI が失敗する。**是正前の実装に対して赤化することを実証してから導入する。**
8. 参照した DESIGN.md の来歴とライセンスがリポジトリに残る。

### 制約・前提

- **`lineColors` は変更しない**（ユーザー決定）。LINE アプリ自身の緑 UI の中で映えるため。
- **ベンダリングした部品ソースの書き換えは最小限にする。** ベンダリング元との差分を増やすと次回の `shadcn add` で巻き戻る。`theme.css` が採ってきた「アプリの DOM を変えずに直す」方針を維持する。
- **`@theme` に余白の名前付きキーを宣言しない**（#54 の是正結果）。宣言するとサイズ系ユーティリティの解決先が覆われる。
- **角丸スケールの段を上書きしない**（#54 の是正結果）。一部の段だけ上書きすると隣段と同値になるか、隣段を追い越して逆転する。**逆転は既存ガードが検出しない。**
- **フォーカス指標は `@layer base` に一本化する**（#49 の是正結果）。部品側で輪郭を打ち消すユーティリティを書くと、カスケードレイヤにより base 層が必ず負ける。
- **hover は暗くする方向で表現する**（#50 の是正結果）。アルファ合成は白背景で明るくなり AA を割る。
- **Tailwind v4 はソースをプレーンテキストとして走査する。** コメント内に書いたクラス名・hex までユーティリティ生成とガード検出の対象になる。
- **性能予算**: survey-web は client JS 300KB gzip（現 213.6KB）と Lighthouse mobile の制約下にある。
- **外部依存を増やさない**: `@base-ui/react` の新規ベンダリングは行わない。

3. **Kiro spec-driven で進め、作業単位を Issue で分割する。** 1 セッションで全部を行わない。

## Introduction

本仕様は、fw-line-meo のデザイン基盤に**意匠の方向**を与える。参照するのは Airbnb の DESIGN.md であり、
その色・形・余白・階層をトークン層（`@fwlm/design-tokens` と `theme.css`）へ写像し、
各面が共通で必要とする部品を `@fwlm/ui` へ追加する。

本仕様が扱うのは**利用者と開発者に観測できる振る舞い**である。すなわち、描画される色とその実効コントラスト比、
成功と危険が区別できること、キーボード操作時に輪郭が見えること、見出しの階層が読めること、
共通部品が全面から同一に使えること、そしてこれらが失われたときに CI が失敗すること。
どのトークンをどう定義し直すか、どのファイルをどう分けるかといった実現手段は design フェーズで決定する。

**本仕様は各面のデザイン整備のゲートである。** また、差し替えが引き起こす退行の 2 件
（成功通知の色とフォーカス指標の色）は**画面が正常に見えたまま無言で壊れる**種類であるため、
是正そのものと同じ重さで、失われたときに CI が失敗する仕掛けを要求する。

## Boundary Context

- **In scope**: Web 3 面に共通するアクセント色・中立色・面色・危険色・成功色の意味役割と実効コントラスト、
  見出し階層の一貫性、角丸の役割割当、影の段数、余白の指定手段、フォーカス指標の色、
  各面が共通で必要とする 5 部品、参照した DESIGN.md の来歴とライセンスの保全、
  ならびに以上が失われたときに失敗する自動検証。
- **Out of scope**:
  - **各面の画面デザイン** — 後続 spec `ui-airbnb-surfaces` が #42 / #43 / #44 / #45 として扱う
  - **LINE Flex Message の色** — 変更しないことが決定事項
  - **Web フォントの導入** — `typography.ts` が既に「導入判断は #44」と分界を宣言している
  - **暗色パレットの定義** — `ui-design-foundation` の Non-Goals を継承する
  - **視覚回帰テスト・axe・jsx-a11y・生成 CSS のサイズ予算** — #53 が扱う
  - **overlay 系部品のベンダリング** — 4 面いずれも必要としないと判断した
  - **写像版デザイン文書と steering への昇格** — #175 が本仕様の完了後に扱う
- **Adjacent expectations**:
  - 後続 spec `ui-airbnb-surfaces` は、本仕様の完了後に着手し、アクセント色・見出し階層・角丸・余白の律・5 部品をそのまま前提にできることを期待する。
  - LINE Flex Message を組み立てる層は、デザイントークンの色を CSS を経由せず値として消費する。本仕様が Web 側の色を差し替えても LINE 側の描画は変わらないことを期待する。
  - `ui-a11y-gaps` と `form-non-text-contrast` が確立した保証（フォーカス指標の一本化・非テキスト 3:1・操作領域 44px・動き低減・通知の役割分岐）は、本仕様の変更後も維持されることを期待する。
  - #175 は、本仕様が確定させた実測値と、それを守るガードの名前を、写像版文書の本文として利用できることを期待する。
  - #53 が導入する検証基盤は、本仕様が追加する部品を追加の配線なしに射程へ入れられることを期待する。

## Requirements

### Requirement 1: アクセント色の差し替えと、操作可能な文字のコントラスト

**Objective:** As a Web 3 面の利用者, I want 押せるものの文字が背景に対して十分な濃さで描かれること, so that 明るい環境や視力の低下があっても操作対象を読み取れる

#### Acceptance Criteria

1. The UI デザイン基盤 shall 客向けアンケート Web・LIFF 店舗詳細・管理ダッシュボードの 3 面で同一のアクセント色を用いる
2. When 主要な操作（CTA）の面が塗られ、その上に前景色の文字が置かれたとき, the UI デザイン基盤 shall 文字と面の実効コントラスト比を 4.5:1 以上で描画する
3. While 主要な操作にポインタが重なっているとき, the UI デザイン基盤 shall 静止時より暗い面色で描画し、かつ前景色の文字との実効コントラスト比を 4.5:1 以上に保つ
4. Where 参照デザインシステムの色が単独で 4.5:1 に満たないとき, the UI デザイン基盤 shall その色を通常文字および文字を載せる面の色として用いない
5. Where 参照デザインシステムの色が淡い面の上に同色の文字を載せる表現で用いられるとき, the UI デザイン基盤 shall 合成後の実効色に対して 4.5:1 以上を満たす値を採る
6. The UI デザイン基盤 shall ブランドを表す装飾専用の色と、操作を表す色とを別の意味役割として提供し、装飾専用の色を通常文字および文字を載せる面の色として用いない

### Requirement 2: 意味役割の独立（成功・危険・フォーカス指標）

**Objective:** As a Web 3 面の利用者, I want 成功の通知と危険の通知を色で区別でき、キーボード操作中は常に現在位置が見えること, so that 誤った操作をせずに手続きを完了できる

#### Acceptance Criteria

1. The UI デザイン基盤 shall 成功を表す色を、操作を表す色・装飾専用の色・危険を表す色のいずれからも独立した意味役割として提供する
2. When 成功の通知と危険の通知が同一画面に描画されたとき, the UI デザイン基盤 shall 両者を色相の異なる色で描画する
3. The UI デザイン基盤 shall キーボード操作時の輪郭の色を、操作を表す色から独立した意味役割として提供する
4. While 主要な操作の面が塗られた要素へキーボードで焦点が移っているとき, the UI デザイン基盤 shall 輪郭とその隣接背景との実効コントラスト比を 3:1 以上で描画する
5. The UI デザイン基盤 shall 成功を表す色と背景との実効コントラスト比を 4.5:1 以上で描画する

### Requirement 3: 中立色・面色・形・影・余白の律

**Objective:** As a 各面を実装する開発者, I want 参照デザインシステムの余白・形・影の律が基盤側で決まっていること, so that 面ごとに独自の判断を持ち込まずに一貫した画面を組める

#### Acceptance Criteria

1. The UI デザイン基盤 shall 本文・補足・罫線・淡い面・やや濃い面の意味役割を、参照デザインシステムの中立色から供給する
2. The UI デザイン基盤 shall 補足の文字色と、それが置かれる淡い面との実効コントラスト比を 4.5:1 以上で描画する
3. The UI デザイン基盤 shall 影を 1 段のみ提供し、面の分離は輪郭で表現できる状態を保つ
4. The UI デザイン基盤 shall 余白の指定手段を Tailwind の数値スケールに限り、名前付きの余白ユーティリティを CSS 上で提供しない
5. The UI デザイン基盤 shall 参照デザインシステムの余白 9 段に対応する倍率をデザイントークンとして保持し、CSS を経由しない消費先から参照できる状態にする
6. The UI デザイン基盤 shall 角丸スケールの段を上書きせず、参照デザインシステムの形は既存の段への役割割当によって表現する
7. When 角丸スケールに段を追加したとき, the UI デザイン基盤 shall 追加した段が生成 CSS に出力されていることを機械検証する

### Requirement 4: 見出し階層の一貫性

**Objective:** As a Web 3 面の利用者, I want 見出しが本文と区別でき、レベルごとの大小関係が読めること, so that 長い画面でも情報の構造を把握できる

#### Acceptance Criteria

1. The UI デザイン基盤 shall 見出しレベル 1 から 6 までの寸法・太さ・行間の既定を提供し、レベルが下がるにつれ寸法が単調に減少する状態を保つ
2. When 見出しを共通部品で描画したときと素のタグで描画したとき, the UI デザイン基盤 shall 同一レベルに対して同一の寸法・太さ・行間で描画する
3. If 共通部品側の既定と基盤側の既定が食い違ったとき, then the UI デザイン基盤 shall 継続的インテグレーションを失敗させる

### Requirement 5: 各面が共通で必要とする部品

**Objective:** As a 各面を実装する開発者, I want 表・ページ枠・ページ見出し・空状態・選択が共通部品として使えること, so that 面ごとに同じ意匠を書き写さずに済み、意匠のドリフトが起きない

#### Acceptance Criteria

1. The UI デザイン基盤 shall 表・ページ枠・ページ見出し・空状態・選択の 5 種を共通部品として提供する
2. While 表が描画されているとき, the UI デザイン基盤 shall 行・列・セルの支援技術上の役割を保ったまま意匠を適用する
3. When 選択部品がキーボードおよびプログラムによる値の変更を受けたとき, the UI デザイン基盤 shall ブラウザ標準の選択要素と同一の振る舞いを示す
4. While 選択部品が焦点を持たない状態で描画されているとき, the UI デザイン基盤 shall 輪郭と隣接背景との実効コントラスト比を 3:1 以上で描画する
5. The UI デザイン基盤 shall 追加した部品を、既存の全部品と同一の検証面から到達できる状態にする
6. The UI デザイン基盤 shall 追加した部品が生の色（hex リテラルおよび既定パレットの色クラス）を持たないことを機械検証する
7. The UI デザイン基盤 shall 追加した部品の導入によって外部依存を増やさない

### Requirement 6: 参照デザインシステムの来歴とライセンスの保全

**Objective:** As a 後からこの意匠を読む開発者, I want 参照した原典と、そこから何を採り何を採らなかったかが辿れること, so that 上流の更新や意匠の再検討を根拠つきで行える

#### Acceptance Criteria

1. The リポジトリ shall 参照した DESIGN.md の内容を無改変の形で保持する
2. The リポジトリ shall 参照元の URL・取得時点の識別子・取得日・ライセンス表示を、無改変の内容とは別のファイルに保持する
3. The リポジトリ shall 参照元のライセンス全文を保持する
4. Where 無改変の内容がリポジトリの文書規約に反する記法を含むとき, the リポジトリ shall 当該ファイルを規約の検査対象から除外し、その除外が広がりすぎていないことを対照ケースで固定する

### Requirement 7: 退行の検出（赤化の実証を伴う）

**Objective:** As a このリポジトリを引き継ぐ開発者, I want 意匠が静かに壊れたときに CI が失敗すること, so that 画面を目視するまで気づけない劣化を持ち込まずに済む

#### Acceptance Criteria

1. If 操作を表す色のポインタ重畳時の色が静止時より明るくなったとき, then the 継続的インテグレーション shall 失敗する
2. If 成功を表す色が危険を表す色と同系色になったとき, then the 継続的インテグレーション shall 失敗する
3. If キーボード操作時の輪郭の色が隣接背景に対して 3:1 を割ったとき, then the 継続的インテグレーション shall 失敗する
4. If 見出しの既定が共通部品側と基盤側で食い違ったとき, then the 継続的インテグレーション shall 失敗する
5. The 開発者 shall 上記の各検証について、是正前の実装に対して失敗することを実証した記録を残す
6. The 開発者 shall 合成関数を用いる色の実測値を、実ブラウザで描画した結果から採録する
7. The 継続的インテグレーション shall デザイントークンと CSS の値の対応を、色の集合包含だけでなく意味役割ごとの厳密一致で検証する
