# Requirements Document

## Project Description (Input)
GitHub Issue #57「fix(ui): フォーム部品の枠線・選択状態が WCAG 非テキスト 3:1 未達（border-input 1.35:1）」に基づく是正。親 Issue #41 の子。#49 / #50 の是正（PR #56）で全部品の色使用を網羅捜索した際に検出され、**アルファ合成ではなくトークン素の値そのものが薄すぎる**問題であり、枠線の意匠全体に関わるため #49/#50 のスコープから切り出された、意匠判断が要る案件。

### (a) 誰が困っているか
ダッシュボードでフォーム部品（一行入力・複数行入力・チェックボックス・ラジオボタン）を視覚的に利用する利用者、特に低視力者。既定枠の色（対白コントラスト比 **1.358:1**）が WCAG 2.1 SC 1.4.11（非テキストコントラスト、要求 3:1）を満たさないため、これらの部品の**存在と境界を視覚的に識別できない**。選択肢を包むラベル領域の選択状態表示（**1.522:1**）も同様に識別困難。加えてエラー状態のチェック済み部品では枠が選択色（緑）へ戻ってしまい、**目で見ている利用者にだけエラーであることが伝わらなくなる**（`aria-invalid` 属性は残るためスクリーンリーダー利用者には伝わる）。

### (b) 現状
- #49 で対話的部品のフォーカス指標は 5.02:1 に統一済みだが、**フォーカスしていない状態の既定の輪郭**は依然として薄いまま。
- フォーム部品の枠色トークンは装飾用の枠色トークンと同値に設定されており、片方だけを濃くできない構造になっている。
- PR #56 の時点でこの項目は意図的にスコープ外とされ、コントラスト検証ガードの除外一覧に理由付きで保留されたまま、ガードは緑（意図的な保留）になっている。

### (c) 何が変わるべきか
- フォーム部品の既定枠と選択状態表示を 3:1 以上で識別可能にする。
- エラー状態でチェック済みの部品でも、エラーであることが視覚的に失われないようにする。
- 是正内容をコントラスト検証ガードの検証表へ移し、**移した時点で赤化することを確認してから**修正する（ガード先行の原則）。
- 意匠の変更方針を design フェーズで記録する。

### 完了条件（Issue #57 より）

## Introduction

本仕様は、`ui-design-foundation` で確立した共通 UI 部品のうち、**利用者が部品を識別するために必要な視覚情報**が WCAG 2.1 SC 1.4.11（非テキストコントラスト・要求 3:1）を満たしていない箇所を是正する。

対象は「フォーム入力部品の既定枠」「選択状態の表示」「エラー状態の表示」の 3 系統である。いずれも部品の状態を伝える唯一または主要な視覚手がかりでありながら、現在は 1.358:1〜1.522:1 と要求を大きく下回る。

> **数値の訂正記録（2026-08-01）**: Issue #57 の本文および `ts/packages/ui/test/contrast-usage.test.ts:190` の除外理由は、選択状態表示を「1.96:1 / `#B8D4C3`」と記載しているが、これは誤りである。正典ヘルパ（`@fwlm/design-tokens` の `contrastRatio` / `compositeOver`）による実測値は **1.522:1 / `#B9D9C5`** であり、Issue が掲載した検証スクリプトを逐語実行しても同値が得られる。既定枠は 1.35:1 ではなく **1.358:1**。本書はすべて実測値を採用する。詳細は `research.md` 第 2 節。

本仕様は同時に、この欠陥が**機械検証をすり抜けた構造**そのものを是正する。現在のコントラスト検証ガードは不透明度が明示された色指定しか検出対象にしておらず、不透明度なしの枠色指定は分類漏れの検出にも掛からない。是正の順序は「ガードを検証対象へ広げて失敗を実証する → 色を直す」であり、逆順は許さない。

意匠面では、**「部品の識別に必要な枠」と「情報を持たない純装飾の罫線」を別の意味役割として区別する**方針を採る。SC 1.4.11 が 3:1 を要求するのは前者のみであり、区切り線やカード下部の仕切りといった純装飾まで一律に濃くすることは規格が求めていない代償を意匠に強いるためである。この区別は「同一の意味役割に 1 トークン」（先行 spec 要件 1.3）と矛盾しない。識別用と装飾用は異なる意味役割である。

## Boundary Context

- **In scope**:
  - フォーム入力部品（一行入力・複数行入力・チェックボックス・ラジオボタン）の**既定状態の枠**の識別可能性
  - 選択肢を包むラベル領域の**選択状態表示**の識別可能性
  - **エラー状態**の表示が選択状態によって打ち消されないこと
  - 「識別に必要な枠」と「純装飾の罫線」の**意味役割としての分離**、および装飾側の現在の意匠の維持
  - 非テキストコントラストの**機械検証ガードの網羅範囲拡張**（不透明度の指定有無に関わらず検出する）
  - 上記に伴う色役割の追加が、既存のトークン単一情報源規律と機械検証を壊さないこと
- **Out of scope**:
  - **ダークモード**。ダーク配色は先行 spec の Non-Goal であり、本仕様でも導入しない。現在の無効化状態を維持する
  - **アプリ各面の画面デザイン**。各面の本格整備は #43 / #44 / #45 の範囲であり、本仕様は共通部品の定義のみを扱う
  - **カード外枠**。共有トークンに依存しない独立した指定であり、情報を持たない純装飾のため SC 1.4.11 の対象外
  - **テキストのコントラスト**（SC 1.4.3）の新規是正。既存のガードが担保しており、本仕様はその水準を下げない
  - **無効化された部品のコントラスト**。WCAG が明示的に対象外としている
  - **フォーカス指標**。#49 で 5.02:1 に統一済みであり、本仕様は「フォーカスしていない状態」を扱う
- **Adjacent expectations**:
  - 各面のデザイン整備（#43 / #44 / #45）は、本仕様が確定した「識別用／装飾用」の区別を前提として画面を組む
  - LINE 配信で使う色は独立した名前空間で管理されており、本仕様の色変更は LINE メッセージの見た目に波及しないことを前提とする
  - 既存の CI ガード（トークン単一情報源検証・役割対応の厳密一致検証・デプロイカバレッジ検証）は本仕様の変更後も全て緑であることを前提とする

## Requirements

### Requirement 1: フォーム入力部品の既定枠の識別可能性

**Objective:** As a 低視力の利用者, I want フォーム入力部品の輪郭が背景から明確に判別できること, so that 入力欄がどこにあり、どこまでが入力範囲なのかを目で把握できる

#### Acceptance Criteria

1. The UI 部品ライブラリ shall 一行入力・複数行入力・チェックボックス・ラジオボタンについて、部品の存在と境界を示す視覚情報と隣接する背景色とのコントラスト比を 3:1 以上に保つ
2. While 部品がフォーカスされておらず選択もされていない既定状態にある, the UI 部品ライブラリ shall フォーカス指標に依存せずに部品を識別可能にする
3. Where 部品が無効化されている, the UI 部品ライブラリ shall 前項までのコントラスト比要求を適用しない

### Requirement 2: 選択状態表示の識別可能性

**Objective:** As a 低視力の利用者, I want 選択済みの選択肢がどれか目で判別できること, so that 自分が何を選んだのかを確認できる

#### Acceptance Criteria

1. When 選択肢を包むラベル領域が選択状態になった, the UI 部品ライブラリ shall 選択状態を示す視覚情報と隣接する背景色とのコントラスト比を 3:1 以上に保つ
2. While ラベル領域が選択状態にある, the UI 部品ライブラリ shall 領域内のテキストと面塗り色とのコントラスト比を 4.5:1 以上に維持する
3. When ラベル領域が選択状態から未選択状態へ戻った, the UI 部品ライブラリ shall 選択状態を示す視覚情報を取り下げる

### Requirement 3: エラー状態の視覚的保全

**Objective:** As a 目で見て操作する利用者, I want 誤りのある部品がチェック済みであってもエラーだと分かること, so that 何を直せばよいのかを見つけられる

#### Acceptance Criteria

1. While 部品がエラー状態にある, the UI 部品ライブラリ shall 部品が選択済みであるか未選択であるかに関わらず、エラーであることを示す視覚情報を提示し続ける
2. When エラー状態の部品が未選択から選択済みへ遷移した, the UI 部品ライブラリ shall エラーを示す視覚情報を維持する
3. While 部品がエラー状態かつ選択済みである, the UI 部品ライブラリ shall 選択済みであることを示す視覚情報も同時に提示し続ける
4. While 部品がエラー状態にある, the UI 部品ライブラリ shall エラーを示す視覚情報と隣接する背景色とのコントラスト比を 3:1 以上に保つ
5. While 部品がエラー状態にある, the UI 部品ライブラリ shall エラーであることを色以外の手段でも提示する
6. While 部品がエラー状態にある, the UI 部品ライブラリ shall エラーであることを支援技術に伝達し続ける

### Requirement 4: 識別用と装飾用の意味役割の分離

**Objective:** As a プロダクトの意匠に責任を持つ運営, I want 部品の識別に必要な枠だけを濃くし純装飾の罫線は現在の淡い見た目のままにすること, so that アクセシビリティ要件を満たしつつ現在の意匠を失わない

#### Acceptance Criteria

1. The UI 部品ライブラリ shall 「部品の識別に必要な枠」と「情報を持たない純装飾の罫線」を別の意味役割として区別する
2. While 罫線が区切り線・カード下部の仕切り・情報コンテナの外枠として使われている, the UI 部品ライブラリ shall その罫線の色を、識別可能性の要件を理由として変更しない
3. When 新しい枠線の色使用を部品へ追加する, the UI 部品ライブラリ shall その枠線がいずれの意味役割に属するかを明示する
4. If 枠線が識別用と装飾用のどちらに属するか判断できない, then the UI 部品ライブラリ shall 識別用として扱う
5. While 枠線が対話的部品の輪郭を示している, the UI 部品ライブラリ shall その枠線を識別用として扱う

### Requirement 5: 非テキストコントラスト違反の機械的検出

**Objective:** As a この基盤を保守する開発者, I want 非テキストコントラスト違反が継続的検証で機械的に検出されること, so that 同種の欠陥が静かに再発せず、除外には必ず判断の記録が残る

#### Acceptance Criteria

1. The 継続的検証 shall 部品が使う色指定を、不透明度の指定有無に関わらず検出対象とする
2. If 検出された色指定が検証表にも除外一覧にも登録されていない, then the 継続的検証 shall 検証を失敗させる
3. When 色指定を除外一覧へ登録する, the 継続的検証 shall 除外の根拠が記述されていることを要求する
4. If 検証表または除外一覧に、部品側に実在しない色指定が残っている, then the 継続的検証 shall 検証を失敗させる
5. The 継続的検証 shall 部品の識別に必要な色使用に 3:1、テキストの色使用に 4.5:1 のしきい値を適用する
6. When 本仕様の是正を実施する, the 開発プロセス shall 対象を検証表へ移して検証が失敗することを確認したのちに色の是正へ着手する
7. Where ダークモード配色が導入されていない, the 継続的検証 shall ダークモード専用の色指定を検出対象から除外し、その除外理由を記録する

### Requirement 6: トークン単一情報源規律の保全と副作用の抑止

**Objective:** As a この基盤を保守する開発者, I want 色の値の単一情報源が保たれ枠色の変更が無関係な状態の見た目を巻き添えにしないこと, so that 変更の影響範囲が予測可能で、後から値を差し替えられる

#### Acceptance Criteria

1. When 新しい色役割を導入する, the デザイントークン基盤 shall 値の単一情報源に定義を追加し、意味役割と参照名の対応を明示する
2. If 新しい色役割が単一情報源と役割対応のいずれか一方にのみ存在する, then the 継続的検証 shall 検証を失敗させる
3. When 枠線に使う色の値を変更する, the UI 部品ライブラリ shall 同じ色を面塗りに使っている状態（無効化された入力欄の塗りなど）の見た目が意図せず変化しないことを保証する
4. If 枠線の色変更が他の状態の見た目を変化させる, then the UI 部品ライブラリ shall その変化を意図された意匠判断として記録する
5. The デザイントークン基盤 shall LINE 配信で使う色の名前空間に影響を与えない
6. The UI 部品ライブラリ shall ダークモードの配色を導入せず、現在の無効化状態を維持する
7. When 色の値を直書きで指定する, the 継続的検証 shall その混入を検出して失敗させる

## 今後の判断事項（design フェーズへの引き継ぎ）

以下は要件段階では確定させず、design フェーズで Boundary Commitments として決定する。

1. **識別用の枠色の具体値**: 3:1（例 3.03:1 相当）で足りるか、テキストにも使える 4.5:1 相当まで濃くするか。濃くするほど安全だが意匠は重くなる。
2. **識別用トークンの表現形式**: 既存の別名変数の値を分岐させるか、新しい色役割として単一情報源へ追加するか。後者は役割対応表・網羅ガード・直書き検出の 3 つを同時に更新する必要がある。
3. **対話的部品の枠の帰属**: ボタンやバッジの輪郭線を識別用に含めるか。Requirement 4.5 により対話的部品の輪郭は識別用となるが、輪郭が部品識別の唯一の手がかりでない場合（面塗りや文字で識別できる場合）の扱いを整理する。
4. **無効化状態の面塗りの扱い**: Requirement 6.3 の保証を、枠色と面塗り色を別トークンに分けて達成するか、面塗り側の不透明度を調整して達成するか。
5. **エラー×選択済みの視覚表現の詳細**: 枠をエラー色に保つ方式を採る前提で、選択済みの面塗りとエラー枠が同時に出る配色の実効コントラストを実測して確定する。
6. **ガード拡張で新たに検出される色使用の分類**: 拡張により炙り出される既存の色使用を、識別用として是正するか、根拠付きで除外するかを一件ずつ判定する。
