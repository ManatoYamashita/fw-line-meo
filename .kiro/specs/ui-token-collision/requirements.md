### 誰が問題を抱えているか

- **各面を実装する開発者（#43 LIFF / #44 客向け Web / #45 管理画面）**: `max-w-md` のような**ごく普通の Tailwind の書き方が、書いたとおりに描画されない**。しかも失敗が例外ではなく「幅が違う」という形で現れるため、部品の欠陥かレイアウトの欠陥か切り分けられない。
- **各面の利用者**: 上記の結果としてコンテナ幅が潰れた画面を見る。PR #59 では `/ui-check` が端末幅 393px に対して**実幅 16px** で描画されていた。
- **デザインシステムを読む開発者**: Button（`rounded-lg`）と Card（`rounded-xl`）が同じ角丸で描かれ、「小さなコントロール」と「容器」の視覚階層が 1 段潰れている。意図した差が実装に存在しないため、後から見た人はどちらが正しいのか判断できない。

### 現状（2026-08-02 実測）

生成 CSS を実コンパイルして確認した（`ts/apps/survey-web/src/app/globals.css` を PostCSS + `@tailwindcss/postcss` で処理）。

```
.max-w-md { max-width: var(--spacing-md); }   ← --container-md ではない

--spacing: 0.25rem;
--spacing-md: 1rem;
--container-md: 28rem;    ← 生成されているが参照されない

--radius-lg: 0.75rem;
--radius-xl: 0.75rem;     ← 同値
```

- **`ts/packages/ui/src/theme.css:41-46`** が `--spacing-{xs,sm,md,lg,xl}` を定義している。これは Tailwind v4 で**サイズ系ユーティリティが参照する名前空間**であり、組み込みの `--container-*` を覆う。
- **名前付き余白ユーティリティ（`p-md` / `gap-lg` / `w-sm` 等）はコードベースに 1 箇所も無い**（`rg` で全走査）。`--spacing-*` の現在の効果は「サイズ系ユーティリティを壊すこと」だけである。
- **design-tokens の余白値は Tailwind の数値スケールと完全に一致する**。`--spacing: 0.25rem` に対し xs=0.25(`*-1`) / sm=0.5(`*-2`) / md=1(`*-4`) / lg=1.5(`*-6`) / xl=2(`*-8`)。
- **`ts/packages/ui/src/theme.css:48-51`** は `--radius-sm/md/lg` を上書きするが `--radius-xl` は上書きしていない。Tailwind 既定の `--radius-xl`（0.75rem）が残り、上書きした `--radius-lg`（0.75rem）と同値になる。design-tokens の `radius` に `xl` は存在しない。
- **余白・角丸の同期を保証するガードが存在しない**。`ts/packages/ui/test/theme-sync.test.ts` と `scripts/check-design-tokens.sh` はいずれも **hex 色しか照合していない**。したがって上記 2 件はどちらも CI 全緑のまま存在し続けた。
- PR #59（Issue #52）は (0) を踏み、`ts/apps/survey-web/src/app/ui-check/page.tsx:49-56` で `max-w-[28rem]` という任意値により**回避したにとどまる**。同ファイルの注釈と `ts/apps/survey-web/e2e/ui-foundation.spec.ts:448` の失敗メッセージが、いずれも本 Issue を名指しして先送りを記録している。

### なぜ今やるか

**本 spec は #43 / #44 / #45（各面のデザイン整備）のゲートである。** `max-w-*` は各面のレイアウトで必ず使われる。面を組んでから直すと全面の再調整になる。角丸階層も同様で、各面がどちらの角丸を「正」として組むかが決まらないまま進むと、後から揃えるのが難しくなる。

### 何が変わるべきか

1. 名前付きスケールのサイズ指定（`max-w-md` 等）が、Tailwind の意図した値で描画される。
2. 小さなコントロールと容器が異なる角丸で描画され、視覚階層が復活する。
3. 余白・角丸についても、design-tokens と生成 CSS の対応が**機械照合**される。色と同水準の保証を持つ。
4. これらが失われたときに CI が失敗する。**是正前の実装に対して赤化することを実証してから導入する**。
5. `/ui-check` の回避（`max-w-[28rem]`）と、E2E の先送り記述が解消される。

### 制約・前提

- **ベンダリングした部品ソース（`ts/packages/ui/src/components/**`）は書き換えない。** ベンダリング元との差分を増やすと次回の `shadcn add` で巻き戻る。`theme.css` が採ってきた「アプリ／部品の DOM を変えずに直す」方針を維持する。
- **design-tokens の `spacing` は残す。** LINE Flex Message など CSS 以外の消費先にとっての単一情報源であり、値そのものは正しい。
- **カスケードレイヤと名前空間の罠**: 本リポジトリは同型の欠陥を繰り返している（#48 見出し階層の消失・#49 フォーカス指標の無効化・#52 動き低減の未対応）。いずれも**画面は正常に見えるまま無言で壊れる**種類であり、機械検証でしか守れない。
- **ガードの規律（#60）**: 抽出器には自己検証を付ける。赤化実証は注入位置を最低 2 通り試す。CSS の機械検証は postcss の構文木を使い、`プロパティ: 値;` の正規表現で宣言を拾わない。
- **性能予算**: survey-web は `perf:budget`（client JS 300KB）と Lighthouse mobile（LCP 3 秒）の制約下にある。本件は CSS 変数の増減のみで JS には影響しない見込みだが確認する。
- **対象外**: 生成 CSS のサイズ予算ガードの新設は #53 が扱う。ダークパレットの定義そのものは Non-Goals（残債の記録のみ行う）。

- `.dark` パレット未定義のまま `dark:*` クラスが部品に残存している件を「ダークモード着手時の起点」として記録する

### 確定した判断（2026-08-02・利用者合意）

要件生成時に、開発者から観測できる振る舞いが分岐する 2 点を確認し、次のとおり確定した。

1. **名前付き余白ユーティリティ（`p-md` / `gap-lg` / `w-sm` 等）は CSS 上で提供しない。** 余白は Tailwind の数値スケール（`p-4` 等）で指定する。デザイントークンの `spacing` は LINE Flex Message など CSS 以外の消費先の単一情報源として維持する。根拠は「名前付き余白ユーティリティの使用箇所が 0 件」かつ「トークンの余白値が数値スケールと完全一致（xs=`*-1` / sm=`*-2` / md=`*-4` / lg=`*-6` / xl=`*-8`）」であること。
2. **角丸は Tailwind 既定スケールへ寄せる。** 押しボタンは現在の 0.75rem から既定の `lg`（0.5rem）へ縮まり、容器（カード）の `xl`（0.75rem）は据え置く。ベンダリングした部品は既定スケールを前提に書かれているため、今後 `shadcn add` した部品も無調整で階層が揃う側を採る。


## Introduction

本仕様は、`@fwlm/ui` の `theme.css` が定義するデザイントークンが Tailwind CSS v4 の組み込みスケールと衝突し、**書いたとおりの値で描画されない**状態を解消する。対象は 2 件である。(0) 余白トークンがサイズ系ユーティリティの解決先を覆い、`max-w-md` が 28rem ではなく 1rem へ潰れる件。(1) 角丸スケールの部分的な上書きにより、押しボタンと容器が同径で描かれ視覚階層が 1 段失われている件。あわせて、余白・角丸についてもデザイントークンとの一致を機械照合する土台を確立し、Issue #54 が併記した記録・追補を文書へ反映する。

**本仕様は各面のデザイン整備（#43 LIFF / #44 客向け Web / #45 管理画面）のゲートである。** 最大幅の指定は各面のレイアウトで必ず使われ、角丸階層は各面が「正」とみなす基準になる。面を組んでから直すと全面の再調整になる。

いずれの欠陥も、**画面は正常に見えたまま無言で壊れる**種類である（本リポジトリは #48 見出し階層の消失・#49 フォーカス指標の無効化・#52 動き低減の未対応で同型を繰り返している）。したがって是正そのものと同じ重さで、失われたときに CI が失敗する仕掛けを要求する。

本仕様が扱うのは開発者および利用者に観測できる振る舞い（解決される実寸・描画される角丸・CI の成否・文書の記述）であり、どのトークンをどう定義し直すかといった実現手段は design フェーズで決定する。

## Boundary Context

- **In scope**: `theme.css` とデザイントークンが全 UI 面へ与える (1) 名前付きスケールによる寸法の解決先、(2) 角丸スケールの段差、(3) 余白の指定手段。ならびにこれらが失われたときに失敗する自動検証、検証面に置かれた回避策の解消、Issue #54 が併記した記録・追補の文書反映。
- **Out of scope**:
  - 生成 CSS のサイズ予算ガードの新設 — #53 が扱う（本仕様は実測値の記録までを担う）
  - 暗色パレットの定義そのもの — 記録のみ行う
  - 各面の画面デザイン — #42（LINE）/ #43（LIFF）/ #44（survey-web）/ #45（dashboard-web）が扱う
  - フォーム部品の枠線・選択状態の非テキストコントラスト — #57 が扱う
  - **色トークンの役割・値の変更** — 本仕様は `theme.css` の色定義に触れない
  - タイポグラフィ・影・色の各スケールの見直し — これらは**同名の既定を意図的に上書き**するものであり、本仕様が扱う「別のスケールを覆う」衝突には当たらない
- **Adjacent expectations**:
  - #43 / #44 / #45 は本仕様の完了後に着手し、名前付きスケールによる寸法指定と角丸階層をそのまま前提にできることを期待する。
  - Issue #57 が同じ `theme.css` の色役割行を別の作業ツリーで編集中である。本仕様は色定義に触れないため、双方は同一ファイルの異なる領域を変更し、独立に成立することを前提とする。
  - LINE Flex Message はデザイントークンの余白値を CSS を経由せず値として消費する。本仕様が `theme.css` の余白定義を変更しても LINE 側の描画は変わらないことを期待する。
  - #53 が導入する生成 CSS のサイズ予算は、本仕様が記録する実測値を基準線として利用できることを期待する。
  - ベンダリング元（shadcn）は Tailwind 既定の角丸スケールを前提に部品を出力する。本仕様の是正後は、今後追加する部品も無調整で階層が揃うことを期待する。

## Requirements

### Requirement 1: 名前付きスケールによる寸法指定の復旧

**Objective:** As a 各面を実装する開発者, I want 名前付きスケールで指定した寸法が意図した値で描画されること, so that レイアウトの崩れを部品の欠陥と切り分ける手間なく各面を組める

#### Acceptance Criteria

1. When 名前付きスケール（xs〜xl）で最大幅・最小幅・幅・フレックス基準幅を指定したとき, the UI デザイン基盤 shall 既定のコンテナ寸法スケール（`md` = 28rem）へ解決した実寸で描画する
2. While 端末幅がコンテナ寸法を下回る画面で最大幅を名前付きスケールで指定した容器が描画されているとき, the UI デザイン基盤 shall 当該容器を端末幅から外側余白を除いた幅で描画し、余白スケール由来の寸法へ縮退させない
3. The UI デザイン基盤 shall 名前付きスケールによる寸法指定の解決先を、客向けアンケート Web・LIFF 店舗詳細・管理ダッシュボードの 3 面すべてで同一にする

### Requirement 2: 余白の指定手段の単一化

**Objective:** As a デザインシステムを利用する開発者, I want 余白の指定手段が一つに定まっていること, so that 同じ余白に二通りの書き方が併存して値が枝分かれすることがない

#### Acceptance Criteria

1. The UI デザイン基盤 shall 余白の指定手段として数値スケール（`p-4` 等）のみを提供し、名前付き余白ユーティリティ（`p-md` / `gap-lg` / `w-sm` 等）を提供しない
2. When 開発者が数値スケールで余白を指定したとき, the UI デザイン基盤 shall デザイントークンの余白値（xs=0.25rem / sm=0.5rem / md=1rem / lg=1.5rem / xl=2rem）と同一の実寸を描画する
3. The デザイントークン shall LINE Flex Message など CSS 以外の消費先の単一情報源として、余白トークンの定義と値を維持する
4. The デザインシステム文書 shall 余白トークンと数値スケールの対応（xs→1 / sm→2 / md→4 / lg→6 / xl→8）を明記する

### Requirement 3: 角丸の視覚階層の復活

**Objective:** As a 各面を見る利用者およびデザインシステムを読む開発者, I want 小さなコントロールと容器が異なる角丸で描かれること, so that 意図された視覚階層が実際の画面に存在する

#### Acceptance Criteria

1. When 押しボタンと容器（カード）が同一画面に描画されたとき, the UI デザイン基盤 shall 押しボタンに容器より小さい角丸半径を与える
2. The UI デザイン基盤 shall 角丸スケールの各段が互いに異なる値へ解決される状態を保つ
3. When 角丸ユーティリティが解決されたとき, the UI デザイン基盤 shall デザイントークンの角丸定義と役割ごとに対応付けられた実寸を与え、対応の無い値を描画に用いない
4. Where ベンダリングした共通コンポーネントが角丸を指定しているとき, the UI デザイン基盤 shall 部品ソースを書き換えずに階層を成立させる

### Requirement 4: 回避策と先送り記述の解消

**Objective:** As a 検証面を保守する開発者, I want 衝突を避けるために置いた任意値と先送りの注記が解消されること, so that 検証面が本番と同じ書き方で組まれ、注記と実態の食い違いに惑わされない

#### Acceptance Criteria

1. When 是正が完了したとき, the UI 検証面 shall コンテナ幅を名前付きスケールで指定し、衝突を避けるための任意値を用いない
2. When UI 検証面がスマートフォン幅（端末幅 393px）で描画されたとき, the UI 検証面 shall 主要領域を端末幅の 80% 以上の実幅で描画する
3. The UI 検証面および自動検証 shall 本件の未解決を理由に回避・先送りしている旨の記述を残さない

### Requirement 5: 衝突と乖離の再発を止める自動検証

**Objective:** As a 開発者および運営, I want トークンの名前空間衝突とデザイントークンからの乖離が CI で検出されること, so that 同種の欠陥が「CI 全緑のまま」再び各面へ波及しない

#### Acceptance Criteria

1. If あるスケールへ追加した定義が、別のスケールを参照して解決されるはずのユーティリティの解決先を覆ったとき, the 継続的検証 shall どの定義がどのユーティリティを覆うかを示して失敗する
2. If 名前付きスケールによる寸法指定が余白スケールへ解決されたとき, the 継続的検証 shall 失敗する
3. If 角丸スケールのいずれか 2 段が同値へ解決されたとき, the 継続的検証 shall 失敗する
4. The 継続的検証 shall デザイントークンの余白値および角丸値が、実際に描画へ用いられる指定手段の解決結果と一致することを役割ごとの対応で検証し、値の集合が重なっていることでは代替しない
5. If デザイントークンの余白値が数値スケールで表現できない値へ変更されたとき, the 継続的検証 shall 失敗する
6. The 継続的検証 shall 対応の検証を両方向（指定手段側の網羅・デザイントークン側の網羅）で行い、片側にのみ存在する定義を検出して失敗する
7. The 継続的検証 shall 判定を実際に生成された CSS の解決結果に対して行い、定義元の字面の一致では代替しない
8. The 継続的検証 shall 照合対象の抽出結果が空でないことを自ら検証し、抽出漏れによる空振りの成功を出さない
9. The 継続的検証 shall 各検証項目について、是正前の実装に対して失敗することが実証された状態で導入される
10. If UI 検証面の主要領域の実幅が端末幅に対して過小になったとき, the 継続的検証 shall 失敗する

### Requirement 6: 既存の品質の非後退

**Objective:** As a 全 UI 面の利用者および開発者, I want 本仕様の変更が既に整った品質を損なわないこと, so that 一つの是正が別の劣化と引き換えにならない

#### Acceptance Criteria

1. The 共通コンポーネント shall ベンダリング元との差分を増やさず、部品ソースの書き換えなしに本仕様を満たす
2. The UI デザイン基盤 shall 見出しの視覚階層・キーボード操作時の可視フォーカス表示・動き低減設定下の抑制を現状のまま維持する
3. The UI デザイン基盤 shall 現在満たしている色のコントラスト要件を後退させない
4. The UI デザイン基盤 shall 客向けアンケート Web のクライアント JS 予算（300KB gzip）を超過しない
5. When 是正が完了したとき, the UI デザイン基盤 shall 生成 CSS の実測サイズを記録する
6. The UI デザイン基盤 shall 3 つの Web アプリすべてでビルドと既存の自動検証を成功させる

### Requirement 7: 残債と設計判断の記録

**Objective:** As a 後から参加する開発者, I want 未着手の残債と過去の設計判断が文書に残っていること, so that 記録の欠落や実装との食い違いに惑わされない

#### Acceptance Criteria

1. The デザインシステム文書 shall 暗色パレットが未定義のまま共通コンポーネントに暗色向けクラスが残存している事実と、暗色対応に着手する際の起点を記録する
2. The デザインシステム文書 shall 共通コンポーネントに一括 export の入口（バレル）を設けない判断の理由を記録する
3. The デザインシステム文書 shall 部品構成の記述（ファイル構成計画・部品一覧）を実体の部品構成と一致させる
4. The デザインシステム文書 shall 生成 CSS サイズの記録を実測値と一致させる

## 今後の判断事項（design フェーズへの引き継ぎ）

- **角丸を既定スケールへ寄せる具体的な手段**: `theme.css` から角丸の上書きを外すか、既定と同値で明示的に宣言し直すか。前者を採る場合、「デザイントークンが角丸の単一情報源」という現在の建付けとどう両立させるか（トークン側の `radius` を既定と同値へ改めるのか、CSS 以外の消費先向けの値として据え置き対応表で結ぶのか）を決める必要がある。
- **小寸法の押しボタンへの波及**: 押しボタンの xs/sm 変種は角丸に `min(var(--radius-md), 10px)` 等の指定を持ち、`--radius-md` の値に依存する。既定へ寄せると 8px → 6px へ変わるため、視覚上の許容を確認する。
- **名前空間衝突ガードの検出範囲**: 「別スケールを覆う」判定をどこまで一般化するか（既知の対応表を持つか、生成 CSS の解決結果から機械的に導くか）。過検出すると、意図した同名上書き（タイポグラフィ・影・色）まで赤くなる。
- **余白トークンと数値スケールの対応の置き場所**: デザイントークンのソース・設計文書・機械照合のいずれに正典を置くか。
- **既存ガードへの波及範囲**: 余白・角丸の照合を既存の色ガード（`theme-sync.test.ts` / `check-design-tokens.sh`）へ足すか、別の検証として分けるか。
