# Implementation Plan

> **実装順序の規律**:
> - 判断はまず正典へ書く（要件 9.1）。
> - 構造契約の検証は、実装を足す前に強める（要件 9.2）。
> - 各タスクの「観察可能な完了」に書いた赤・緑・件数が得られなければ、検証が対象へ接続していない。そのまま先へ進まない。
>
> **既知の地雷**（詳細は design.md「実装上の注意（既知の地雷）」）: どのタスクでも次を守る。
> - app コードに前置なしの `#265` を書かない（hex 色と誤検出される）。「Issue #265」と書く。
> - store-detail のテストとコメントを含めて、`bg-primary`・`bg-card`・`field-sizing-content`・`animate-spin`・`outline-none`・単独の語 `dark` を書かない。
> - 「★」付きの評価・「近隣N店中」・「Google 評価」・「表示期間の変化」・「自店の評価」・「新着クチコミ」を、新しい文言で重複させない。
> - `catch {}` を書かない。
> - 新しいファイルは `app/store/` か `lib/` に置く（`components/` を作ると lint の対象から外れる）。
>
> **文書のタスク**: 1.1 と 1.2 は、要件 7.8・9.1 が求める正典と spec の改定である。文書そのものの検査（design-language-doc テスト・節番号・強調記号）で検証する。
>
> **実施記録**: 変異の結果・実描画の確認・ゲートの結果は、該当タスクの下へ「実施記録」として追記する。コミットや run の識別子は先頭 8 文字で書く。

## Implementation Notes
- 実行環境: 既定のシェルの node は v20 で、ts の engines は 24 以上を求める。コマンドの先頭で `export PATH="$HOME/.nvm/versions/node/v24.13.0/bin:$PATH"` を実行する。Bash ツールは zsh なので、引用符の無い `$VAR` は単語に分かれない。コマンドは明示して書く（`--filter` が空振りしても終了コードは 0 になる）。

- spec の Markdown も、強調記号の検査の対象になる。`**…「…」**を` のように約物で閉じた強調は、GFM では閉じない。
