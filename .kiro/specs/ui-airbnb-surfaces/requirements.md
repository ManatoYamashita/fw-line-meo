# Requirements Document

## Project Description (Input)

出典: GitHub Issue [#41](https://github.com/ManatoYamashita/fw-line-meo/issues/41)（親・トラッキング）。
本 spec が閉じる子 Issue: [#43](https://github.com/ManatoYamashita/fw-line-meo/issues/43)（店舗詳細画面）・
[#44](https://github.com/ManatoYamashita/fw-line-meo/issues/44)（客向けアンケート）・
[#45](https://github.com/ManatoYamashita/fw-line-meo/issues/45)（管理ダッシュボード）。
先行 spec `ui-airbnb-foundation` が #173（トークン層）と #174（共通部品 5 点）を、#175 が写像版文書を閉じている。

[#42](https://github.com/ManatoYamashita/fw-line-meo/issues/42)（LINE 面）は本 spec に含めない。
#41 の作業単位表で唯一 #174 に依存せず、技術基盤（CSS・共通部品・トークンの CSS 経由参照）を 1 つも共有せず、
検証手段もスナップショットで別物であるため、別の単位として扱う（2026-09-03・利用者合意）。
先行 spec の Project Description は「後続 spec が #42・#43・#44・#45 を閉じる」と書いていたが、
本 spec の起票にあたってこの分界を見直した。

作業場所: 専用 worktree `.claude/worktrees/spec-ui-airbnb-surfaces`（branch `spec/ui-airbnb-surfaces-41`・起点 `origin/main` = `49d10f7`）。
他セッションが並行稼働しているため隔離した。

### 誰が問題を抱えているか

- **クライアントへデモを見せる運営（我々）**: 基盤は 3 層（トークン・共通部品・写像版文書）そろったが、
  **どの画面もその成果を受け取っていない**。デモで見えるのは依然としてブラウザ標準描画である。
- **管理画面を日常的に使う運営・代理店**: 一覧・フォーム・ナビが素の HTML のままで、
  情報の階層も操作の可否も見た目から読み取れない。キーボード操作が主体の面であるにもかかわらず、
  焦点の可視性は共通部品を通る 5 箇所でしか保証されていない。
- **QR から流入する来店客**: 満足度の星が現状のアクセント色を参照しており、
  トークン差し替え後は**満足度評価が赤い星で描かれる**。赤はエラーとして読まれる。
- **各面を実装する開発者**: 面ごとに意匠を判断すると必ず食い違う。判断の正典は既に 1 箇所にあるが、
  面の側がそれを参照する規律は、まだどこにも書かれていない。

### 現状（2026-09-03 実測・起点 `49d10f7`）

本番画面が実際に通っている共通部品は 5 種だけである。

```
Alert / Button / Card / Heading / Spinner        本番画面で使用中（3 ファイル・8 import）
Table / PageShell / PageHeader / EmptyState / Select   本番画面での使用 0 件（#174 で追加・検証面のみ）
Badge / Checkbox / Field / Input / Label / RadioGroup / Separator / Textarea   本番画面での使用 0 件
```

`className` を 1 つも持たないファイルが 9 個ある（`store-detail` の唯一の画面は 417 行で 0 個）。
素の要素の実数は次のとおり。

```
表          5 個   （管理ダッシュボード 4 / 店舗詳細 1）
選択        6 個   （すべて管理ダッシュボード）
記入欄      5 個   単一行
複数行入力  2 個
押しボタン 17 個
ラベル     12 個
見出し     26 個   共通の見出し部品を通っているのは 1 箇所のみ
```

先行 spec が積み残した受入基準が 2 つある。**面をまたいだ同一描画**は、3 面とも部品の利用が
ほぼ無いため前件が成立せず一度も実証されていない。**余白の適用**は、トークンが定義済みでも
どの画面にも適用されていない。

既存の検証が固定している構造契約は、意匠の適用で壊れうるものを正確に見張っている。
写像版文書の 8 節に一覧があり、要素の個数・読み上げ名・列見出しの完全一致・主要領域の単一性に及ぶ。

性能の余裕は限られている。客向けアンケートの実行コードは予算 300KB gzip に対して現状 213.6KB、
最大要素の描画完了は 3000ms が失敗閾値である。実ブラウザ検証は客向けアンケートにしか無い。

### なぜ今やるか

基盤 3 層が閉じ、面適用を阻む依存は残っていない。一方で**デモとして成立する線**は
「トークン → 共通部品 → 管理ダッシュボード → 店舗詳細 → 客向けアンケート」であり、
ここが空白だとデモが成立しない。共通部品 5 点は追加されたが消費者がゼロであり、
使われないまま次の意匠変更を迎えると、部品の設計が実際の面に耐えるかを一度も確かめないことになる。

### 何が変わるべきか

- 3 面が共通部品と共通のトークンを通って描画され、同じ役割の要素が面をまたいで同じに見える。
- 一覧が表の意味論を保ったまま装飾され、0 件のときに次の操作へ進める。
- 既存の構造契約と、アクセシビリティの現行水準（焦点の可視・実効コントラスト・操作領域・動き低減・横スクロール不発生）が、
  意匠の適用後も維持される。
- 性能の予算と閾値を割らない。
- 意匠の判断を面ごとに新設せず、写像版文書を正典として参照する。

### 制約・前提

- **意匠の判断の正典は `docs/design/design-language.md` である**（#175 の決定）。本 spec は結論も数値も転記せず、参照する。
- **共通部品を書き換えない**（`ui-token-collision` の運用規約）。面の都合で部品を変える必要が生じたら、それは部品側の課題として切り出す。
- **overlay 系の部品を新規にベンダリングしない**（先行 spec D6 の判断）。バンドルの増分をゼロに保つ。
- **書込操作の要素を店舗詳細画面へ導入しない**。これは意匠上の好みではなく、当該面の構造契約である。
- **選択はブラウザ標準の選択要素の振る舞いを保つ**（先行 spec の受入基準 5.3 が既に要求している）。
- **生の色を書かない**。直書きの色リテラルと既定パレットの色クラスは CI が落とす。
- **無効状態の通知手段は 1 つに統一できない**。既存の検証には、焦点が到達し続けることを要求する箇所と、
  ブラウザ標準の無効属性そのものを要求する箇所の両方が実在する。統一を目指すと必ずどちらかが壊れる。
- **客の個人情報を扱わない**という不可侵制約と、**低評価の客も同一の投稿導線へ誘導する**という不可侵制約は、
  意匠の変更によっても崩さない。

### 確定した判断（2026-09-03・利用者合意）

利用者から観測できる振る舞いが分岐する 2 点を確認し、次のとおり確定した。

1. **本 spec は Web 3 面（#43 / #44 / #45）を対象とし、LINE 面（#42）を含めない。**
   LINE 面は技術基盤も検証手段も共有せず、トークン層にも依存しない。
2. **先行 spec の分界の記述を実態へ直す。** 「後続 spec が #42・#43・#44・#45 を閉じる」という記述は
   本 spec の起票時点で誤りになるため、同じ変更で是正する。

## Introduction

本仕様は、確立済みのデザイン基盤を **3 つの Web 面へ実際に適用する**。
扱うのは利用者に観測できる振る舞いである。すなわち、同じ役割の要素が面をまたいで同じに見えること、
一覧が支援技術から表として読めること、対象が 0 件のときに次の操作へ進めること、
焦点と状態が見えること、携帯端末の幅で横に溢れないこと、そして客向けの面が現行の性能予算を割らないこと。

どの面をどの順で着手するか、どの部品をどこへ当てるか、実描画の検証をどこまで足すかといった実現手段は
design フェーズで決定する。

**本仕様は基盤の成果を初めて実際の画面へ届ける単位である。** 同時に、意匠の適用が
既存の構造契約とアクセシビリティの水準を壊しうるため、壊れたときに CI が失敗する状態を維持することを、
意匠の適用そのものと同じ重さで要求する。

## Boundary Context

- **In scope**: 管理ダッシュボード・店舗詳細画面・客向けアンケートの 3 面における、
  ページの版面と主見出しの一貫、一覧と空状態の表現、フォームと選択の表現、通知と処理中の表現、
  面をまたいだ同一描画、既存の構造契約とアクセシビリティ水準の維持、性能予算の遵守、
  ならびに以上が失われたときに失敗する自動検証と、実描画でしか確認できない事項の目視記録。
- **Out of scope**:
  - **LINE 面の意匠** — #42 が別の単位として扱う。本 spec の基盤を共有しない
  - **共通部品そのものの追加・変更** — 先行 spec `ui-airbnb-foundation` が閉じた層であり、必要が生じたら別途切り出す
  - **意匠の判断の新設** — 正典は `docs/design/design-language.md` であり、本 spec は参照する側である
  - **overlay 系部品のベンダリング** — 3 面いずれも必要としないと判断済み
  - **視覚回帰テスト・自動アクセシビリティ検査・生成 CSS のサイズ予算・新しい面への実ブラウザ検証基盤の新設** — #53 が扱う
  - **Web フォントの導入** — 導入判断は据え置かれている
  - **暗色パレット** — 先行 spec の非目標を継承する
- **Adjacent expectations**:
  - 本仕様は、共通部品とトークンが先行 spec の完了状態のまま使えることを期待する。部品の不足が判明した場合、本仕様は部品を書き換えず課題として差し戻す。
  - 本仕様は、意匠の判断が `docs/design/design-language.md` に記述済みであり、面の側が新たな判断を持ち込まずに済むことを期待する。
  - 既存の構造検証（要素の個数・読み上げ名・列見出し・主要領域の単一性）は、本仕様の変更後も同じ意味を保つことを期待する。本仕様はそれらを弱めない。
  - #53 が導入する検証基盤は、本仕様が触れた面を追加の配線なしに射程へ入れられることを期待する。
  - #42 は、本仕様が Web 側の意匠を変えても LINE 側の描画が変わらないことを期待する。

## Requirements

### Requirement 1: 面をまたいだ意匠の一貫

**Objective:** As a 3 面を横断して使う運営・代理店, I want 同じ役割の要素が面をまたいで同じ見た目と状態表現で描かれること, so that 面ごとに読み方と操作を学び直さずに済む

#### Acceptance Criteria

1. The 各 Web 面 shall ページの版面・主見出し・一覧・空状態・選択・通知・処理中の表示を共通部品から描画する
2. While 同一の役割を持つ要素が異なる Web 面に描画されているとき, the 各 Web 面 shall 同一の寸法・色・状態表現で描画する
3. The 各 Web 面 shall 意匠の値を共通の定義から参照し、面ごとの独自の値を持たない
4. If 面の実装が生の色（色リテラルまたは既定パレットの色クラス）を導入したとき, then the 継続的インテグレーション shall 失敗する
5. The 各 Web 面 shall ページの余白と行間を共通の律に従って与え、要素が端に接した状態で描画しない

### Requirement 2: 一覧と空状態

**Objective:** As a 一覧から対象を探す運営・代理店, I want 一覧が表として読め、0 件のときに次の操作へ進めること, so that 支援技術でも視覚でも同じ情報構造をたどれる

#### Acceptance Criteria

1. While 一覧が描画されているとき, the 各 Web 面 shall 行・列・セルの支援技術上の役割を保つ
2. The 各 Web 面 shall 一覧の列見出しとして読み上げられる文字列を変更しない
3. When 一覧に表示する対象が 0 件のとき, the 各 Web 面 shall 対象が無い旨と、次に取れる操作への導線を提示する
4. While 行そのものが操作の対象でないとき, the 各 Web 面 shall 行に重畳したときの面の塗りを変えない
5. When 一覧の幅が表示領域を超えたとき, the 各 Web 面 shall 一覧の内部だけを横方向にたどれる状態にし、ページ全体を横に溢れさせない

### Requirement 3: 既存の操作契約の維持

**Objective:** As a 既存の動作に依存している利用者と検証, I want 意匠の適用が操作の構造を変えないこと, so that 見た目の変更が機能の退行を連れてこない

#### Acceptance Criteria

1. The 店舗詳細画面 shall 書込操作の要素（フォーム・押しボタン・記入欄・複数行入力・選択）を 1 つも描画しない
2. The 各 Web 面 shall 既存の操作要素とリンクについて、支援技術に読み上げられる名前を変更しない
3. The 各 Web 面 shall 既存の検証が個数を固定している要素（操作要素・リンク・主要領域・ナビゲーション領域）について、その個数を変えない
4. The 管理ダッシュボード shall 選択の操作について、ブラウザ標準の選択要素と同一の振る舞いと属性を保つ
5. While 操作が実行できない状態のとき, the 各 Web 面 shall その状態を支援技術へ通知し、焦点が到達し続ける必要がある操作と到達を止めてよい操作とで、通知の手段を使い分ける
6. If 上記のいずれかが失われたとき, then the 継続的インテグレーション shall 失敗する

### Requirement 4: アクセシビリティ水準の維持

**Objective:** As a 支援技術の利用者・キーボード操作の利用者・色覚特性を持つ利用者, I want 意匠の適用後も現行の到達性と可読性が保たれること, so that 見た目の改善が利用の障害にならない

#### Acceptance Criteria

1. While 操作可能な要素が焦点を持っているとき, the 各 Web 面 shall 可視の焦点指標を描画する
2. The 各 Web 面 shall 通常の文字とその背面との実効コントラスト比を 4.5:1 以上で描画する
3. The 各 Web 面 shall 部品の境界と状態を示す指標を、隣接する色に対して 3:1 以上で描画する
4. The 各 Web 面 shall 操作領域を寸法区分ごとの下限以上で提供し、隣接する部品の視覚領域を覆わない
5. While 動きの低減が要求されているとき, the 各 Web 面 shall 反復する動きを停止し、進行状態を動きに依存しない手掛かりで提示する
6. When 表示幅が携帯端末相当のとき, the 各 Web 面 shall ページ全体の横方向のスクロールを発生させない
7. The 各 Web 面 shall 状態の区別を色だけに依存させず、字形・記号・文言のいずれかを併せて提示する

### Requirement 5: 性能予算の遵守

**Objective:** As a QR から流入する来店客, I want 意匠の適用後も表示が待たされないこと, so that 回答を始める前に離脱しない

#### Acceptance Criteria

1. The 客向けアンケート shall 配信する実行コードの容量を現行の予算内に保つ
2. The 客向けアンケート shall 携帯端末を想定した計測において、最大要素の描画完了までの時間を現行の失敗閾値内に保つ
3. If 容量または描画完了時間が閾値を超えたとき, then the 継続的インテグレーション shall 失敗する
4. The 各 Web 面 shall 外部依存を新たに増やさずに意匠を適用する

### Requirement 6: 意匠の判断の単一情報源

**Objective:** As a 後から面を足す開発者, I want 意匠の判断が 1 箇所にあり、面の側が判断を新設していないこと, so that 面が増えても意匠が分岐しない

#### Acceptance Criteria

1. The 各 Web 面 shall 意匠の判断を写像版デザイン言語文書から参照し、結論も数値も面の側へ転記しない
2. Where 写像版デザイン言語文書に対応する判断が存在しない意匠が必要になったとき, the 開発者 shall その判断を当該文書へ追加してから面へ適用する
3. When 面への適用によって共通部品の公開面または意匠の値が変わったとき, the 継続的インテグレーション shall 写像版デザイン言語文書との不一致を検出して失敗する
4. The 各 Web 面 shall 参照デザインシステムの色のうち閾値に満たないものを、通常の文字にも文字を載せる面にも用いない

### Requirement 7: 変更が壊していないことの実証

**Objective:** As a この変更をレビューする人, I want 「意匠を変えたが壊していない」の根拠が実行可能な形で残ること, so that 目視の印象ではなく再現できる証拠で判断できる

#### Acceptance Criteria

1. The 開発者 shall 各面への適用について、適用前後で既存の構造検証が緑であることを記録する
2. When 新しい検証を追加したとき, the 開発者 shall 是正前の実装に対して失敗することを、注入位置を変えた 2 通り以上で実証した記録を残す
3. The 開発者 shall 実描画でなければ確認できない事項について、確認した内容と結果を記録する
4. If 追加した検証が対象を 1 件も走査しない状態になったとき, then the 継続的インテグレーション shall 失敗する
