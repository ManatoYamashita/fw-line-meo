# Requirements Document

## Introduction

**line-crosspost（LINE 起点の一括発信）** — 店主が LINE に写真と伝えたいことを送ると、Instagram 用と Google ビジネスプロフィール用の投稿文を AI が下書きし、店主が確認・修正したうえで「Instagram だけ／Google だけ／両方」を選び、明示的に承認したときだけ投稿する。

出典: Issue #494（LINE → Instagram）・#479（Instagram と Google の二重投稿の需要）・#8（GBP 投稿）。前提の調査は `docs/proposals/instagram-integration-prereqs-2026-11/README.md`（第 2 版）と本 spec の `research.md`。

**Instagram の投稿を Google へ転載する機能（前提資料の機能 B）は対象外**である。

本 spec は「外部 API の承認・連携が揃う前に作れる部分」と「揃った後に足す部分」を分けて定める。外部 API の承認・実疎通が済むまで、本機能を本番で有効にしない（Requirement 10）。

## Boundary Context

- **In scope**:
  - LINE からの投稿作成の開始・店舗の選択・写真と文の受け取り・取り消しと再開
  - Instagram 用・Google 用の投稿文の生成・再生成・修正（AI への指示と、店主自身の書き直し）
  - 投稿先の選択・最終確認・明示的な承認
  - 投稿先ごとの状態（成功・失敗・結果不明）の保持と、重複投稿の防止・再試行・確認
  - 結果の LINE 通知と次の操作の案内
  - 投稿先の API を後から接続するための共通の境界（アダプタ）と、Google の発信先アダプタ
  - 連携していない投稿先へは「文をコピーして各アプリで投稿する」導線
- **Out of scope**:
  - Instagram → Google の転載（機能 B）
  - Meta の OAuth 連携・トークンの保管と更新・認可の解除とデータ削除のコールバック（Meta のログイン方式の決定後に別 spec で定める。前提資料 §7.6 PR 3〜5）
  - Instagram の発信先アダプタの API 呼び出しの実装（同上。v1 は「準備中」を返す）
  - 動画・リール・ストーリーズ・カルーセル（複数枚）の投稿
  - 予約投稿・定期的な自動投稿（店主の承認を伴わない投稿は行わない）
  - リッチメニューの画像と区画の差し替え（#354・パイロットと実演の期間中は行わない）
  - GBP の既存の単体の投稿フロー（`g_post`）・クチコミ返信の変更
- **Adjacent expectations**:
  - **gbp-post-review-reply**: Google の連携（OAuth）・トークン・ロケーションの身元は同 spec が所有する。本機能は読むだけで、連携の成立・解除を行わない（未連携のときは同 spec の連携の入口 `g_connect` へ案内する）。
  - **line-onboarding / line-on-demand-report**: 店舗特定済みオーナーの振り分け（`owner/router.ts`）とレポートの応答は変えない。本機能が引き受けなかったイベントは既存の分岐へ落ちる。
  - **four-tier-data-model**: 店舗とオーナーの所有関係を変えない。本機能のすべての操作は、そのオーナーが所有する店舗に閉じる。

## Requirements

### Requirement 1: 投稿作成の開始と店舗の選択

**Objective:** As a オーナー, I want LINE から迷わず投稿作成を始められること, so that 管理画面を開かずに情報発信を始められる

#### Acceptance Criteria

1. When 本機能が有効な店舗のオーナーが投稿作成の開始を選ぶ, the 本システム shall 写真と伝えたいことを送るよう案内し、受け取りを始める
2. When 本機能が有効な店舗を複数持つオーナーが開始を選ぶ, the 本システム shall 対象の店舗を選ばせてから受け取りを始める
3. When 開始の時点で投稿先が 1 つも使えない, the 本システム shall その旨と、使えるようにするための準備（Google 連携・Instagram 連携の状況）を案内し、そのうえで「文をコピーして各アプリで投稿する」使い方で続けられることを示す
4. If オーナーが本機能の有効な店舗を持たない, then the 本システム shall 本機能の案内・ボタンを一切出さず、既存の応答（ステータス案内・レポート）を変えない
5. When 作成中の下書きがあるオーナーが開始を選ぶ, the 本システム shall 作成中の下書きを再開するか、捨てて新しく始めるかを選ばせる（黙って捨てない）

### Requirement 2: 写真と文の受け取り

**Objective:** As a オーナー, I want 写真と文を普段どおり LINE で送るだけで素材を渡せること, so that 操作を覚えなくてよい

#### Acceptance Criteria

1. While 下書きが受け取り中である, when オーナーが写真を送る, the 本システム shall 写真をただちに取得・検証して保存し、受け取ったことを返す
2. While 下書きが受け取り中である, when オーナーが文を送る, the 本システム shall 受け取った順に素材の文へ加え、受け取ったことを返す
3. The 本システム shall 文が複数のメッセージに分かれて届いても 1 つの素材として扱い、オーナーが「下書きを作る」を選ぶまで生成を始めない
4. The 本システム shall 1 件の投稿に使う写真を 1 枚とし、複数枚がまとめて送られたときは 1 枚目（送信時の並びの先頭）を使うことと、ほかの写真を使わないことを伝える
5. When 受け取り中・確認中に新しい写真が届く, the 本システム shall 店主がいまの写真より後に送った写真であるときだけ差し替え、差し替えたことを伝える（文は保持する）。送った順は LINE の送信の時刻で判定し、届いた順・処理が終わった順で判定しない。前に送った写真が後から届いたときは差し替えず、同じ時刻に送られた別の写真・送った時刻が分からない写真は推測で採用せず、使いたい写真を送り直すよう求める
6. If 写真が取得できない・形式や大きさが条件を満たさない, then the 本システム shall その写真を使わず、理由と送り直しの方法を平易に伝え、ほかの素材を失わせない
7. The 本システム shall 写真から位置情報などの付随情報（メタデータ）を取り除いてから保存する
8. When オーナーが「やめる」を選ぶ, the 本システム shall 下書きを取り消し、保存した写真を削除する
9. If 受け取り中・確認中の下書きが一定時間操作されない, then the 本システム shall その下書きを期限切れとして扱い、次の操作で期限切れであることと始め直す方法を伝える
10. While 本機能が無効である, the 本システム shall 写真を受け取らず、写真が送られたときの応答を本機能の導入前と変えない

### Requirement 3: 投稿文の生成

**Objective:** As a オーナー, I want 媒体ごとに合った投稿文が用意されること, so that 文章を考える手間なく発信できる

#### Acceptance Criteria

1. When オーナーが「下書きを作る」を選ぶ, the 本システム shall 素材の文と店名だけを材料に、Instagram 用と Google 用の投稿文をそれぞれ生成して提示する
2. The 本システム shall 素材の文に含まれない事実（価格・数量・日付・時刻・割引・限定・無料・電話番号・URL・メールアドレス・人名・料理名・食材・産地を含む）を投稿文に含めないよう生成を指示し、そのうち機械的に照合できるもの（数字・URL・メールアドレス・電話番号・定めた宣伝の語・ハッシュタグの語）は出力を照合する
3. The 本システム shall 誇張・虚偽・他店の誹謗中傷にあたる表現を生成しない
4. The 本システム shall Instagram 用は親しみやすい語調と少数のハッシュタグ（素材の語から作るものに限る）を、Google 用はハッシュタグ・電話番号を含まない簡潔な案内文を生成する
5. The 本システム shall 生成した投稿文が各媒体の受理条件（字数・ハッシュタグ数）に収まることを確かめ、収まらない・事実の照合に通らない出力を提示しない。**機械的な照合は料理名・食材・産地・人名などの創作を検知できない**ので、事実の保証の最後は店主の確認である（Requirement 3.10）
6. The 本システム shall 写真を生成の材料に使わない
7. If 素材の文が無い, then the 本システム shall 生成を始めず、伝えたいことを文で送るよう案内する
8. If 生成に失敗した, then the 本システム shall 失敗した旨と再試行の手段を伝え、素材を失わせない
9. The 本システム shall 同じ店舗の投稿が毎回同じ定型文にならないよう、文体・書き出しを素材に依存しない候補から選んで生成する
10. The 本システム shall 確認と最終確認で、AI が書いた文であることと、伝えていない内容や事実と違うところ（料理名・食材・産地・価格・日付など）が無いかを確かめるよう店主に示す

### Requirement 4: 確認と修正

**Objective:** As a オーナー, I want 投稿前に写真と文を確かめ、思いどおりに直せること, so that 自分の店の発信として納得できる

#### Acceptance Criteria

1. When 投稿文を提示する, the 本システム shall 投稿先ごとに、全文と、使う写真の有無を確認できる形で示す
2. The 本システム shall 投稿先ごとに「作り直す」「AI に直してもらう」「自分で書き直す」「文をコピー」の手段を提供する
3. When オーナーが AI への修正指示を送る, the 本システム shall 指示を反映した文を再提示する（指示の内容も素材として扱い、指示に無い事実を加えない）
4. When オーナーが「自分で書き直す」を選んで文を送る, the 本システム shall その文を AI で書き換えずにその投稿先の文として採用し、受理条件に収まらないときは理由を伝えて採用しない
5. The 本システム shall 文または写真が変わるたびに下書きの版を進め、古い版のボタンから投稿・修正できないようにする
6. While 下書きが確認中である, when オーナーが手段を選ばずに文を送る, the 本システム shall その文を勝手に投稿文へ反映せず、修正の手段を案内する

### Requirement 5: 投稿先の選択と承認

**Objective:** As a オーナー, I want 投稿先を選び、最後に確かめてから投稿できること, so that 意図しない公開が起きない

#### Acceptance Criteria

1. The 本システム shall 投稿先として「Instagram だけ」「Google だけ」「両方」を、その時点で使える投稿先の組み合わせに限って提示する
2. The 本システム shall 使えない投稿先には理由（未連携・連携の期限切れ・準備中・写真が無い・写真の比率が合わない）と、必要な準備への導線を示す
3. When オーナーが投稿先を選ぶ, the 本システム shall まだ投稿せず、投稿先と投稿する文の全文・写真（Requirement 5.8）をまとめた最終確認を示す（承認する内容と公開される内容を一致させる）
4. The 本システム shall 最終確認での明示的な承認があったときだけ投稿を実行する
5. If 最終確認を示した後に下書きの版が変わった、または投稿先が使えなくなった, then the 本システム shall その最終確認からは投稿せず、最新の内容で確認し直すよう案内する
6. The 本システム shall 承認した時点の文と写真を投稿先ごとに固定し、承認の後の下書きの変更を投稿に反映しない
7. If 同じ承認が二重に届いた（二重タップ・再配信・並行したリクエスト）, then the 本システム shall 各投稿先への投稿を高々 1 回だけ実行する
8. When 写真付きの投稿の最終確認を示す, the 本システム shall 店主が送った写真のメッセージそのものを引用して、公開する写真を目で確かめられるようにする
9. If 写真を引用できない（引用の手掛かりが無い）, then the 本システム shall 最終確認も承認も行わず、写真を送り直すよう案内する（確かめていない写真を公開しない）

### Requirement 6: 投稿の実行と結果の保持

**Objective:** As a オーナー, I want 投稿先ごとの結果が正確に分かること, so that 片方だけ失敗しても次に何をすればよいか分かる

#### Acceptance Criteria

1. When 承認された投稿を実行する, the 本システム shall 投稿先ごとに独立して実行し、ある投稿先の失敗がほかの投稿先の実行を妨げないようにする
2. The 本システム shall 投稿先ごとの結果を「成功」「失敗（投稿されていないことが確か）」「結果不明（投稿されたかどうか確かめられない）」に区別して保持する
3. The 本システム shall 送信の後に応答が失われた・時間切れになった場合と、投稿が作られた可能性を否定できない応答（サーバー側の障害を示す応答など）を、「失敗」ではなく「結果不明」として扱う
4. The 本システム shall 成功した投稿先へ再び投稿しない
5. If 投稿先の結果が「結果不明」である, then the 本システム shall 自動で再投稿せず、確認の手段（投稿先の API による照合、または店主による確認）を案内する
6. When 店主が結果不明の投稿先について「投稿されていなかった」と確認する, the 本システム shall その投稿先を再試行できる状態へ戻す
7. If 投稿が失敗した, then the 本システム shall 平易な理由と、再試行してよい場合に限り再試行の手段を示す（連携の期限切れなどは再連携の導線を示す）
8. The 本システム shall 同じ投稿先への再試行の回数に上限を設ける
9. If 実行中のまま一定時間を過ぎた投稿先がある（処理の中断）, then the 本システム shall その投稿先を「結果不明」として扱う
10. The 本システム shall 投稿先の呼び出しに時間制限を設け、外部の応答が止まっても LINE の処理を塞がない
11. If 承認を記録した後、投稿先へ送る前に処理が止まった, then the 本システム shall その投稿先（一度も送っていないことが確かなもの）を、店主の操作（同じ承認の押し直し・投稿の状況からの再開）で送れるようにし、取りやめも選べるようにする。送った可能性がある投稿先は送り直さない
12. If 承認から一定時間（24 時間）を過ぎても一度も送っていない投稿先がある, then the 本システム shall 店主の知らないうちに古い内容を公開しないよう、送らずに取りやめとして扱う。期限の判定は、取りやめの確認と実行権の獲得の両方で行い、その間に期限を越えても公開しない

### Requirement 7: 結果の通知と案内

**Objective:** As a オーナー, I want 投稿の結果を LINE で受け取り、次の操作が分かること, so that 不安なく使い続けられる

#### Acceptance Criteria

1. When 投稿の実行が終わる, the 本システム shall 投稿先ごとの結果と、結果ごとの次の操作（成功: 投稿を見る導線があれば示す／失敗: 再試行・再連携／結果不明: 確認）を LINE で知らせる
2. If 返信で知らせられなかった, then the 本システム shall プッシュで知らせ、結果を届けられたかどうかを記録する。どちらでも届けられなかった結果は失わず、店主の次の操作（どの操作でも）と投稿の状況の確認で必ず示す。下書きの作成中・確認中の操作では、その操作の入力を受け取り、応答の前に結果を添える（下書きの操作を妨げない）
3. When オーナーが投稿の状況の確認を選ぶ（「投稿の状況」「投稿の結果」と送る場合を含む）, the 本システム shall 直近の投稿の投稿先ごとの状態を示す。下書きの作成中・確認中（自分で書き直す途中を含む）でもこの文は命令として扱い、素材・書き直しの文にせず、下書きを変えない
4. The 本システム shall 通知の文面に、トークン・内部の ID・外部 API のエラー本文を含めない

### Requirement 8: 安全性・権限・データの扱い

**Objective:** As a 運営, I want 店舗のデータと権限が守られること, so that 店舗と運営の信用を損なわない

#### Acceptance Criteria

1. The 本システム shall すべての操作で、下書き・写真・投稿先の行がそのオーナーの所有する店舗のものであることを確かめ、postback に含まれる ID を信用しない
2. The 本システム shall 写真を推測できない名前で非公開の置き場に保存し、投稿先が取得する間だけ取得できるようにする
3. The 本システム shall 投稿が終わった（全投稿先が成功・失敗の確定・取り消し）写真を削除し、どの場合も保存の期間に上限を設ける
4. The 本システム shall 下書きの素材・投稿文を、保存の期間を過ぎたら削除する
5. The 本システム shall ログ・エラー通知に、投稿文・素材・写真・トークン・LINE ユーザー ID を載せない
6. The 本システム shall LINE の Webhook の再配信・重複イベントで、素材の重複・写真の重複保存・投稿の重複を起こさない
7. The 本システム shall 写真に来店客などが写り込む可能性について、最終確認で注意を促す
8. The 本システム shall 保存期間（下書き・投稿文は作成から 30 日、写真は受け取りから 7 日、作成中の下書きは最後の操作から 24 時間）を、利用者の次の操作に依存せず定期的な処理で守る。写真の実体は置き場の寿命の規則でも上限を保証する

### Requirement 9: 投稿先の接続の境界

**Objective:** As a 開発者, I want 投稿先の API を後から安全に接続できること, so that 認証と承認が揃った後に、媒体ごとの接続と検証だけで導入へ進める

#### Acceptance Criteria

1. The 本システム shall 投稿の共通処理（承認・実行権の獲得・状態遷移・通知）と、投稿先ごとの API 処理を分け、投稿先ごとの処理を差し替え可能な部品として扱う
2. The 本システム shall 投稿先ごとの部品が、使えるかどうか（連携・設定・内容の適合）の判定と、結果の 4 分類（成功・失敗・結果不明・途中の到達点）を返す契約を持つ
3. The 本システム shall 途中の到達点（例: 公開前のコンテナ）を外部 API の次の呼び出しより前に保存し、再試行と確認でそれを使う
4. The 本システム shall API が未接続・未設定の投稿先を「準備中」として扱い、投稿を試みない
5. The 本システム shall 投稿先ごとの部品を外部 API の偽物に差し替えて、時間切れ・部分成功・応答の喪失を自動テストできる構造にする

### Requirement 10: 既定 OFF と段階的な有効化

**Objective:** As a 運営, I want 未完成の機能が店舗に見えないこと, so that 既存の利用者に影響を与えずに開発と検証を進められる

#### Acceptance Criteria

1. The 本システム shall 本機能を既定で無効とし、有効にする店舗を明示的に指定したときだけ、その店舗のオーナーに本機能を見せる
2. The 本システム shall 投稿先ごとの有効化を本機能の有効化と分け、投稿先の API の承認・実疎通の確認が済むまで、その投稿先へ投稿しない
3. While 本機能が無効である, the 本システム shall LINE の応答・GBP の会話・レポートの挙動を本機能の導入前と変えない
4. If 本機能の設定が一部だけ与えられた, then the 本システム shall 起動時に失敗し、どの設定が足りないかを示す
