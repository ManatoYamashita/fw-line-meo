# Requirements Document

## Project Description (Input)

出典: Issue #252（店舗の利用停止 — 運営・代理店の操作）

### 誰が困っているか
- **運営・代理店**: パイロット（計画上 2026-10-19 開始・3〜6 店）で離脱した店舗や、本番の実機 E2E で作ったテスト用の店舗・オーナーを止められない。
- **運営（コスト）**: LINE 公式アカウントの無料プランは月 200 通で追加購入できず（毎朝 1 通なら約 6 店舗分）、止められない店舗の配信が通数枠を食う。Places API の従量課金（自店＋競合 5 店）も続く。

### 現状
- 本番で店舗を止める経路がアプリのどこにも無い。dashboard-api が無効化できるのは招待コードとダッシュボード利用者だけ。line-webhook は `unfollow` を黙って無視する。日次バッチ（Go）と配信ジョブ（TS）は `place_status = 'confirmed'` の全店舗を対象にし、停止という概念が無い。
- `place_status` を `pending` へ戻すと店舗の身元（`place_id`）を捨てることになり、停止の代わりにならない（`ck_place_confirmed`）。
- 止めるには本番 DB の直接書換しか無く、それは書込境界（`stores` は TS 所有・`db/write-boundary.md`）の外からの書込になる。
- LINE はブロック中のユーザーへの push も `200` で受理するため、delivery-job はブロック中のオーナーへの配信を毎日 `delivered` と記録し続ける。

### 何を変えるか
- 運営・代理店が管理画面から店舗の利用を停止できるようにし、停止した店舗は翌朝の daily-batch（Go）と summary-delivery（TS）の両方の対象から外れる。停止・再開は監査記録（`audit_logs`）に残す。物理削除にはしない。
- **これは要件の変更である。** `competitive-daily-summary` の Out of scope（配信停止）と Requirement 3.10（オプトアウト手段を MVP では提供しない）を先に改訂し、`db/test/check_no_optional_capabilities.sh` の不在検査を新しい要件に合わせて書き換えてから実装する。現行の検査は `stores` の列と dashboard-api / dashboard-web を見ていないため、名前や置き場所で検査をすり抜けてはならない。

### 確定した論点（2026-09-23）
| 論点 | 決定 | 根拠 |
|---|---|---|
| 停止の単位 | 店舗単位 | 取得も配信も店舗単位。オーナー単位はその全店舗を止めれば足りる |
| 操作できる人 | 運営＋担当代理店 | 既存 RBAC（agency-dashboard Req 2）と招待コード無効化に揃える |
| 再開 | できる | 誤操作・一時休業から戻せるようにする |
| unfollow（ブロック） | 無視のまま（本 spec では扱わない） | 下記「unfollow を扱わない根拠」 |
| 客向けアンケート（QR） | 停止中は受け付けない | 離脱店舗で生成費用を発生させない。既存の匿名集計は消さない |
| QR の発行 | 停止中は発行しない | 止めた店舗の QR が新たに店頭へ出ないようにする。未確定店舗へ発行しない既存の扱いと揃える（gap 分析 §4-1） |
| 詳細画面（LIFF）・リッチメニューのレポート | 停止中の店舗は出さない | 「全面停止」を採用 |
| 監査記録 | 停止・再開を残す | 失敗時の扱いは #250 の決定に従う |

### unfollow を扱わない根拠
- LINE の一次情報は、ブロック中のユーザーへの送信は通数に数えないと明記している。
  - [Messaging API pricing](https://developers.line.biz/en/docs/messaging-api/pricing/)（"How to count the number of messages sent"）: "If you send a message to a user who blocked your LINE Official Account or a user ID that doesn't exist, the message isn't counted."
  - [How message counts are calculated in the Messaging API](https://developers.line.biz/en/tips/2026/05/28/how-to-count-messages/)（2026-05-28）: 同旨。
- したがってブロック中のオーナーへの配信は月 200 通の枠を消費せず、#252 の「通数枠を食う」動機は unfollow には当てはまらない。残る問題は `delivered` と記録される不正確さだけで、別 Issue で扱う。
- unfollow で自動停止するとオーナー自身の意思で配信を止める手段（＝オプトアウト）になり、Req 3.10 の趣旨そのものを覆す。本 spec はその改訂を行わない。

## Introduction

運営と代理店が、管理ダッシュボードから店舗の利用を停止・再開できるようにする。停止中の店舗は、毎朝の競合データ取得（Places API の従量課金）と LINE への日次の変化通知の対象から外れ、客向けアンケート・店舗詳細画面・リッチメニューのレポートからも利用できなくなる。停止は論理的な状態の切替であり、店舗の身元（Place の確定）と、これまでに蓄積した匿名集計・日次データは保持する。

本機能は `competitive-daily-summary` の Requirement 3.10（配信停止手段を MVP では提供しない）に関わる要件変更である。「オーナー自身による配信停止（オプトアウト）」は引き続き提供せず、「運営・代理店による店舗の利用停止」を別の能力として定義する。

## Boundary Context

- **In scope**:
  - 運営・担当代理店による店舗単位の停止と再開
  - 停止中の店舗を、日次の競合データ取得・日次の変化通知・客向けアンケート・店舗詳細画面・リッチメニューのレポートから外すこと
  - 停止中の店舗への QR の発行を止めること
  - 停止状態の表示（店舗一覧）と、停止・再開の監査記録
  - `competitive-daily-summary` の Out of scope と Requirement 3.10 の改訂、および不在検査の書き換え
- **Out of scope**:
  - オーナー自身による配信停止（オプトアウト）。LINE 上にもダッシュボード上にも設けない
  - オーナーのブロック（unfollow）を契機とした自動停止・自動再開。ブロック中の配信が `delivered` と記録される問題も本 spec では扱わない（別 Issue）
  - オーナー単位・代理店単位の一括停止
  - 店舗・オーナー・代理店の物理削除
  - 停止中の欠損日の日次データの遡及取得
  - 既に店頭に置かれた QR コードそのものの回収・無効化（停止中は読まれても回答を受け付けないことで足りる）
- **Adjacent expectations**:
  - 権限の範囲は `agency-dashboard` の Requirement 2（代理店は担当店のみ・範囲外の要求はUIに関係なく拒否）に従う
  - 再開直後の前日比の扱いは `competitive-daily-summary` の既存の規則（前日のデータが無い日は前日比を通知・表示しない）に従う
  - 監査記録の書込に失敗したときの扱いは #250 の決定に従う

## Requirements

### Requirement 1: 店舗の停止と再開の操作
**Objective:** As a 運営・代理店の利用者, I want 担当する店舗を管理ダッシュボードから停止・再開したい, so that 離脱した店舗やテスト用の店舗への取得と配信を、本番データベースを直接書き換えずに止められる

#### Acceptance Criteria
1. When 運営の利用者が任意の店舗の停止を実行したとき, the 管理ダッシュボード shall その店舗を停止中の状態にする
2. When 代理店の利用者が自代理店の担当店舗の停止を実行したとき, the 管理ダッシュボード shall その店舗を停止中の状態にする
3. When 停止中の店舗に対して運営または担当代理店の利用者が再開を実行したとき, the 管理ダッシュボード shall その店舗を利用中の状態へ戻す
4. If 代理店の利用者が他の代理店の店舗、または存在しない店舗の停止・再開を要求したとき, then the 管理ダッシュボード shall 状態を変えずに要求を拒否し、その店舗が存在するかどうかを応答から判別できないようにする
5. If 既に停止中の店舗に停止を、または利用中の店舗に再開を要求したとき, then the 管理ダッシュボード shall 状態を変えずに成功として扱う
6. When 利用者が停止を実行しようとしたとき, the 管理ダッシュボード shall 停止によって日次の取得・変化通知・アンケート・QR の発行・詳細画面が止まることを示して確認を求め、確認された場合にのみ停止する
7. The 管理ダッシュボード shall 停止・再開によって店舗の身元（Place の確定状態）、オーナー・代理店との関係、蓄積済みの匿名集計・日次データを変更・削除しない
8. If 停止・再開の処理が失敗したとき, then the 管理ダッシュボード shall 失敗したことを利用者に示し、成功したかのような表示をしない

### Requirement 2: 停止状態の表示
**Objective:** As a 運営・代理店の利用者, I want 店舗一覧でどの店舗が停止中かを見分けたい, so that 止めた店舗と動いている店舗を取り違えずに管理できる

#### Acceptance Criteria
1. The 管理ダッシュボード shall 店舗一覧の各店舗について、利用中か停止中かを表示する
2. While 店舗が停止中である, the 管理ダッシュボード shall その店舗を店舗一覧から除かずに表示し、再開の操作を提供する
3. While 店舗が利用中である, the 管理ダッシュボード shall その店舗に停止の操作を提供する
4. When 停止または再開が成功したとき, the 管理ダッシュボード shall 画面を再読み込みせずに店舗一覧の表示を新しい状態へ更新する

### Requirement 3: 日次の競合データ取得からの除外
**Objective:** As a 運営, I want 停止中の店舗への競合データ取得を止めたい, so that 離脱した店舗のために外部 API の従量課金が発生し続けない

#### Acceptance Criteria
1. When 日次の競合データ取得が開始したとき, the 日次取得処理 shall その時点で停止中の店舗について、自店と競合店のデータを取得しない
2. When 日次の競合データ取得が開始したとき, the 日次取得処理 shall その時点で停止中の店舗について、競合店の抽出・固定を行わない
3. While 店舗が停止中である, the 日次取得処理 shall その店舗の日次サマリーを作成しない
4. The 日次取得処理 shall 実行結果の要約に含める対象店舗数から停止中の店舗を除く
5. When 再開された店舗について次の日次取得が開始したとき, the 日次取得処理 shall その店舗を再び取得の対象に含める
6. When 再開後の最初の日次サマリーを作成するとき, the 日次取得処理 shall 停止中に欠けた日を遡って取得せず、停止中に増えたクチコミを新着として数えない

### Requirement 4: 日次の変化通知からの除外
**Objective:** As a 運営, I want 停止中の店舗への LINE 配信を止めたい, so that パイロットの限られた月間通数枠を、利用中の店舗のために使える

#### Acceptance Criteria
1. While 店舗が停止中である, the 日次配信処理 shall その店舗について、オーナーへ日次の変化通知を送信しない
2. If 日次サマリーの作成後から配信時刻までの間に店舗が停止されたとき, then the 日次配信処理 shall その日の変化通知を送信しない
3. While 店舗が停止中である, the 日次配信処理 shall その店舗について、送信したことも、いかなる理由で送信を見送ったことも通知記録として残さない
4. When 再開された店舗について日次サマリーが作成されたとき, the 日次配信処理 shall 通常の規則に従って変化通知の判定対象に含める
5. The 日次取得処理 and 日次配信処理 shall 同じ停止状態を参照して対象を決め、片方だけが停止中の店舗を扱う状態を生じさせない

### Requirement 5: 客向けアンケートと QR の停止
**Objective:** As a 運営, I want 停止中の店舗のアンケートと QR の発行を止めたい, so that 離脱した店舗の店頭に残った QR から回答と下書き生成が続かず、止めた店舗の QR が新たに店頭へ出ない

#### Acceptance Criteria
1. When 来店客が停止中の店舗のアンケートを開いたとき, the 客向けアンケート shall 店舗を特定できない場合と同じ「現在利用できない」旨の表示を行い、回答の入力を提供しない
2. If 停止中の店舗への回答が送信されたとき, then the 客向けアンケート shall 回答を受け付けず、集計にも下書き生成にも用いない
3. The 客向けアンケート shall 停止中であることを理由に、その店舗の既存の匿名集計を削除しない
4. When 再開された店舗のアンケートを来店客が開いたとき, the 客向けアンケート shall 通常どおり回答を受け付ける
5. If 停止中の店舗の QR の発行を要求されたとき, then the 管理ダッシュボード shall QR を発行せず、停止中のため発行できないことを利用者に示す
6. While 店舗が停止中である, the 管理ダッシュボード shall 店舗一覧でその店舗の QR 発行の操作を提供しない
7. When 再開された店舗の QR の発行を要求されたとき, the 管理ダッシュボード shall 通常どおり QR を発行する

### Requirement 6: オーナー向け LINE の面の停止
**Objective:** As a 運営, I want 停止中の店舗をオーナー向けの面に出さないようにしたい, so that 利用を止めた店舗の情報がオーナーに提示され続けない

#### Acceptance Criteria
1. While 店舗が停止中である, the 店舗詳細画面 shall その店舗をオーナーの閲覧対象に含めない
2. While 店舗が停止中である, the LINE 応答 shall リッチメニューからのレポート要求において、その店舗を選択肢と応答の対象に含めない
3. If オーナーの店舗がすべて停止中のとき, then the 店舗詳細画面 and LINE 応答 shall 閲覧できる店舗が無い場合と同じ応答を返す
4. When オーナーが公式アカウントをブロックまたはブロック解除したとき, the LINE 応答 shall 店舗の停止状態を変更しない

### Requirement 7: 停止・再開の監査記録
**Objective:** As a 運営, I want 誰がいつどの店舗を停止・再開したかを残したい, so that 停止の経緯を後から確かめ、誤操作を追跡できる

#### Acceptance Criteria
1. When 店舗が停止中の状態になったとき, the 管理ダッシュボード shall 操作した利用者、その役割、対象店舗、日時を停止として監査記録に残す
2. When 店舗が利用中の状態へ戻ったとき, the 管理ダッシュボード shall 操作した利用者、その役割、対象店舗、日時を再開として監査記録に残す
3. If 停止・再開の要求によって状態が変わらなかったとき, then the 管理ダッシュボード shall 監査記録を追加しない
4. The 管理ダッシュボード shall 停止・再開の監査記録を、既存の監査記録の種別を失わない形で追加する

### Requirement 8: オーナー自身の配信停止の不在と要件改訂
**Objective:** As a 運営, I want 運営・代理店による停止を入れても、オーナー自身が配信を止める手段が無いことを保ちたい, so that 既存の要件の趣旨を名前や置き場所の違いで崩さずに要件を変更できる

#### Acceptance Criteria
1. The fw-line-meo shall オーナー自身が配信や店舗の利用を停止する手段を、LINE 上にも Web 上にも提供しない
2. The `competitive-daily-summary` 仕様 shall Out of scope と Requirement 3.10 を、「オーナー自身による配信停止」を引き続き提供しないことと、「運営・代理店による店舗の利用停止」を本仕様が提供することを区別して記述する
3. The 不在検査 shall オーナー自身による配信停止の手段が加わったことを、その手段がどの画面・どの層・どの名前で加えられても検出する
4. The 不在検査 shall 運営・代理店による店舗の利用停止を、オーナー自身による配信停止と区別して許容する
5. When 不在検査を書き換えるとき, the 開発者 shall 書き換え前の検査が運営・代理店による停止の実装を検出できなかったことを確かめて記録する

### Requirement 9: 本番での効果の確認
**Objective:** As a 運営, I want 本番で停止が実際に取得と配信を止めたことを確かめたい, so that テストが通るだけで効果が出ていない状態を完了と見なさない

#### Acceptance Criteria
1. When 本番で 1 店舗を停止した翌朝の日次取得が完了したとき, the 運営 shall 実行結果の要約の対象店舗数から当該店舗が外れたことを確認して記録する
2. When 本番で 1 店舗を停止した翌朝の日次配信が完了したとき, the 運営 shall 当該店舗について変化通知の送信と通知記録のいずれも無いことを確認して記録する
3. When 停止状態を保持するための変更を本番へ適用したとき, the 運営 shall 適用が完了していることを本番のデータベースで確認してから停止の操作を行う
