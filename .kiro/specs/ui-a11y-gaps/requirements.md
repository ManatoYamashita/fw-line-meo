# Requirements Document

## Project Description (Input)

出典: GitHub Issue [#52](https://github.com/ManatoYamashita/fw-line-meo/issues/52)（親 #41 の子）`feat(ui): a11y 実装の欠落 — prefers-reduced-motion 未対応 / Alert の role 固定 / タッチターゲット`

### 誰が問題を抱えているか

- **前庭障害・光過敏のある利用者**: 無限に回り続けるアニメーションは、めまい・吐き気・発作の誘因になりうる。OS の動き低減設定を有効にしていても本プロダクトはそれを一切尊重しない。
- **スクリーンリーダー利用者**: すべての通知が読み上げを即座に中断する強度で提示されるため、単なる案内文でも作業が毎回遮られる。
- **スマートフォンで指操作する来店客・飲食店オーナー**: 本プロダクトの主動線は QR → モバイル → LIFF であり（`.kiro/steering/product.md`）、利用者は IT に不慣れであることが前提。にもかかわらずボタンの操作領域が 32px と小さい。

### 現状（Issue #52 起票時 + 2026-07-30 の再調査）

- **`prefers-reduced-motion` への配慮がゼロ**。`grep -rn "prefers-reduced-motion\|motion-safe\|motion-reduce" ts/` が 0 件。
- **動きを持つのは `@fwlm/ui` だけ**である（2026-07-30 再調査）。`ts/apps/*/src` に `animate-*` / `transition-*` / `@keyframes` は 0 件で、アプリ側は自前の動きを一切持たない。`@fwlm/ui` 全 13 部品の動きは次の 5 種に尽きる。
  - `spinner.tsx:16` — `animate-spin`（**無限回転**）
  - `button.tsx:23` / `badge.tsx` — `transition-all`
  - `input.tsx` / `textarea.tsx` / `checkbox.tsx` — `transition-colors`
  - `checkbox.tsx` — `transition-none`
  - `button.tsx:23` — `active:not-aria-[haspopup]:translate-y-px`（押下時の沈み込み）
- **`alert.tsx:46` は variant 不問で `role="alert"`** を付与する。これは assertive なライブリージョンであり、`default`（静的な情報表示を想定）でも読み上げを割り込ませる。`role="status"`（polite）との出し分けが無い。
- **タッチターゲットが 32px**。`button.tsx` の `default` は `h-8`、`icon` は `size-8`。WCAG 2.2 SC 2.5.8（24px）は充足するが、AAA（SC 2.5.5）および一般的な推奨値 44px には届かない。一方 `checkbox.tsx` / `radio-group.tsx` は `after:absolute after:-inset-x-3 after:-inset-y-2` により**見た目 16px のまま操作領域だけを拡大済み**で、Button にだけ同等の配慮が無い。
- `theme.css` は既に `@layer base` を持ち（`theme.css:123`）、見出し復元・グローバル `:focus-visible` 既定など「アプリ DOM を触らずに全面を直す」手段として機能している。

本Issueは、同時起票の #49（フォーカス可視性の喪失）/ #50（アルファ合成色の AA 未達）が**実害バグ**であったのに対し、**実装の欠落**（回帰ではない）として MIDDLE で扱われている。

### 確定した判断（2026-07-30・利用者合意）

Issue #52 が「決め打ちせずトレードオフを併記」として保留していた 2 点を、本 spec の開始時に確定した。

1. **タッチターゲット**: **見た目の寸法は変えず、操作領域だけを拡大する**（Checkbox / RadioGroup が既に採っている作法を Button にも適用する）。ボタンの視覚的な高さを 44px へ変更する案は、各面デザイン（#43 / #44）と衝突し手戻りを生むため採らない。これにより本項目は #43 / #44 を待たずに本 spec で完結できる。
   - **要求寸法の適用範囲**: 44 CSS ピクセルを要求するのは**客向け主動線で用いる既定寸法**（`button.tsx` の `default` / `lg` / `icon` / `icon-lg` に相当）に限る。**高密度配置向けの縮小寸法**（同 `xs` / `sm` / `icon-xs` / `icon-sm`）は WCAG 2.2 SC 2.5.8 の 24 CSS ピクセルを下限とする。理由は、縮小寸法が管理画面（dashboard-web）の密集レイアウトおよびボタングループ（`in-data-[slot=button-group]`）向けであり、24px の部品に 44px の操作領域を与えると領域の重なりが不可避で「意図した部品のみが反応する」ことと両立しないため。客向け主動線（survey-web / store-detail）では縮小寸法を用いない。

### 実装着手時の訂正（2026-08-01・実測にもとづく利用者合意）

上記の「Checkbox / RadioGroup と同じ作法を Button へ」という前提は、**選択部品については実行不能である**ことが実測で判明した。

- `RadioGroup` は部品自身が項目間隔 8 CSS ピクセル（`grid gap-2`）を規定し、項目の視覚寸法は 16 CSS ピクセルである。したがって項目のピッチは **24 CSS ピクセル**に固定される。
- ピッチ 24 の並びに 44 の操作領域を与えると、**隣の項目の視覚領域そのものを覆う**。これは「利用者が意図した部品のみが反応する」（要件 4.5）と両立しない。間隔を広げれば解決するが、それは操作領域の拡大による余白の変更（要件 4.4）にあたり、各面デザイン（#43 / #44）とも衝突する。
- 現状の拡張量（上下各 8 CSS ピクセル）は、隣の項目の視覚領域と**境界で接するがこれを覆わない**上限値であることを実測で確認した。

**したがって選択部品（チェックボックス・ラジオ）の 44 CSS ピクセルは、テキスト入力（要件 4.7）と同型の扱いとし、ラベルを伴う構成の行全体で満たす。** 部品単体の操作領域は SC 2.5.8 の 24 CSS ピクセルを下限として現状を維持する。実世界のフォームで選択肢のラベル行全体が押せることは一般的な作法であり、視覚表現を一切変えずに指操作の確実性を得られる。

なお、ラベルを伴う構成の行全体は現状 **42 CSS ピクセル**であり要求に 2 ピクセル不足している。これは本仕様が是正する対象である（Checkbox / RadioGroupItem 単体ではなく、ラベル構成が是正対象になる）。
2. **通知の読み上げ強度**: **エラー（destructive）のみ assertive**、既定（default）と成功（success）は polite とする。成功通知は「今すぐ作業を中断してでも伝えるべき情報」ではないため。

### 制約・前提

- **既存の a11y を後退させない**。特に #49 で `theme.css` の `@layer base` へ一本化したフォーカス表示、および `spinner.tsx` の `role="status"` + 上書き可能な `aria-label` は維持する。
- **カスケードレイヤの罠**: `@layer base` に置いた規則は `@layer utilities` の部品側ユーティリティに**詳細度に関係なく負ける**（#49 の原因）。動きの抑制をどの層に置くかは design フェーズの判断事項だが、要件としては「動き低減設定下で実際に抑制されること」を実描画で満たすことを求める。
- **性能予算**: survey-web は `perf:budget`（client JS 300KB）と Lighthouse mobile（LCP 3 秒・要件 2.8）の制約下にある。
- **対象外**: 自動 a11y 監査基盤（axe / jsx-a11y / 視覚回帰）の導入は #53 が扱う。

## Introduction

本仕様は、`@fwlm/ui` が全 UI 面へ提供する共通コンポーネントに欠けている 3 つのアクセシビリティ配慮 —— **動きへの配慮**、**通知の読み上げ強度の出し分け**、**タッチ操作の確実性** —— を確立する。いずれも部品を各面へ本格展開する（#42〜#45）前に決めておくべき土台であり、後から入れると全面の再調整を招く。

本仕様が扱うのは利用者に観測できる振る舞いのみであり、抑制をどの層に置くか・どの API 形で出し分けるかといった実現手段は design フェーズで決定する。

## Boundary Context

- **In scope**: `@fwlm/ui` の共通コンポーネントおよび `theme.css` が全 UI 面へ提供する、(1) 動きの表現、(2) 通知の支援技術への提示強度、(3) 操作可能部品の操作領域。ならびにこれら 3 点が失われたときに失敗する自動検証。
- **Out of scope**:
  - 自動 a11y 監査基盤（axe / jsx-a11y / 視覚回帰）の導入 — #53 が扱う
  - 各面の画面デザインそのもの — #42（LINE）/ #43（LIFF）/ #44（survey-web）/ #45（dashboard-web）が扱う
  - フォーム部品の枠線・選択状態の非テキストコントラスト — #57 が扱う
  - **ボタンの視覚的な寸法の変更**（上記「確定した判断」により明示的に除外する）
  - 角丸スケールの整合 — #54 が扱う
- **Adjacent expectations**:
  - 各面（survey-web / store-detail / dashboard-web）は `@fwlm/ui` を経由して部品を使う限り、本仕様の配慮を追加実装なしで受け取れることを期待する。
  - 各面が独自に動きを追加した場合も、動き低減設定下では抑制対象に含まれることを期待する。本仕様は各面の画面実装そのものには責任を持たない。
  - **各面はテキスト入力部品および選択部品（チェックボックス・ラジオ）をラベルを伴う構成（Field 構成）で組むことを期待する。** テキスト入力は指で押した位置に文字カーソルを置く性質を持つため、他の操作可能部品と同じ手段で操作領域を広げられない。選択部品は部品自身が規定する項目間隔（ピッチ 24 CSS ピクセル）により、44 CSS ピクセルの操作領域を隣接項目の視覚領域を覆わずに与えることが物理的にできない（「実装着手時の訂正」参照）。いずれも要求寸法はラベルを含む行全体で満たす前提とし、**ラベルを伴わない裸の入力・裸の選択部品**を各面が直接配置した場合の 44 CSS ピクセル充足について本仕様は責任を持たない（その場合も要件 4.2 の 24 CSS ピクセル下限は本仕様が保証する）。
  - LINE Flex Message は React ではなく本仕様の対象外である。

## Requirements

### Requirement 1: 動きへの配慮（動き低減設定の尊重）

**Objective:** As a 前庭障害・光過敏のある利用者, I want OS で設定した動き低減の意思が製品に尊重されること, so that めまい・不快感を誘発されずに安心してサービスを利用できる

#### Acceptance Criteria

1. While 利用者の環境で動き低減設定が有効であるとき, the 共通コンポーネント shall 無限に繰り返すアニメーションの再生を停止する
2. While 利用者の環境で動き低減設定が有効であるとき, the 共通コンポーネント shall 状態変化（hover / focus / 選択 / 押下）に伴う視覚的な遷移を、利用者が動きとして知覚しない程度まで抑制する
3. While 利用者の環境で動き低減設定が有効でないとき, the 共通コンポーネント shall 現在の動きの表現を変更せずに維持する
4. The 共通コンポーネント shall 動き低減設定の有無にかかわらず、状態変化の結果として到達する見た目（色・位置・可視性）を同一に保つ

### Requirement 2: 動きに依存しない処理中の伝達

**Objective:** As a 動き低減設定を有効にしている利用者, I want 処理が進行中であることを動き以外の手段でも把握できること, so that 画面が固まったのか処理中なのかを判断できる

#### Acceptance Criteria

1. While 動き低減設定が有効であり、かつ処理が進行中であるとき, the 共通コンポーネント shall 動きに依存しない視覚的手段で処理中であることを提示する
2. The 共通コンポーネント shall 動き低減設定の有無にかかわらず、処理中であることを支援技術へ通知する
3. The 共通コンポーネント shall 処理中の通知に用いる読み上げ文言を、呼び出し側が用途に応じて置き換えられる状態を維持する

### Requirement 3: 通知の読み上げ強度の出し分け

**Objective:** As a スクリーンリーダー利用者, I want 通知の重要度に応じて読み上げの割り込み方が変わること, so that 案内文で作業を毎回中断されず、かつエラーは確実に気づける

#### Acceptance Criteria

1. When エラーを表す通知が表示されたとき, the 共通コンポーネント shall 支援技術に進行中の読み上げを中断させ、当該通知を直ちに読み上げさせる
2. When 成功を表す通知または既定の情報通知が表示されたとき, the 共通コンポーネント shall 進行中の読み上げを中断させず、区切りのよい時点で当該通知を読み上げさせる
3. The 共通コンポーネント shall 通知の変種ごとの視覚表現（配色・アイコン・レイアウト）を、読み上げ強度の出し分けによって変化させない
4. The 共通コンポーネント shall 通知が支援技術に対して常に何らかのライブリージョンとして提示される状態を維持し、読み上げ対象から外れる変種を作らない

### Requirement 4: タッチ操作の確実性

**Objective:** As a スマートフォンで指操作する来店客および飲食店オーナー, I want 小さく見えるボタンでも確実に押せること, so that 押し損ねによる離脱や誤操作なくアンケート回答・店舗閲覧を完了できる

#### Acceptance Criteria

1. The 共通コンポーネント shall 客向け主動線で用いる既定寸法の押しボタンについて、縦横いずれも 44 CSS ピクセル以上の操作領域を提供する
2. Where 操作可能部品が高密度配置向けの縮小寸法で提示されるとき, the 共通コンポーネント shall 縦横いずれも 24 CSS ピクセル以上の操作領域を提供する
3. The 共通コンポーネント shall 操作領域の拡大によって部品の視覚的な寸法を変更しない
4. The 共通コンポーネント shall 操作領域の拡大によって周囲の要素の位置および余白を変化させない
5. If 操作可能部品が隣接して配置されるとき, the 共通コンポーネント shall いずれの部品の拡大した操作領域も隣接部品の視覚領域を覆わない状態を保ち、利用者が見えている部品を指した場合に必ずその部品が反応する状態を保つ
6. Where 部品が既に要求寸法以上の操作領域を持つとき, the 共通コンポーネント shall 現在の操作領域を維持する
7. Where テキスト入力部品または選択部品（チェックボックス・ラジオ）がラベルを伴う構成で用いられるとき, the 共通コンポーネント shall ラベルを含む行全体で 44 CSS ピクセル以上の操作領域を満たし、当該領域の指定によって対応する部品が反応する状態を保つ
8. The 共通コンポーネント shall 選択部品（チェックボックス・ラジオ）の単体の操作領域について、要件 4.2 の下限を満たしたうえで現在の値を維持する

### Requirement 5: 欠落の再発を止める自動検証

**Objective:** As a 開発者および運営, I want 本仕様の配慮が失われたときに CI が失敗すること, so that 同種の欠落が「CI 全緑のまま」再び本番へ出ることを防げる

#### Acceptance Criteria

1. The 継続的検証 shall 動き低減設定下で無限アニメーションおよび状態遷移が抑制されることを検証し、抑制が存在しない実装に対しては失敗する
2. The 継続的検証 shall 通知の変種ごとの読み上げ強度の出し分けを検証し、出し分けが失われた場合に失敗する
3. The 継続的検証 shall 操作可能部品の操作領域が寸法区分ごとの要求値を下回った場合に失敗する
4. If 操作可能部品の寸法区分が追加され、いずれの要求値に属するかが宣言されていないとき, the 継続的検証 shall その未分類を検出して失敗する
5. If 動きを伴う新しい表現が共通コンポーネントへ追加され、動き低減設定下の抑制対象に含まれていないとき, the 継続的検証 shall その混入を検出して失敗する
6. The 継続的検証 shall 各検証項目について、是正前の実装に対して失敗することが実証された状態で導入される

### Requirement 6: 既存の品質の非後退

**Objective:** As a 全 UI 面の利用者, I want 本仕様の変更が既に整った品質を損なわないこと, so that ある配慮の追加が別の配慮の劣化と引き換えにならない

#### Acceptance Criteria

1. The 共通コンポーネント shall キーボード操作時の可視フォーカス表示を、現在の表示内容および視認性のまま維持する
2. The 共通コンポーネント shall 現在提供している役割・状態の支援技術への通知を後退させない
3. The 共通コンポーネント shall 現在満たしているコントラスト要件を後退させない
4. The UI デザイン基盤 shall 客向けアンケート Web のクライアント JS 予算および表示速度の基準を超過しない

## 今後の判断事項（design フェーズへの引き継ぎ）

- **抑制をどの層へ置くか**: `theme.css` の `@layer base` によるグローバル抑制か、部品ごとの個別指定か、その併用か。#49 で判明したとおり `@layer base` の規則は `@layer utilities` の部品側ユーティリティに詳細度と無関係に負けるため、抑制が実際に効くことを実描画で確認できる置き方を選ぶ必要がある。
- **処理中インジケータの代替表現**: 動きを止めた Spinner をどう「処理中」と伝えるか（静的アイコン＋文言、極低速化、別表現）。光過敏への配慮上、点滅は避けることが望ましい。
- **読み上げ強度の出し分け方**: 変種に応じて固定するか、呼び出し側が上書きできる形にするか。上書き可能にする場合、指定漏れ時の既定値をどちらにするかで安全側の倒れ方が変わる。
- **操作領域の拡大手段と重なりの扱い**: Checkbox / RadioGroup と同じ疑似要素方式を Button へ適用する場合、隣接配置時の重なりをどう検出・回避するか（部品側で保証するか、各面のレイアウト規約とするか）。
- **操作領域の検証手段**: 操作領域は実描画でのみ確定するため、jsdom のクラス検証では不足する可能性がある。#49 / #50 の是正で追加した `/ui-check` と実測 E2E（`readRenderedColors` と同じ経路）を再利用できるか。
