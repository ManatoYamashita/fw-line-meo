# Implementation Plan

本計画は「**ガードを先に入れて赤化を実証してから是正する**」という本リポジトリの規律（要件 5.6）に従う。したがって各領域は「ガード追加（赤化の確認）→ 実装（緑化）」の対で構成する。

`(P)` は直前の同階層タスクと同時実行できることを示す。共有するテストファイルが競合するため、多くの検証タスクは `(P)` にできない（各タスクの補足に理由を記す）。

- [ ] 1. Foundation: 実測が成立する検証面と計測基盤を用意する

- [x] 1.1 検証面を実測可能な状態に整える
  - 検証面のコンテナ幅が端末幅に対して妥当になるよう、既定スケールと衝突する指定を避けた形へ改める
  - 縮小寸法の操作可能部品を検証面へ配置し、縮小側の要求値の検証対象を実在させる
  - ラベルを伴うテキスト入力および選択部品の構成を検証面へ配置し、ラベルを含む行の検証対象を実在させる
  - 観察可能な完了条件: 検証面のコンテナ幅が端末幅相当（従来の 16px ではない）になり、縮小寸法の部品とラベル付きの入力・選択部品が実描画で確認できる
  - _Requirements: 4.2, 4.7_
  - _Boundary: UiCheckSurface_
  - 実測（Chromium / Pixel 5）: コンテナ幅 16px → **393px**。縮小寸法 `sm` 361×28 / `icon-sm` 28×28。ラベル付き入力（縦積み Field）361×59.3。ラベル付きチェック・ラジオの行 361×**42.0**（要求 44 に 2 不足＝タスク 5.3 の是正対象）。ラベル指定でチェック・ラジオ・入力のいずれも反応することを確認

- [x] 1.2 実描画の計測基盤と検証面の妥当性確認を用意する
  - 要素の実効的な操作領域（本体と拡張面を合わせた矩形）を実描画から求める計測手段を用意する
  - 計算済みスタイルからアニメーションと遷移の実効値を読み取る計測手段を用意する
  - 求めた幾何が実際に当たり判定を持つことを、座標を撃って確かめる手段を併せて用意する
  - 検証面のコンテナ幅が端末幅に対して妥当であることを、他の実測に先立って確認する
  - 観察可能な完了条件: 検証面の幅が不当な場合に、寸法の検証より先にその旨を示して失敗する
  - _Requirements: 5.3_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.1_
  - 赤化の実証: コンテナ幅の指定を元へ戻すと、寸法の検証に到達する前に
    `検証面の main の実幅が 32px しかない（端末幅 393px）` で失敗することを確認（`expectVerificationSurfaceSane`）

- [ ] 2. 動きへの配慮を確立する

- [x] 2.1 抑制規則の存在をコンパイル結果から検証するガードを追加する
  - 実コンパイルした結果に動き低減時の抑制規則が存在すること、それが基底のカスケードレイヤに属すること、および優先指定を伴うことを構文木で判定する
  - 優先指定が外れた場合に失敗することを、判定条件として明示する
  - 到達状態を決めるプロパティが抑制対象へ紛れ込んでいないことを併せて判定する（要件 1.4 の CSS 側の防波堤）
  - 抽出器の自己検証として、基底レイヤ外の同条件メディアクエリを拾わないことを確認する
  - 観察可能な完了条件: 抑制規則が未実装の現状に対して赤化し、失敗内容が「規則が存在しない」と読み取れる
  - _Requirements: 5.1, 5.6_
  - _Boundary: GeneratedCssGuard_
  - 赤化の実証: 3 面 × 2 項目 = 6 件が失敗。`base レイヤに prefers-reduced-motion の抑制ブロックがありません` /
    `抑制ブロックに animation-duration がありません（宣言されているのは （無し））`

- [x] 2.2 (P) 動き低減設定下の実測を検証へ追加する
  - 動き低減を有効にした文脈で、無限に繰り返すアニメーションの反復が停止し、状態遷移の所要時間が知覚できない水準であることを実測する
  - 対象は部品を名指しせず、面上でアニメーションを持つ要素を全走査する（部品の構造変更で静かに対象を失わないため）
  - 動き低減が無効な文脈で、同じ部品の動きが従来どおり維持されていることを実測する
  - 状態変化の到達状態（押下時の変位など）が、動き低減の有無によらず同一であることを実測する
  - 観察可能な完了条件: 抑制が未実装の現状に対して赤化し、実測値（反復回数・所要時間）が失敗メッセージに現れる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 5.1, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.2_
  - 赤化の実証: 抑制ブロックを撤去すると `spinner: 反復回数が infinite のまま。無限に繰り返すアニメーションが停止していない`
  - 空振りの実証（要件 1.4 側）: 抑制対象へ `translate` を紛れ込ませると
    `既定のボタン: 押下しても描画位置が変わらない（0px）` で赤化。静的ガードも
    `抑制ブロックが translate を宣言しています` で同時に赤化する
  - 検証手段そのものの欠陥を 2 件是正した（下の Implementation Notes 参照）

- [x] 2.3 動き低減設定下の抑制を実装する
  - テーマ層の基底レイヤに、動き低減時の抑制規則を追加する
  - 抑制の対象はアニメーションと遷移の「経過」に限り、到達する見た目には触れない
  - 優先指定が動作条件であること（外すと後段のレイヤに負けて無言で機能しなくなること）を実装コメントで固定する
  - 観察可能な完了条件: 2.1 と 2.2 のガードが緑になり、動き低減が無効な環境では従来の動きが保たれている
  - _Requirements: 1.1, 1.2, 1.3, 1.4_
  - _Boundary: MotionSuppression_
  - _Depends: 2.1, 2.2_
  - 実測（動き低減 有効 / 無効）: `animation-duration` 1e-05s / 1s、`animation-iteration-count` 1 / infinite、
    `transition-duration` 1e-05s / 0.15s。research.md R-1 の予測と一致

- [x] 2.4 動きに関わる指定の分類ガードを追加する
  - 部品の動きに関わる指定を走査し、「経過（抑制対象）」と「到達状態（抑制禁止）」の 2 区分へ双方向で突き合わせる
  - いずれの区分にも属さない指定、および部品から消えたのに表に残った項目を失敗させる
  - 到達状態に分類された指定が出力する CSS プロパティを表に持ち、それをテーマ層が抑制していないことを判定する
  - 観察可能な完了条件: 分類表から 1 件を意図的に外すと赤化し、抽出結果が 0 件でも赤化する
  - _Requirements: 1.4, 5.5, 5.6_
  - _Boundary: ComponentContractGuard_
  - _Depends: 2.3_
  - 空振りの実証（4 通り）:
    1. 分類表から 1 件除去 → `分類されていない動きの指定があります: transition-none`
    2. 部品へ新しい動きを追加 → `分類されていない動きの指定があります: animate-pulse`
    3. 分類表に死んだ項目を残す → `部品から消えた指定が分類表に残っています: animate-bounce`
    4. 到達状態のプロパティをテーマ層の抑制対象へ入れる →
       `active:not-aria-[haspopup]:translate-y-px が出力する translate を theme.css が抑制しています`

- [ ] 3. 処理中の伝達を動きから切り離す

- [x] 3.1 処理中表示の役割と読み上げ名の非後退ガードを追加する
  - 処理中表示が支援技術へ通知される役割を保持していること、および読み上げ名を呼び出し側が置換できることを固定する
  - 呼び出し側の視覚指定が「実際に動く要素」へ届くことを、要素名を名指しせずに固定する
  - 構造変更の前に置くことで、変更が既存の支援技術向け情報を壊した場合に赤化する状態を作る
  - 観察可能な完了条件: 現行実装に対して緑であり、役割または読み上げ名の指定を外すと赤化する
  - _Requirements: 2.2, 2.3, 5.6_
  - _Boundary: ComponentContractGuard_
  - 赤化の実証: 役割の指定を外すと 6 件が `Unable to find an accessible element with the role "status"` で失敗。
    視覚指定を動く要素へ渡さないと `呼び出し側の className が、動きを持つ視覚的な本体へ届いていません`

- [x] 3.2 (P) 動き低減時に処理中と判別できることの実測を追加する
  - 動き低減を有効にした文脈で、処理中表示が動きに依存しない可視の手掛かりを提示していることを実測する
  - 「見えているか」はクラス名ではなく実際に描画された幅で判定する（読み上げ専用の指定と可視化の指定はどちらも同じレイヤに生成され、勝敗は生成順で決まるため）
  - 動き低減が無効な文脈では、その手掛かりが露出していないことを併せて確認する
  - 観察可能な完了条件: 代替表現が未実装の現状に対して赤化し、静止した図形だけでは判別できない状態を検出する
  - _Requirements: 2.1, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.2, 2.3_
  - 赤化の実証: `処理中表示に文言が無く、静止した図形だけになっている`

- [x] 3.3 処理中表示に動きへ依存しない代替表現を実装する
  - 動き低減時のみ、読み上げ名と同一の情報源から得た文言を可視化する
  - 視覚的な大きさを決める指定は図形側へ適用し、包む要素には寸法指定を持たせない
  - 包む要素と内側の要素を区別できる識別子を与え、検証が対象を取り違えないようにする
  - 観察可能な完了条件: 3.1 と 3.2 のガードが緑になり、動き低減が無効な環境では表示が従来どおりである
  - _Requirements: 2.1, 2.2, 2.3_
  - _Boundary: Spinner_
  - _Depends: 3.1, 3.2_
  - 設計上の最大のリスク（可視化の指定が読み上げ専用の指定に生成順で負けないか）は実描画で解消。
    動き低減 有効時に文言が描画され、無効時は 1px 未満に潰れることを実測で確認

- [ ] 4. 通知の読み上げ強度を出し分ける

- [x] 4.1 変種ごとの読み上げ強度を検証するガードを追加する
  - エラーを表す変種は読み上げを直ちに割り込ませる強度、成功と既定の変種は割り込ませない強度であることを判定する
  - 部品が提供する変種の一覧をソースから抽出し、強度の対応表と双方向で突き合わせる
  - 読み上げ対象から外れる変種が存在しないこと、および呼び出し側による上書きが効くことを判定する
  - 変種ごとの視覚表現が読み上げ強度の変更によって変化していないことを併せて固定する
  - 観察可能な完了条件: 全変種が同一強度である現状に対して赤化し、どの変種が要求と異なるかが失敗メッセージに現れる
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 5.2, 5.6_
  - _Boundary: ComponentContractGuard_
  - 赤化の実証: `default 変種の読み上げ強度が alert です。status であるべきです` /
    `success 変種の読み上げ強度が alert です。status であるべきです`
  - 抽出器の欠陥を 1 件是正: カンマ直後を起点に変種キーを探す実装は、説明コメントに挟まれた

- [x] 4.2 変種に応じた既定の読み上げ強度を実装する
  - 変種から既定の強度を導く対応を与え、呼び出し側が明示した場合はそれを優先する現行の性質を保つ
  - 視覚表現には一切手を触れない
  - 観察可能な完了条件: 4.1 のガードが緑になり、通知の見た目が変更前と同一である
  - _Requirements: 3.1, 3.2, 3.3, 3.4_
  - _Boundary: Alert_
  - _Depends: 4.1_
  - 波及: 既存の検証が通知を `role` で引いていた箇所（単体 4 件・実描画 1 件）を `data-slot` 経由へ改めた。
    変種ごとに `role` が変わるため、`role` で引くと変種によって取れたり取れなかったりする

- [ ] 5. タッチ操作の確実性を確立する

- [x] 5.1 既定寸法の操作領域と隣接部品の被覆を実測するガードを追加する
  - 客向け主動線で用いる既定寸法の押しボタンについて、実効的な操作領域が要求値以上であることを実測する
  - 隣接して配置された操作可能部品について、いずれの拡張領域も隣接部品の視覚領域を覆っていないことを実測する
  - 被覆の判定は拡張が入って初めて意味を持つため、拡張量を一時的に過大にすると赤化することを確認し、常に真の判定になっていないことを示す
  - 観察可能な完了条件: 拡張が未実装の現状に対して寸法不足で赤化し、不足している実測値（px）が失敗メッセージに現れる。かつ被覆判定が空振りしていないことを示せる
  - _Requirements: 4.1, 4.3, 4.4, 4.5, 5.3, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.2_
  - 赤化の実証: `既定のボタン（区分 default）の操作領域の高さが 32px（要求 44px・視覚寸法は 32px）`
  - 空振りの実証: 選択部品の拡張量を過大（44px 相当）にすると
    `ラジオ1 の操作領域 … が ラジオ2 の見えている領域 … を覆っています` で赤化。
    同時にこれは、選択部品へ 44px を与えられないという設計訂正の根拠そのものである
  - 前提の追加: 押しボタンが寸法区分を実描画から読めるよう `data-size` を付与した（`card.tsx` と同じ作法）。
    高さから区分を推測すると、区分が増えたときに検証が静かに誤った要求値を当てはめる

- [x] 5.2 縮小寸法・複数行入力・ラベル行の充足を実測するガードを追加する
  - 高密度配置向けの縮小寸法の部品、および選択部品単体が縮小側の要求値を満たすことを実測する
  - 既に要求値を満たしている複数行入力が、変更を受けずに満たし続けていることを実測する
  - ラベル行の指定でテキスト入力へフォーカスが移り、チェックボックスとラジオが当該項目へ反応すること、およびラベルを含む行全体が要求値を満たすことを実測する
  - 観察可能な完了条件: ラベル行の高さ不足で赤化し、実測値が失敗メッセージに現れる。既に充足している項目については要求値を一時的に引き上げると赤化し、空振りしていないことを示せる
  - _Requirements: 4.2, 4.6, 4.7, 4.8, 5.3, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.1, 1.2_
  - 赤化の実証: `ラベルを含む行「ラベル付きチェック」の高さが 42px（要求 44px）`
  - 空振りの実証: 下限を一時的に 33px へ引き上げると `checkbox の操作領域の高さが 30px（下限 33px）` で赤化。
    ラベルの関連付けを外すと `ラベル文字を指してもテキスト入力へフォーカスが移らない` で赤化

- [x] 5.3 既定寸法の操作領域とラベル行を視覚寸法を変えずに是正する
  - 押しボタンに、部品の外側へはみ出す不可視の面による操作領域の拡張を与える
  - ラベルが制御を包む構成について、行全体の最小高を要求値まで引き上げる（内容が要求値を超える場合は現状どおり内容に従う）
  - 拡張は押しボタンの既定寸法にのみ適用し、縮小寸法と選択部品は現状のまま据え置く
  - 観察可能な完了条件: 5.1 と 5.2 のガードが緑になり、部品の視覚的な寸法と周囲の余白が変更前と同一である。拡張後も隣接部品の視覚領域が覆われていない
  - _Requirements: 4.1, 4.3, 4.4, 4.5, 4.7_
  - _Boundary: Button, Field 構成_
  - _Depends: 5.1, 5.2_
  - **設計時の見積もりの誤りを是正**: `::after` の含有ブロックは本体の *padding box* であり、
    枠線 1 ピクセル分だけ内側から始まる。外側への実効的なはみ出しは `指定値 − 枠線幅` になるため、
    32px を 44px にするには指定 6px では足りず 8px が要る（実効 7px → 46px）
  - 実測（視覚 → 実効）: 既定ボタン 361×32 → **375×46**、`lg` 相当も 46。
    ラベル行 42 → **44**。縮小寸法（28px）・選択部品（38×30）・複数行入力（64px）は不変

- [x] 5.4 寸法区分の分類ガードを追加する
  - 部品が提供する寸法区分を走査し、既定寸法と縮小寸法のいずれの要求値に属するかの宣言と双方向で突き合わせる
  - いずれにも宣言されていない寸法区分、および部品から消えたのに表に残った項目を失敗させる
  - 観察可能な完了条件: 宣言から 1 件を意図的に外すと赤化し、抽出結果が 0 件でも赤化する
  - _Requirements: 5.4, 5.6_
  - _Boundary: ComponentContractGuard_
  - _Depends: 5.3_
  - 分類と実装の対応も固定する（既定区分は拡張面と配置基準を持ち、縮小区分は持たない）
  - 空振りの実証（4 通り）:
    1. 分類から 1 件除去 → `いずれの要求値に属するか宣言されていない寸法区分があります: icon-sm`
    2. 死んだ区分を残す → `部品から消えた寸法区分が分類表に残っています: xxl`
    3. 分類を取り違える → `sm は既定寸法だが操作領域の拡張を持たない（44px に届かない）`
    4. 部品へ新しい区分を追加 → `いずれの要求値に属するか宣言されていない寸法区分があります: xl`

  - 観察可能な完了条件: 単体・統合・実描画の全検証が緑であり、各ガードの赤化実証が対応付けて示せる

## 並行実行に関する補足

- `(P)` を付けたのは 2.2 と 3.2 のみである。いずれも直前の同階層タスクと**別のファイルを対象とし、相互に依存しない**。
- 実装タスク（2.3 / 3.3 / 4.2 / 5.3）は互いに異なる部品を対象とするため本来は同時実行できるが、**それぞれが直前の検証タスクに依存する**ため `(P)` は付けない。各グループの検証が済んだ段階では、これら 4 つを並行して進めてよい。
- 検証タスクの多くは共有する検証ファイル上で作業するため `(P)` にできない。具体的には 3.1 / 4.1 / 5.4 が同一の属性検証ファイルを、2.2 / 3.2 / 5.1 / 5.2 が同一の実描画検証ファイルを対象とする。

## Implementation Notes

- **ローカルでの E2E 実行手順**（本 spec の検証は実描画が中心のため頻繁に要る）:
  ```bash
  pnpm -C ts --filter @fwlm/survey-web run build
  lsof -ti:3100 | xargs -r kill -9          # 古い next start の残留を必ず殺す
  NODE_OPTIONS="--import $PWD/ts/apps/survey-web/e2e/mock-gemini.mjs" \
    PORT=3100 pnpm -C ts --filter @fwlm/survey-web run start &
  E2E_BASE_URL=http://127.0.0.1:3100 pnpm -C ts --filter @fwlm/survey-web \
    exec playwright test ui-foundation.spec.ts
  ```
  `NODE_OPTIONS` の Gemini モックを省くと下書き画面のテストだけが `generation_failed` で落ちる。
  これは環境要因であり実装の欠陥ではない。**next サーバのプロセスにのみ**読み込ませること。
- **`/ui-check` は `next build` を通さないと変更が反映されない**（本番相当の静的生成面）。
  ソースを直しただけで E2E を回すと古い描画を測ることになる。
- **E2E spec は `tsconfig.json` の `exclude` に入っており型検査されない。** Playwright は
  型検査なしでトランスパイルするため、型の誤りは実行時まで表面化しない。
- **動き低減の模擬は `test.use({ contextOptions: { reducedMotion } })` で渡す**（Playwright 1.61）。
  `test.use({ reducedMotion })` はトップレベルの test option として存在せず **黙って無視される**。
  未知のキーが素通りするうえ型検査もされないため、「設定したつもりで通常の文脈を測り、
  抑制が無くても緑」という空振りになる。実際にこれを踏んだ。各検証の冒頭で
  `matchMedia(...).matches` を assert しておくと必ず捕まえられる。
- **到達状態を計算済みスタイルの特定プロパティで測ってはならない。** Tailwind v4 の
  `translate-y-px` は `transform` ではなく独立した `translate` プロパティへ出力される。
  `transform` を読むと押下の有無によらず常に `none` が返り、**何も測らずに緑**になる。
  実際に描画された位置（`getBoundingClientRect`）で測ること。同じ理由で、抑制の禁止
  プロパティ表には `transform` だけでなく `translate` / `scale` / `rotate` を含める。
- **遷移の到達値を読むときは走り切るまで待つ。** 待たずに読むと途中の値（実測 0.92px）を
  最終値（1px）と比べ、抑制の有無ではなく遷移速度の差を検出してしまう。待ち時間は
  実測した遷移時間から導く。
