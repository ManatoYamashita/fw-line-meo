# Implementation Plan

本計画は「**ガードを先に入れて赤化を実証してから是正する**」という本リポジトリの規律（要件 5.6）に従う。したがって各領域は「ガード追加（赤化の確認）→ 実装（緑化）」の対で構成する。

`(P)` は直前の同階層タスクと同時実行できることを示す。共有するテストファイルが競合するため、多くの検証タスクは `(P)` にできない（各タスクの補足に理由を記す）。

- [ ] 1. Foundation: 実測が成立する検証面と計測基盤を用意する

- [x] 1.1 検証面を実測可能な状態に整える
  - 検証面のコンテナ幅が端末幅に対して妥当になるよう、既定スケールと衝突する指定を避けた形へ改める
  - 縮小寸法の操作可能部品を検証面へ配置し、縮小側の要求値の検証対象を実在させる
  - ラベルを伴うテキスト入力および選択部品の構成を検証面へ配置し、ラベルを含む行の検証対象を実在させる
  - 観察可能な完了条件: 検証面のコンテナ幅が端末幅相当（従来の 16px ではない）になり、縮小寸法の部品とラベル付きの入力・選択部品が実描画で確認できる
  - _Requirements: 4.2, 4.7_
  - _Boundary: UiCheckSurface_
  - 実測（Chromium / Pixel 5）: コンテナ幅 16px → **393px**。縮小寸法 `sm` 361×28 / `icon-sm` 28×28。ラベル付き入力（縦積み Field）361×59.3。ラベル付きチェック・ラジオの行 361×**42.0**（要求 44 に 2 不足＝タスク 5.3 の是正対象）。ラベル指定でチェック・ラジオ・入力のいずれも反応することを確認

- [ ] 1.2 実描画の計測基盤と検証面の妥当性確認を用意する
  - 要素の実効的な操作領域（本体と拡張面を合わせた矩形）を実描画から求める計測手段を用意する
  - 計算済みスタイルからアニメーションと遷移の実効値を読み取る計測手段を用意する
  - 検証面のコンテナ幅が端末幅に対して妥当であることを、他の実測に先立って確認する
  - 観察可能な完了条件: 検証面の幅が不当な場合に、寸法の検証より先にその旨を示して失敗する
  - _Requirements: 5.3_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.1_

- [ ] 2. 動きへの配慮を確立する

- [ ] 2.1 抑制規則の存在をコンパイル結果から検証するガードを追加する
  - 実コンパイルした結果に動き低減時の抑制規則が存在すること、それが基底のカスケードレイヤに属すること、および優先指定を伴うことを構文木で判定する
  - 優先指定が外れた場合に失敗することを、判定条件として明示する
  - 観察可能な完了条件: 抑制規則が未実装の現状に対して赤化し、失敗内容が「規則が存在しない」と読み取れる
  - _Requirements: 5.1, 5.6_
  - _Boundary: GeneratedCssGuard_

- [ ] 2.2 (P) 動き低減設定下の実測を検証へ追加する
  - 動き低減を有効にした文脈で、無限に繰り返すアニメーションの反復が停止し、状態遷移の所要時間が知覚できない水準であることを実測する
  - 動き低減が無効な文脈で、同じ部品の動きが従来どおり維持されていることを実測する
  - 状態変化の到達状態（押下時の変位など）が、動き低減の有無によらず同一であることを実測する
  - 観察可能な完了条件: 抑制が未実装の現状に対して赤化し、実測値（反復回数・所要時間）が失敗メッセージに現れる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 5.1, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.2_

- [ ] 2.3 動き低減設定下の抑制を実装する
  - テーマ層の基底レイヤに、動き低減時の抑制規則を追加する
  - 抑制の対象はアニメーションと遷移の「経過」に限り、到達する見た目には触れない
  - 優先指定が動作条件であること（外すと後段のレイヤに負けて無言で機能しなくなること）を実装コメントで固定する
  - 観察可能な完了条件: 2.1 と 2.2 のガードが緑になり、動き低減が無効な環境では従来の動きが保たれている
  - _Requirements: 1.1, 1.2, 1.3, 1.4_
  - _Boundary: MotionSuppression_
  - _Depends: 2.1, 2.2_

- [ ] 2.4 動きに関わる指定の分類ガードを追加する
  - 部品の動きに関わる指定を走査し、「経過（抑制対象）」と「到達状態（抑制禁止）」の 2 区分へ双方向で突き合わせる
  - いずれの区分にも属さない指定、および部品から消えたのに表に残った項目を失敗させる
  - 到達状態に分類された指定が抑制対象へ紛れ込んでいないことを判定する
  - 観察可能な完了条件: 分類表から 1 件を意図的に外すと赤化し、抽出結果が 0 件でも赤化する
  - _Requirements: 1.4, 5.5, 5.6_
  - _Boundary: ComponentContractGuard_
  - _Depends: 2.3_

- [ ] 3. 処理中の伝達を動きから切り離す

- [ ] 3.1 処理中表示の役割と読み上げ名の非後退ガードを追加する
  - 処理中表示が支援技術へ通知される役割を保持していること、および読み上げ名を呼び出し側が置換できることを固定する
  - 構造変更の前に置くことで、変更が既存の支援技術向け情報を壊した場合に赤化する状態を作る
  - 観察可能な完了条件: 現行実装に対して緑であり、役割または読み上げ名の指定を外すと赤化する
  - _Requirements: 2.2, 2.3, 5.6_
  - _Boundary: ComponentContractGuard_

- [ ] 3.2 (P) 動き低減時に処理中と判別できることの実測を追加する
  - 動き低減を有効にした文脈で、処理中表示が動きに依存しない可視の手掛かりを提示していることを実測する
  - 動き低減が無効な文脈では、その手掛かりが露出していないことを併せて確認する
  - 観察可能な完了条件: 代替表現が未実装の現状に対して赤化し、静止した図形だけでは判別できない状態を検出する
  - _Requirements: 2.1, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.2, 2.3_

- [ ] 3.3 処理中表示に動きへ依存しない代替表現を実装する
  - 動き低減時のみ、読み上げ名と同一の情報源から得た文言を可視化する
  - 視覚的な大きさを決める指定は図形側へ適用し、包む要素には寸法指定を持たせない
  - 包む要素と内側の要素を区別できる識別子を与え、検証が対象を取り違えないようにする
  - 観察可能な完了条件: 3.1 と 3.2 のガードが緑になり、動き低減が無効な環境では表示が従来どおりである
  - _Requirements: 2.1, 2.2, 2.3_
  - _Boundary: Spinner_
  - _Depends: 3.1, 3.2_

- [ ] 4. 通知の読み上げ強度を出し分ける

- [ ] 4.1 変種ごとの読み上げ強度を検証するガードを追加する
  - エラーを表す変種は読み上げを直ちに割り込ませる強度、成功と既定の変種は割り込ませない強度であることを判定する
  - 読み上げ対象から外れる変種が存在しないこと、および呼び出し側による上書きが効くことを判定する
  - 変種ごとの視覚表現が読み上げ強度の変更によって変化していないことを併せて固定する
  - 観察可能な完了条件: 全変種が同一強度である現状に対して赤化し、どの変種が要求と異なるかが失敗メッセージに現れる
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 5.2, 5.6_
  - _Boundary: ComponentContractGuard_

- [ ] 4.2 変種に応じた既定の読み上げ強度を実装する
  - 変種から既定の強度を導く対応を与え、呼び出し側が明示した場合はそれを優先する現行の性質を保つ
  - 視覚表現には一切手を触れない
  - 観察可能な完了条件: 4.1 のガードが緑になり、通知の見た目が変更前と同一である
  - _Requirements: 3.1, 3.2, 3.3, 3.4_
  - _Boundary: Alert_
  - _Depends: 4.1_

- [ ] 5. タッチ操作の確実性を確立する

- [ ] 5.1 既定寸法の操作領域と隣接部品の被覆を実測するガードを追加する
  - 客向け主動線で用いる既定寸法の押しボタンについて、実効的な操作領域が要求値以上であることを実測する
  - 隣接して配置された操作可能部品について、いずれの拡張領域も隣接部品の視覚領域を覆っていないことを実測する
  - 被覆の判定は拡張が入って初めて意味を持つため、拡張量を一時的に過大にすると赤化することを確認し、常に真の判定になっていないことを示す
  - 観察可能な完了条件: 拡張が未実装の現状に対して寸法不足で赤化し、不足している実測値（px）が失敗メッセージに現れる。かつ被覆判定が空振りしていないことを示せる
  - _Requirements: 4.1, 4.3, 4.4, 4.5, 5.3, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.2_

- [ ] 5.2 縮小寸法・複数行入力・ラベル行の充足を実測するガードを追加する
  - 高密度配置向けの縮小寸法の部品、および選択部品単体が縮小側の要求値を満たすことを実測する
  - 既に要求値を満たしている複数行入力が、変更を受けずに満たし続けていることを実測する
  - ラベル行の指定でテキスト入力へフォーカスが移り、チェックボックスとラジオが当該項目へ反応すること、およびラベルを含む行全体が要求値を満たすことを実測する
  - 観察可能な完了条件: ラベル行の高さ不足で赤化し、実測値が失敗メッセージに現れる。既に充足している項目については要求値を一時的に引き上げると赤化し、空振りしていないことを示せる
  - _Requirements: 4.2, 4.6, 4.7, 4.8, 5.3, 5.6_
  - _Boundary: RenderedMeasurementE2E_
  - _Depends: 1.1, 1.2_

- [ ] 5.3 既定寸法の操作領域とラベル行を視覚寸法を変えずに是正する
  - 押しボタンに、部品の外側へはみ出す不可視の面による操作領域の拡張を与える
  - ラベルが制御を包む構成について、行全体の最小高を要求値まで引き上げる（内容が要求値を超える場合は現状どおり内容に従う）
  - 拡張は押しボタンの既定寸法にのみ適用し、縮小寸法と選択部品は現状のまま据え置く
  - 観察可能な完了条件: 5.1 と 5.2 のガードが緑になり、部品の視覚的な寸法と周囲の余白が変更前と同一である。拡張後も隣接部品の視覚領域が覆われていない
  - _Requirements: 4.1, 4.3, 4.4, 4.5, 4.7_
  - _Boundary: Button, Field 構成_
  - _Depends: 5.1, 5.2_

- [ ] 5.4 寸法区分の分類ガードを追加する
  - 部品が提供する寸法区分を走査し、既定寸法と縮小寸法のいずれの要求値に属するかの宣言と双方向で突き合わせる
  - いずれにも宣言されていない寸法区分、および部品から消えたのに表に残った項目を失敗させる
  - 観察可能な完了条件: 宣言から 1 件を意図的に外すと赤化し、抽出結果が 0 件でも赤化する
  - _Requirements: 5.4, 5.6_
  - _Boundary: ComponentContractGuard_
  - _Depends: 5.3_

- [ ] 6. 統合と非後退の確認

- [ ] 6.1 既存の品質が後退していないことを確認する
  - キーボード操作時の可視フォーカス表示が、表示内容と視認性の両面で従来どおりであることを既存のガードで確認する
  - 部品が支援技術へ通知する役割と状態が後退していないことを既存のガードで確認する
  - 既存のコントラスト要件、およびクライアント資源の予算と表示速度の基準を超過していないことを確認する
  - 観察可能な完了条件: 既存の全ガードが緑であり、予算の実測値が基準内であることを数値で示せる
  - _Requirements: 6.1, 6.2, 6.3, 6.4_

- [ ] 6.2 本番相当の条件で全検証を通し、赤化の実証を記録する
  - 本番相当のビルドに対して実描画の検証を通し、開発時のみ成立する挙動に依存していないことを確認する
  - 各ガードについて、是正前に赤化したことの記録（失敗内容と実測値）を揃える
  - 観察可能な完了条件: 単体・統合・実描画の全検証が緑であり、各ガードの赤化実証が対応付けて示せる
  - _Requirements: 5.6_
  - _Depends: 2.4, 3.3, 4.2, 5.4_

## 並行実行に関する補足

- `(P)` を付けたのは 2.2 と 3.2 のみである。いずれも直前の同階層タスクと**別のファイルを対象とし、相互に依存しない**。
- 実装タスク（2.3 / 3.3 / 4.2 / 5.3）は互いに異なる部品を対象とするため本来は同時実行できるが、**それぞれが直前の検証タスクに依存する**ため `(P)` は付けない。各グループの検証が済んだ段階では、これら 4 つを並行して進めてよい。
- 検証タスクの多くは共有する検証ファイル上で作業するため `(P)` にできない。具体的には 3.1 / 4.1 / 5.4 が同一の属性検証ファイルを、2.2 / 3.2 / 5.1 / 5.2 が同一の実描画検証ファイルを対象とする。
