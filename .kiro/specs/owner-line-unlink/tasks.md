# Implementation Plan

- [ ] 1. 基盤: スキーマ・型・DB 権限・不在検査
- [ ] 1.1 オーナーの連携状態の列と不変条件、監査の種別を足す migration を書く
  - `owners` の LINE ユーザー ID を空にできるようにし、解除の時刻・メニュー未解除の元の ID・引継ぎ先の 3 列を足す
  - 連携状態の 3 つの不変条件（解除と ID の有無の同値、未解除の印は解除済みだけ、引継ぎ先は解除済みだけで自分自身を指さない）を CHECK で表す
  - 監査の種別を、既存の 25 値に解除・引継ぎ（オーナー）・引継ぎ（店舗）の 3 値を足した 28 値で作り直し、TS 側の種別の一覧も同じ 3 値で揃える
  - migrations をクリーンに適用でき、既存の db/test の assertions と smoke が緑のまま。不正な組み合わせ（ID も解除時刻も無い行など）の更新が CHECK で拒否される assertion が赤→緑で確認できる
  - _Requirements: 1.6, 2.6, 4.1, 7.4_

- [ ] 1.2 オーナーの面から解除の列を書けなくする列単位の権限と、その検査を足す
  - line-webhook と客向け Web のロールから `owners` の INSERT・UPDATE をテーブル単位で剥がし、解除の列を除いた列だけを与え直す（引継ぎ先は UPDATE のみ与える）
  - 実ロールを作って権限を問う検査スクリプトを足し、db/test の実行装置の RUN 表へ登録する
  - 検査が緑。line-webhook のロールへ LINE ユーザー ID の UPDATE を戻す変異で検査が赤になることを実測し、PR に記録できる形で残す
  - _Requirements: 8.1, 8.3, 8.4_
  - _Boundary: GrantsOwnerColumns, OwnerLinePrivilegesCheck_

- [ ] 1.3 (P) オーナー・客の面に解除を書く識別子が無いことの不在検査 (B5) を足す
  - 店舗の停止の不在検査 (B4) と同じ走査面・同じ「走査 0 件は赤」の規律で、解除の DAL 名と解除の列への代入を検出する
  - line-webhook の既存の個別メニュー操作の名前に誤検出しない
  - 不在検査が緑。line-webhook の実装へ解除の DAL の呼び出しを足す変異で赤になることを実測し、記録を残す
  - _Requirements: 8.1, 8.3, 8.4_
  - _Boundary: AbsenceCheckB5_
  - _Depends: 1.1_

- [ ] 1.4 オーナーの行の型を連携状態に合わせ、旧 LINE ID の消費箇所を直す
  - オーナーの行の LINE ユーザー ID を「無いことがある」型にし、新しい 3 列を型と読み出しの列に加える
  - 型検査が示す消費箇所を直す: GBP の通知は ID が無ければ送らない、完了後メニューの一括張り直しは解除済みを抽出しない
  - 全ワークスペースの型検査と既存の試験が緑。GBP の通知が解除済みオーナーへ送られないこと、一括張り直しの抽出に解除済みが含まれないことを試験で確かめる
  - _Requirements: 3.5, 4.5_
  - _Depends: 1.1_

- [ ] 2. データアクセス: 解除・一覧・引継ぎ
- [ ] 2.1 範囲つきの解除とメニュー未解除の印の消去を実装する
  - 範囲（代理店）の判定と施錠を 1 つのトランザクションで行い、不存在と範囲外を同じ結果にする
  - 連携中なら解除済みにし、元の ID を未解除の印として残し、元の ID か当該オーナーに紐づく会話の行を消す。既に解除済みなら状態を変えない
  - 元の ID を別の連携中オーナーが持つときは、メニュー操作の対象を返さず未解除の印を消す
  - 実 DB 試験で、解除後に店舗・集計・停止状態・代理店が変わらないこと、二重の解除が「変化なし」になること、失敗時に解除前のままであることが確かめられる
  - _Requirements: 1.1, 1.2, 1.3, 1.5, 1.6, 1.7, 3.3, 4.2, 5.5_

- [ ] 2.2 (P) 連携状態つきのオーナー一覧を実装する
  - 代理店の指定が無ければ全代理店、あれば当該代理店のオーナーを返す
  - 各行に担当代理店名・連携状態・メニュー未解除・確定済み店舗の名前・引継ぎ先（表示名）を含め、LINE ユーザー ID は含めない
  - 既存の代理店別の一覧関数は 4.4 で呼び出し元を切り替えるまで残し、各タスクの時点で全ワークスペースの型検査が緑のままにする
  - 実 DB 試験で、範囲・連携状態の 3 通り・引継ぎ先の有無が期待どおりに返る
  - _Requirements: 2.1, 2.5, 2.6_
  - _Boundary: OwnersRepo_

- [ ] 2.3 引継ぎのための所有者の施錠と全店舗の付け替えを実装する
  - Place の店舗の所有者をトランザクション内で施錠し、施錠後に読み直して返す
  - 旧オーナーの全店舗（確定済み・未確定・停止中）の所有者を新しいオーナーへ移し、旧オーナーに引継ぎ先を記録する。店舗のほかの列には触れない
  - 実 DB 試験で、付け替え後も店舗の ID・停止状態・日次データ・集計が残り、旧オーナーの引継ぎ先が新しいオーナーを指す
  - _Requirements: 2.6, 6.1, 6.3, 6.6_

- [ ] 3. オンボーディングの確定での引継ぎ
- [ ] 3.1 オンボーディング専用の確定を実装する
  - 所有者が無ければ新規に確定し、自分なら成功、解除済みかつ同じ代理店なら全店舗を引き継ぎ、それ以外は登録済みとして拒否する。確定・付け替え・状態遷移は 1 トランザクション
  - 並行の挿入で一意制約に当たったときは 1 回だけやり直す
  - 既存の確定（管理画面の店舗登録が使う）の振る舞いは変えない
  - 実 DB 試験で、別の代理店・連携中の所有者の拒否、2 つの接続での同時確定で片方だけが引き継ぐこと、既存の確定が解除済みオーナーの Place に対して登録済みを返し続けることが確かめられる
  - _Requirements: 6.1, 6.3, 6.4, 6.5, 6.6_
  - _Depends: 2.3_

- [ ] 4. dashboard-api: 解除の操作と一覧
- [ ] 4.1 (P) 個別リッチメニューの解除だけを行う LINE アダプタを実装する
  - 呼び出しごとにトークンを発行して個別リンクを外し、2xx と 404 を成功、それ以外とトークン発行・通信の失敗を種別つきの失敗として返す。例外を投げない
  - 通信は注入された取得関数と時間制限を使い、記録に応答本文・トークン・LINE ユーザー ID を載せない
  - 単体試験で、応答の各種と時間切れが期待どおりの結果に写り、外部へ通信しない
  - _Requirements: 3.1, 3.4_
  - _Boundary: LineRichMenuAdapter_

- [ ] 4.2 dashboard-api の設定に LINE の資格情報を必須として足す
  - チャネル ID とチャネルシークレットを起動時に検証し、欠落は明示エラーで止める
  - spec の env 宣言表（店舗 QR 発行の手順）と、env を組み立てる既存の試験に 2 値（ダミー）を足す
  - env 名ガードと dashboard-api の既存の試験が緑で、欠落時に起動が失敗することを試験で確かめる
  - _Requirements: 3.1_

- [ ] 4.3 解除と外し直しのルートを実装し、合成ルートへ配線する
  - 認証・UUID の事前ガード・範囲の決定の後に解除を行い、状態が変わったときだけ監査を残し、メニュー操作の対象があれば LINE アダプタを呼んで成功時に未解除の印を消す
  - 応答はオーナーの連携状態とメニューの結果（外した・失敗・不要）を返し、範囲外と不存在は同じ 404 にする
  - メニューの成否を事象として記録し、事象名を観測の正典へ登録する
  - ハンドラの単体試験と実 DB の試験で、運営・代理店の範囲、二重の解除、LINE の成功・失敗・不要、監査の有無、監査の失敗でも 200 になることが確かめられる
  - _Requirements: 1.1, 1.2, 1.3, 1.5, 1.7, 3.1, 3.2, 3.3, 3.4, 7.1, 7.3_
  - _Depends: 2.1, 4.1, 4.2_

- [ ] 4.4 オーナー一覧のルートを連携状態つきに広げる
  - 運営が代理店を指定しなければ 400 ではなく全オーナーを返し、代理店の利用者は従来どおり自代理店に束縛する
  - 応答に連携状態・メニュー未解除・店舗名・引継ぎ先・担当代理店名を足す
  - 合成ルートの一覧の取得を新しい関数へ切り替え、旧い代理店別の一覧関数を消す（4.3 と同じ合成ルートを触るので 4.3 の後に行う）
  - 単体試験で範囲の規則と応答の形が確かめられ、既存の店舗登録の試験が緑のまま
  - _Requirements: 2.1, 2.5, 2.6_
  - _Depends: 2.2_

- [ ] 5. dashboard-web: オーナーの画面

  - クライアントの試験で、要求の形と応答の読み取り（メニューの結果の 3 値を含む）が確かめられる

- [ ] 5.2 オーナー一覧の画面と、解除・外し直しの操作を作る

  - 解除は 3 点（通知が届かず店舗も見られなくなる／店舗と履歴は残る／同じ店舗を LINE で確定し直すと引き継げる）を示す確認ダイアログを経てだけ送る。メニュー未解除なら外し直しの操作を出す
  - メニューの失敗、要求の失敗のそれぞれで所定の表示を出し、成功時は再読み込みせずに一覧を取り直す。ナビゲーションにオーナーの項目を足す
  - 画面と操作部品の試験で、表示の 4 通り、ダイアログの 3 点とキャンセル、失敗で行が変わらないこと、成功で行が更新されることが確かめられる

- [ ] 6. line-webhook: 再開の安全網と引継ぎ
- [ ] 6.1 Messenger に個別メニューの解除を足し、未登録の友だち追加で外す

  - 会話の試験で、引継ぎで完了の案内と完了後メニューが出て、3 種の監査が残り、拒否では既存の登録済みの案内が出る
