# Requirements Document

## Project Description (Input)

出典: Issue #487（オーナーの LINE の紐づけを管理画面から解除する）

### 誰が困っているか
- **運営・代理店**: 店舗の LINE 担当者（オーナー）が替わったとき、別の LINE アカウントで誤って登録したとき、本番の実機 E2E やスクリーンショットの撮り直しのときに、オーナーの LINE の紐づけを外す必要がある。

### 現状
- 紐づけを解除する経路がアプリのどこにも無い。dashboard-api にはオーナーへの書き込みルートが無く、`GET /owners` の一覧だけである。店舗の停止・再開（#252）はオーナーの紐づけに触れない。
- line-webhook は `unfollow` を黙って無視するので、ブロックしても状態は変わらない。
- 店舗特定済みのオーナーは、内容を問わずステータス案内だけを受け取り、オンボーディングへ戻る経路が無い。振り分けは `owners.onboarding_status` と LINE ユーザー ID だけを見て、`stores.suspended_at` を見ない（全店舗を停止しても完了後メニューが張り直されるだけだった・2026-10-24 実測）。
- 新しい担当者は同じ店舗を登録できない（`ux_stores_place_id` の一意制約で `place_already_registered` になる。`line-onboarding` Requirement 4.4）。
- 2026-10-24 には、撮り直しのために運営自身のアカウントを本番 DB の手作業で切り離した（`onboarding_sessions` の削除、`owners.line_user_id` の付け替え、LINE の個別リッチメニューのリンク解除）。この書き込みは書込境界の外（`owners` / `onboarding_sessions` の書き手は line-webhook）から行った。
- 旧 LINE ID を宛先・認可に使う箇所は、日次配信（delivery-job）、店舗詳細の LIFF 認可、完了後メニューの一括張り直しスクリプト、GBP 連携の通知（第2フェーズ・既定 OFF）である。

### 何を変えるか
- 運営・担当代理店が管理画面の操作で、オーナーの LINE の紐づけを解除できるようにする。物理削除はしない（`stores` の外部キーは `ON DELETE RESTRICT` で、日次サマリー・評価スナップショット・匿名集計が連鎖するため）。
- 解除した LINE アカウントは、招待コードの段階からオンボーディングをやり直せる。完了後メニューの個別リンクは外す。
- 解除済みオーナーの店舗と同じ Place を、同じ代理店の招待コードでオンボーディングした LINE アカウントが確定すると、解除済みオーナーの全店舗を引き継ぐ。これで担当者の交代・撮り直し・誤登録の取り消しを同じ操作で済ませる。

### 確定した論点（2026-10-24）
| 論点 | 決定 | 根拠 |
|---|---|---|
| 操作できる人 | 運営＋担当代理店 | 店舗の停止（#252）・招待コードの無効化と同じ RBAC（`agency-dashboard` Requirement 2） |
| 店舗の引継ぎ | 同じ Place の確定で引き継ぐ（同じ代理店の招待コードに限る） | 担当者の交代・撮り直し・誤登録の 3 用途を 1 つの経路で満たす。管理画面での付け替え操作は設けない |
| 引き継ぐ範囲 | 解除済みオーナーの全店舗 | オンボーディングで確定できるのは 1 店だけなので、1 店ずつにすると残りの店舗が LINE から二度と引き継げない |
| 解除中の店舗 | 取得は続け、配信だけ止める | 宛先の LINE アカウントが無い。取得を続けることで、引き継いだ担当者の推移に空白を作らない（Places の費用は続く） |
| 本人への通知 | 送らない | 月 200 通の枠を使わない。退職した担当者の場合もある。次に話しかけると招待コードの案内が出る |
| メニューを外せなかったとき | 解除は確定し、画面から外し直せる | LINE の操作は DB の確定と一体にできない。外れていなくても、次の会話はオンボーディングから始まる |
| 解除の取り消し | 専用の操作は設けない | 元の LINE アカウントが同じ Place を確定し直せば、引継ぎで元に戻る |

## Introduction

運営と代理店が、管理ダッシュボードからオーナーと LINE アカウントの紐づけを解除できるようにする。解除した LINE アカウントは、次の友だち追加かメッセージで、招待コードの入力からオンボーディングをやり直せる。解除済みオーナーの店舗は消さず、毎朝の競合データ取得を続けたまま、LINE への配信だけを止める。新しい担当者（または同じ LINE アカウント）が、同じ代理店の招待コードでオンボーディングを始め、解除済みオーナーの店舗と同じ Place を確定すると、そのオーナーの全店舗と履歴を引き継ぐ。

本機能は `line-onboarding` Requirement 4.4（他のオーナーの店舗として登録済みの Place は確定しない）に例外を加える要件変更である。オーナー自身による配信停止（オプトアウト）を提供しないこと（`competitive-daily-summary` Requirement 3.10）は変えない。

## Boundary Context

- **In scope**:
  - 運営・担当代理店によるオーナー単位の解除と、オーナーごとの連携状態の表示
  - 解除した LINE アカウントに個別に設定した完了後メニューを外すこと、外せなかったときの外し直し
  - 解除した LINE アカウントが、招待コードの入力からオンボーディングをやり直せること
  - 解除済みオーナーの店舗について、取得を続け配信を止めること
  - 同じ Place の確定による、解除済みオーナーの全店舗の引継ぎ
  - 解除と引継ぎの監査記録
  - `line-onboarding` Requirement 4.4 の改訂と、オプトアウトの不在検査との両立
- **Out of scope**:
  - オーナー自身による解除。LINE 上にも Web 上にも設けない
  - ブロック（unfollow）を契機とした自動解除
  - オーナー・店舗・代理店の物理削除
  - 管理ダッシュボードで店舗を別のオーナーへ付け替える操作
  - 解除を取り消す専用の操作（同じ Place の確定し直しで代える）
  - 解除された LINE アカウントへの通知
  - 別の代理店の招待コードで来た LINE アカウントへの引継ぎ
  - 既に店舗特定済みの LINE アカウントによる引継ぎ（オンボーディングに入れないため）
  - 解除・引継ぎを契機とした店舗の停止・再開
- **Adjacent expectations**:
  - 権限の範囲は `agency-dashboard` Requirement 2（代理店は担当範囲のみ・範囲外の要求は UI に関係なく拒否）に従う
  - 店舗の停止状態（`store-suspension`）は解除・引継ぎで変わらない。停止中の店舗は、オーナーの連携状態にかかわらず停止の規則に従う
  - 引継ぎ後の最初の変化通知の判定は、`competitive-daily-summary` の既存の規則に従う
  - 監査記録の書込に失敗したときの扱いは #250 の決定に従う

## Requirements

### Requirement 1: 紐づけの解除の操作
**Objective:** As a 運営・代理店の利用者, I want 担当するオーナーの LINE の紐づけを管理ダッシュボードから解除したい, so that 担当者の交代・誤登録の取り消し・撮り直しのたびに本番データベースを直接書き換えずに済む

#### Acceptance Criteria
1. When 運営の利用者が任意のオーナーの解除を実行したとき, the 管理ダッシュボード shall そのオーナーと LINE アカウントの紐づけを解除する
2. When 代理店の利用者が自代理店のオーナーの解除を実行したとき, the 管理ダッシュボード shall そのオーナーと LINE アカウントの紐づけを解除する
3. If 代理店の利用者が他の代理店のオーナー、または存在しないオーナーの解除を要求したとき, then the 管理ダッシュボード shall 状態を変えずに要求を拒否し、そのオーナーが存在するかどうかを応答から判別できないようにする
4. When 利用者が解除を実行しようとしたとき, the 管理ダッシュボード shall 解除によって元の LINE アカウントへ日次の変化通知が届かなくなり店舗の情報も見られなくなること、店舗とその履歴は残ること、同じ店舗を LINE で確定し直すと引き継げることを示して確認を求め、確認された場合にのみ解除する
5. If 既に解除済みのオーナーに解除を要求したとき, then the 管理ダッシュボード shall 紐づけの状態を変えずに成功として扱う
6. The 管理ダッシュボード shall 解除によってオーナーの店舗、店舗の身元（Place の確定状態）、代理店との関係、蓄積済みの日次データ・匿名集計・監査記録を変更・削除しない
7. If 紐づけの解除が失敗したとき, then the 管理ダッシュボード shall 紐づけを解除前の状態のまま保ち、失敗したことを利用者に示し、成功したかのような表示をしない

### Requirement 2: 連携状態の表示
**Objective:** As a 運営・代理店の利用者, I want オーナーごとに LINE と連携中か解除済みかを見分けたい, so that 解除したオーナーと連携中のオーナーを取り違えずに管理できる

#### Acceptance Criteria
1. The 管理ダッシュボード shall 利用者が閲覧できる範囲のオーナーについて、LINE と連携中か解除済みかを表示する
2. While オーナーが連携中である, the 管理ダッシュボード shall そのオーナーに解除の操作を提供する
3. While オーナーが解除済みである, the 管理ダッシュボード shall そのオーナーを一覧から除かずに表示し、解除の操作を提供しない
4. When 解除が成功したとき, the 管理ダッシュボード shall 画面を再読み込みせずに表示を解除済みの状態へ更新する
5. When 利用者が店舗の登録でオーナーを選ぶとき, the 管理ダッシュボード shall 解除済みのオーナーを連携中のオーナーと区別して表示する
6. While 解除済みのオーナーの店舗がほかのオーナーへ引き継がれている, the 管理ダッシュボード shall そのオーナーについて、店舗を引き継いだオーナーが分かる形で表示する

### Requirement 3: 完了後メニューの解除
**Objective:** As a 運営, I want 解除した LINE アカウントから完了後メニューを外したい, so that 解除した LINE アカウントに、店舗のレポートを求めるメニューが残らない

#### Acceptance Criteria
1. When 紐づけを解除したとき, the 管理ダッシュボード shall 元の LINE アカウントに個別に設定した完了後メニューを外し、未登録の利用者と同じメニューが表示される状態にする
2. If 紐づけの解除は成功したが完了後メニューを外せなかったとき, then the 管理ダッシュボード shall 紐づけの解除を取り消さず、解除は完了したがメニューを外せなかったことを利用者に示す
3. While 解除済みのオーナーについて完了後メニューを外せたことが確かめられていない, the 管理ダッシュボード shall メニューを外し直す操作を提供する
4. When 利用者がメニューを外し直す操作を実行したとき, the 管理ダッシュボード shall 元の LINE アカウントの完了後メニューを外し、紐づけの状態を変えない
5. The fw-line-meo shall 運用の一括の張り直しを含むいかなる経路でも、解除済みのオーナーの元の LINE アカウントへ完了後メニューを設定しない

### Requirement 4: 元の LINE アカウントの扱い
**Objective:** As a 運営, I want 解除した LINE アカウントが最初の状態からオンボーディングをやり直せるようにしたい, so that 撮り直しや担当者の交代で、同じ LINE アカウントを未登録のアカウントと同じように扱える

#### Acceptance Criteria
1. When 解除した LINE アカウントが公式アカウントを友だち追加（ブロック解除を含む）したとき、またはメッセージを送ったとき, the オンボーディングサービス shall 招待コードの入力を求める最初の案内を返す
2. The オンボーディングサービス shall 解除前の会話の進み具合（段階・候補・招待コードの入力失敗の回数）を、解除後の会話へ持ち越さない
3. When 解除した LINE アカウントが店舗詳細画面を開いたとき, the 店舗詳細画面 shall 解除前のオーナーの店舗を表示せず、閲覧できる店舗が無い場合と同じ応答を返す
4. The LINE 応答 shall 解除した LINE アカウントからのレポート要求に、解除前のオーナーの店舗を含めない
5. The fw-line-meo shall 解除済みのオーナーを宛先として、日次の変化通知や解除の通知を含むいかなるメッセージも送信しない

### Requirement 5: 解除済みオーナーの店舗の扱い
**Objective:** As a 運営, I want 解除済みオーナーの店舗のデータ取得を続けたまま配信だけを止めたい, so that 引き継いだ担当者の推移に空白を作らず、宛先の無い配信も行わない

#### Acceptance Criteria
1. While 店舗のオーナーが解除済みで、店舗が停止中でない, the 日次取得処理 shall その店舗を通常どおり取得の対象に含め、日次サマリーを作成する
2. While 店舗のオーナーが解除済みである, the 日次配信処理 shall その店舗について変化通知を送信しない
3. While 店舗のオーナーが解除済みである, the 日次配信処理 shall その店舗について、送信したことも送信に失敗したことも通知記録として残さない
4. If 日次サマリーの作成後から配信時刻までの間にオーナーが解除されたとき, then the 日次配信処理 shall その日の変化通知を送信しない
5. The fw-line-meo shall 解除を理由に、店舗の停止状態、客向けアンケートの受付、QR の発行を変えない

### Requirement 6: 同じ Place の確定による店舗の引継ぎ
**Objective:** As a 新しい担当者（または解除前と同じ LINE アカウントの持ち主）, I want オンボーディングで自店を確定するだけで解除済みオーナーの店舗を引き継ぎたい, so that 担当者の交代・撮り直し・誤登録の取り消しで、店舗の履歴を失わずに LINE での利用を再開できる

#### Acceptance Criteria
1. When オンボーディング中の LINE アカウントが解除済みオーナーの店舗と同じ Place を確定し、その LINE アカウントが招待コードで紐づいた代理店が解除済みオーナーの代理店と同じとき, the オンボーディングサービス shall 解除済みオーナーの全店舗を、その LINE アカウントのオーナーへ引き継ぐ
2. When 店舗を引き継いだとき, the オンボーディングサービス shall 通常の確定と同じく店舗特定済みの状態へ遷移させ、完了の案内と完了後メニューを提供する
3. The オンボーディングサービス shall 引継ぎによって、引き継いだ店舗の身元（Place の確定状態）、停止状態、代理店、蓄積済みの日次データ・匿名集計、発行済みの QR の有効性を変えない
4. If 確定した Place の店舗のオーナーが解除済みでも、オンボーディング中の LINE アカウントの代理店がそのオーナーの代理店と異なるとき, then the オンボーディングサービス shall 確定と引継ぎを行わず、既に登録済みの店舗を選んだ場合と同じ案内を返す
5. If 確定した Place の店舗のオーナーが連携中のとき, then the オンボーディングサービス shall 確定と引継ぎを行わず、既に登録済みの店舗を選んだ場合と同じ案内を返す
6. If 同じ解除済みオーナーの店舗を、複数の LINE アカウントがほぼ同時に確定したとき, then the オンボーディングサービス shall 1 つの LINE アカウントにだけ引き継ぎ、ほかの LINE アカウントには既に登録済みの店舗を選んだ場合と同じ案内を返す
7. When 引継ぎの後に日次配信を行うとき, the 日次配信処理 shall 引き継いだ店舗の変化通知を、引き継いだオーナーの LINE アカウントへ通常の規則に従って送信する
8. When 引き継いだオーナーが店舗詳細画面を開いたとき, the 店舗詳細画面 shall 引き継いだ全店舗を閲覧対象に含める
9. When 引継ぎが完了したとき, the 管理ダッシュボード shall 引き継いだ店舗を新しいオーナーの店舗として表示する
10. The `line-onboarding` 仕様 shall Requirement 4.4 を、解除済みオーナーの店舗を同じ代理店から確定した場合は引継ぎとして扱うことを含めて記述する

### Requirement 7: 解除と引継ぎの監査記録
**Objective:** As a 運営, I want 誰がいつどのオーナーを解除し、どの店舗が誰へ引き継がれたかを残したい, so that 紐づけの経緯を後から確かめ、誤操作や意図しない引継ぎを追跡できる

#### Acceptance Criteria
1. When オーナーの紐づけを解除したとき, the 管理ダッシュボード shall 操作した利用者、その役割、対象オーナー、日時を解除として監査記録に残す
2. When 店舗を引き継いだとき, the オンボーディングサービス shall 引き継いだオーナー、元の解除済みオーナー、引き継いだ店舗、日時を引継ぎとして監査記録に残す
3. If 解除の要求やメニューの外し直しによって紐づけの状態が変わらなかったとき, then the 管理ダッシュボード shall 解除の監査記録を追加しない
4. The fw-line-meo shall 解除と引継ぎの監査記録を、既存の監査記録の種別を失わない形で追加する

### Requirement 8: オーナー自身による解除・配信停止の不在
**Objective:** As a 運営, I want 解除の仕組みを入れても、オーナー自身が配信を止める手段が無いことを保ちたい, so that 既存の要件（オプトアウトを提供しない）を名前や置き場所の違いで崩さずに機能を足せる

#### Acceptance Criteria
1. The fw-line-meo shall オーナー自身が LINE 上でも Web 上でも、紐づけの解除や配信の停止を行う手段を提供しない
2. When オーナーが公式アカウントをブロックまたはブロック解除したとき, the LINE 応答 shall オーナーの紐づけの状態を変更しない
3. The 不在検査 shall 運営・代理店による解除を許容したうえで、オーナー自身による配信停止の手段が加わったことを、その手段がどの画面・どの層・どの名前で加えられても検出する
4. When 不在検査を変更するとき, the 開発者 shall 変更の前後で、オーナー自身による配信停止を加える変異が検出されることを確かめて記録する

### Requirement 9: 本番での効果の確認
**Objective:** As a 運営, I want 本番で解除と引継ぎが実際に効いたことを確かめたい, so that テストが通るだけで効果が出ていない状態を完了と見なさない

#### Acceptance Criteria
1. When 連携状態を保持するための変更を本番へ適用したとき, the 運営 shall 適用が完了していることを本番のデータベースで確認してから解除の操作を行う
2. When 本番で 1 つの LINE アカウントの紐づけを解除したとき, the 運営 shall その LINE アカウントで招待コードの入力を求める最初の案内が出ることと、個別の完了後メニューが外れていることを確認して記録する
3. When 本番で解除した LINE アカウントが同じ Place を確定し直したとき, the 運営 shall 店舗詳細画面に引き継いだ店舗が表示されることを確認して記録する
