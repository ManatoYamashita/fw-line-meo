# Implementation Plan

本計画は `review-acquisition` Requirement 1 の未充足部分（UI 側）を閉じる。サーバ側の QR エンドポイントは実装済みであり、本計画は `dashboard-web` のみを変更する。

**前提は既に満たされている**（ギャップ分析で実測）。Tailwind と `@fwlm/ui` の配線は `globals.css` の 3 点セットで完了し、`ts/packages/ui/test/app-integration.test.ts` が機械検証している。vitest と Testing Library の規約も確立済み。新規の外部依存・新規の `NEXT_PUBLIC_*`・DB 変更・インフラ変更はいずれもゼロ。したがって Foundation 段のタスクを置かない。

`(P)` は直前の同階層タスクと同時実行できることを示す。表示部品と一覧画面はそれぞれ単一ファイルを共有するため `(P)` にできない（各タスクの補足に理由を記す）。

- [ ] 1. Core: 純粋ロジック層

- [ ] 1.1 (P) 保存ファイル名の決定規則を実装する
  - 店名と店舗 ID からファイル名を組み立てる。パス区切り・制御文字・ファイル名として使えない予約文字を除去し、前後の空白と点を落とし、連続空白を畳み込む
  - 店舗 ID の断片を常に付与する。一覧の絞り込み状態や他店舗の存在に依存せず、同名店舗でも一意になるようにする
  - 正規化後に店名部分が空になった場合でも、非空で拡張子を持つ名前を返す
  - 名前部分に長さ上限を設ける。日本語はそのまま残す（人が判別できることが目的のため）
  - Observable: node 環境の単体テストで、店名を含むこと・`.png` で終わること・同一店名で店舗 ID が異なれば別名になること・予約文字が残らないこと・空になる店名でも非空を返すことが緑
  - _Requirements: 2.4, 2.5, 2.6_
  - _Boundary: qr-filename_

- [ ] 1.2 (P) 認証付きで画像を取得する窓口を実装する
  - 既存のトークン取得とエラー封筒の解釈をそのまま再利用し、成功時はバイト列と content type だけを返す。既存メソッドの署名・挙動は変えない
  - 印刷用途に固定したサイズを要求する。利用者にサイズを選ばせない
  - トークンは Authorization ヘッダにのみ載せ、URL・クエリには載せない
  - 2xx でも本文が空の場合は失敗として扱う。サーバが返した `code` を書き換えたり既定値へ丸めたりしない
  - 応答本文を例外メッセージやログへ載せない
  - Observable: node 環境の単体テストで、Authorization ヘッダが付き URL にサイズ指定が含まれ、401・403・404・409 の `code` と文言が保たれ、空応答が失敗として返ることが緑
  - _Requirements: 2.7, 3.3, 4.1, 4.2, 4.3, 4.5, 5.1_
  - _Boundary: api client_

- [ ] 2. Core: QR パネル

- [ ] 2.1 パネルの取得・表示・保存を実装する
  - 対象店舗の画像を 1 回だけ取得し、画面表示と保存の双方へ同一の資源を束ねる。保存時に再取得を発生させない
  - 保存は実際のリンク要素として描画する。プログラムによる click 合成を行わない
  - 表示資源の生成と解放を単一の副作用に閉じ、アンマウントで必ず解放する。永続領域へ書かない
  - 取得中は処理中であることを示し、その間の再入を防ぐ
  - 画像の代替テキストと保存操作の名前に店名を含める。表示する情報を店名と画像に限定する
  - jsdom には表示資源を作る手段が無いため、テストで差し込む（実装側は差し込みのための抽象を作らない）
  - Observable: jsdom テストで、画像と保存リンクが現れ保存名と代替テキストに店名が入り、保存操作で取得が再発行されず、アンマウントで解放が呼ばれることが緑
  - _Requirements: 2.1, 2.2, 2.3, 2.8, 5.2, 5.3, 5.4, 6.4_
  - _Depends: 1.1, 1.2_
  - _Boundary: StoreQrPanel_

- [ ] 2.2 パネルの失敗表現と再試行を実装する
  - サーバの `code` を利用者向けの文言へ写す対応表をパネル内に持つ。窓口側は文言を決めない
  - 権限不足と対象不在を同一の文言にし、担当外店舗の存在を推測させない
  - 場所の未確定・認証切れ・通信障害・未知の失敗をそれぞれ区別して示す
  - 失敗時に再試行の操作を提示する。再試行は一覧の再取得を伴わずパネル内で完結する
  - 処理中・成功・失敗の変化を支援技術へ通知する
  - 2.1 と同一ファイルを編集するため `(P)` にできない
  - Observable: jsdom テストで `code` ごとに文言が切り替わり、権限不足と不在が同一文言になり、再試行で取得が 1 回だけ追加で走ることが緑
  - _Requirements: 3.3, 4.1, 4.2, 4.3, 4.4, 4.5, 6.2_
  - _Boundary: StoreQrPanel_

- [ ] 3. Integration: 店舗一覧への結線

- [ ] 3.1 一覧に発行導線と未確定の理由を追加する
  - 発行のための列を追加する。既存の 4 列とロール別の列分岐を保つ
  - 場所が確定済みの行にのみ発行操作を置く。未確定の行には同じ位置に、場所の確定が先に必要である旨を置く
  - 分岐条件を場所の状態のみとする。競合設定の状態を条件に含めない
  - 発行操作の名前に店名を含める。追加する文言をすべて日本語にする
  - 新しい色指定を持ち込まない。未確定の理由テキストは既存の意味論トークンを用いる
  - Observable: jsdom テストで、確定済み行に店名入りの発行操作があり、未確定行には操作が無く理由が読め、競合未設定の確定済み店舗にも操作が出て、既存 4 列と運営・代理店の列構成が従来どおりであることが緑
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 3.1, 3.2, 5.5, 6.1, 6.3_
  - _Boundary: StoresPage_

- [ ] 3.2 パネルの開閉を一覧へ結線する
  - どの店舗のパネルを開いているかを一覧が持ち、対象行の直下へ挿入する。対応関係が視覚的にも DOM 順でも読み取れるようにする
  - 挿入行の列数をロールから算出する。定数で二重管理しない
  - 別店舗の発行で前のパネルを差し替え、前の状態と資源を引き継がせない
  - 同じ店舗の発行操作を再度押しても取得を再発行しない
  - 失敗しても一覧の表示を維持し、他店舗の発行を妨げない
  - 3.1 と同一ファイルを編集するため `(P)` にできない
  - Observable: jsdom テストで、発行操作でパネルが対象行の直下に現れ、別店舗の発行で差し替わり、同一店舗の再操作で取得回数が増えず、失敗後も一覧が残ることが緑
  - _Requirements: 2.8, 4.4_
  - _Boundary: StoresPage_

- [ ] 4. Validation: 回帰と実機確認

- [ ] 4.1 既存スイートと CI ガードの回帰を確認する
  - `dashboard-web` の型検査・lint・テストを通す。既存 13 本のテストを緑のまま保つ
  - 追加した className を棚卸しし、直書き色・生パレット色・新しい不透明度付きの色指定が無いことを確認する。用いる色は部品の既定 variant と既存の意味論トークンに限る
  - 新しい `NEXT_PUBLIC_*` を増やしていないことを確認する
  - Observable: `dashboard-web` の typecheck・lint・test と `bash scripts/check-design-tokens.sh` と `bash scripts/check-next-public-buildargs.sh` がいずれも緑
  - _Requirements: 6.5_

- [ ] 4.2 実ブラウザで保存と印刷を 1 回確認する
  - 実ブラウザで発行から保存までを操作し、期待したファイル名で保存されることを確認する
  - 保存した画像を一辺 5cm で印刷し、スマートフォンで読み取れることを確認する
  - キーボードのみで発行から保存まで到達できること、焦点が視覚的に判別できることを確認する
  - `dashboard-web` に E2E が無いため（Issue #53）、本項目のみ機械検証の対象外とし、実施結果を記録する
  - Observable: 期待したファイル名での保存・印刷物の読み取り・キーボードのみでの到達の 3 点が確認され、実施記録が残る
  - _Requirements: 2.7, 6.1_
