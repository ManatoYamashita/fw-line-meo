# Implementation Plan

本計画は `review-acquisition` Requirement 1 の未充足部分（UI 側）を閉じる。サーバ側の QR エンドポイントは実装済みであり、本計画は `dashboard-web` のみを変更する。

**前提は既に満たされている**（ギャップ分析で実測）。Tailwind と `@fwlm/ui` の配線は `globals.css` の 3 点セットで完了し、`ts/packages/ui/test/app-integration.test.ts` が機械検証している。vitest と Testing Library の規約も確立済み。新規の外部依存・新規の `NEXT_PUBLIC_*`・DB 変更・インフラ変更はいずれもゼロ。したがって Foundation 段のタスクを置かない。

`(P)` は直前の同階層タスクと同時実行できることを示す。表示部品と一覧画面はそれぞれ単一ファイルを共有するため `(P)` にできない（各タスクの補足に理由を記す）。

## 4.2 の実施手順

**確認の前提**（3 点がそろっている必要がある）:

1. `dashboard-api` が動いていること
2. Firebase 認証で operator または agency としてログインできること
3. `place_status = 'confirmed'` の店舗が 1 件以上あること

**経路 A（推奨・手数が最少）**: マージ後にデプロイされた `dashboard-web` で確認する。
`dashboard-api` の CORS は単一オリジンのみ許可するため、ローカルの `next dev`（既定 `localhost:3000`）
から本番 API は叩けない。デプロイ済みの面で確認するのが最も少ない手数で前提 3 点を満たす。

**経路 B（ローカル一式）**: `make db-dev-setup` で `fwlm_dev` を用意し
（`ts/apps/survey-web/e2e/seed.sql` が `place_status` 付きの店舗を投入する）、`dashboard-api` を
ビルドして起動する（**`dev` スクリプトは無い**。`build` の出力を直接起動する）。そのうえで
`pnpm -C ts --filter @fwlm/dashboard-web dev` を叩く。Firebase は実プロジェクトの資格情報を使う。

`dashboard-api` は起動時に必須 env を検証して落ちる（`config.ts` の `loadConfig`）。CORS の許可元は
`DASHBOARD_WEB_ORIGIN` であり、**`CORS_ORIGIN` という名前は存在しない**。

|---|---|---|

### 実施記録（2026-08-21・確認項目 2 の機械検証部分のみ）

確認項目 2（印刷解像度・Requirement 2.7）のうち、**物理的な印刷と読み取りを除く部分を機械で検証した**。
`dashboard-api` と同一の生成条件（`QRCode.toBuffer(url, { width: 1024, margin: 1 })`・`index.ts:112`）を
再現し、生成物を **Apple Core Image**（生成側とは独立した実装）で復号した。

| URL 長 | QR 版 | モジュール数（静穏帯込み） | 5cm 印刷時のモジュール寸法 | 復号 |
|---|---|---|---|---|
| 59 | 4 | 35 | 1.429 mm | 期待どおりの URL |
| 68 | 5 | 39 | 1.282 mm | 期待どおりの URL |
| 94 | 6 | 43 | 1.163 mm | 期待どおりの URL |

- 1024 px を 5cm に印刷すると **約 520 dpi 相当**で、一般的な家庭用・事務用プリンタ（300 dpi）の
  能力が先に上限になる。元画像が制約になることはない
- 段階的に縮小して復号限界を測ると、**1.5 px/モジュールまで成功**し 1.0 px/モジュールで失敗した。
  実機のスマートフォンが 5cm の QR を捉えるときは 20 px/モジュール前後になるため、余裕は 1 桁大きい
- `margin: 1` は QR 規格が求める静穏帯 4 モジュールより狭いが、**外周を黒で塗った条件でも
  2.39 px/モジュールまで復号でき**、静穏帯 4 モジュール版と差が出なかった。実用上の危険は無い

## Implementation Notes

- `ts/packages/ui/test/app-integration.test.ts` は `bg-primary` / `bg-card` / `field-sizing-content` /
  `animate-spin` の 4 語が**アプリ自身のソースに出現しないこと**を帰属プローブに使う。この 4 語を
  `ts/apps/*/` に literal で書くと、自分のアプリではなく ui パッケージのテストが落ちる
- `test/stores-page.test.tsx` の api モックはモジュール全体を差し替える。窓口を増やしたら
  hoisted オブジェクトへ足すこと。忘れると新機能ではなく既存テストが道連れで落ちる
- Base UI の `Button` に `render` ＋ `nativeButton={false}` を渡すと描画先へ `role="button"` が付く。
  `<a download>` のように要素の種類そのものに意味がある場合は使わず、`buttonVariants()` で
  class だけを借りる
- `@fwlm/ui` の `Spinner` は自前で `role="status"` を持つ。外側にライブリージョンを置くなら
  `aria-hidden` を付けて二重読み上げを避ける
- `Alert` は variant で role が決まる（`destructive` → `alert` / `default`・`success` → `status`）
- 一覧から個別対象を操作する UI では、表示由来の値（見出しの店名など）だけで対象を検証しない。
  取得側の引数を必ず固定する。表示と取得が別々の店舗を指していてもテストが緑になる
- `aria-label` に助詞を挟むと WCAG 2.5.3 Label in Name を破る（「QR を発行」に「QR 発行」は
  含まれない）。見えている文言は読み上げ名の部分文字列でなければならない
- `dashboard-web` には `react-hooks/exhaustive-deps` が無い。effect の依存配列は誰も検査しない
- TypeScript 5.7 以降、既定の `Uint8Array<ArrayBufferLike>` は `BlobPart` にも `BodyInit` にも
  載らない。`res.arrayBuffer()` 由来の実体は非共有なので `Uint8Array<ArrayBuffer>` へ狭める
- 条件描画で消える対話的要素は、**消える側に焦点があった場合の受け皿を先に決める**。要素が DOM
  から外れるとブラウザは焦点を `body` へ移し、焦点指標が消える。「閉じる」だけを直して「再試行」に
  同じ穴を残したのが PR #142 のレビュー指摘だった
- Base UI の `Button` は `disabled` と `focusableWhenDisabled` を併せて渡すと、native の `disabled`
  属性を付けずに `aria-disabled` と `data-disabled` だけを与え、`tabIndex` を保つ。押下は primitive
  側の `onClick` が `preventDefault` で止めるため、再入抑止のガードを呼び出し側へ書かなくてよい。
  ただし `buttonVariants` の減光は native の `:disabled` 擬似クラスに掛かっており**発火しない**ので、
  `data-[disabled]:` 側で与える必要がある
- **jsdom は「`disabled` になった要素から焦点が外れる」挙動を再現しない。** そのため
  `focusableWhenDisabled` の欠落は焦点のテストでは捕まらず、`aria-disabled` / `data-disabled` の
  存在を直接固定するテストだけが検出できる（ミューテーションで実測済み）
