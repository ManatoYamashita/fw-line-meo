# Implementation Plan

- [ ] 1. 基盤: 正典・共有パッケージ・依存宣言

- [x] 1.1 項目名の正典を作る
  - 現存する 6 実行面の事象名と項目名をすべて棚卸しし、意味・応答層での名前・日次バッチ層での名前・由来・出典・備考を持つ表に落とす
  - **移送後の姿で書く**。現在は事象名を持たない実行面の事象名、移送で新しく生まれる項目名（対象を特定できない記録へ足す識別子など）、握り潰されている補助的処理の成功・失敗の対を、この段階ですべて決めて登録する。出典列は移送後の位置を書く
  - 該当のない欄は空欄にせず「該当なし」を明示的に宣言する。棚卸しの漏れが「行が無い」という不可視の形にならないようにするため
  - 変更できない行には、それを参照している下流（稼働中の集計指標／既存 spec の要求仕様）を備考に記録する
  - 相関識別子と、外部プラットフォームが付与するリクエスト識別子を別々の行として登録する
  - 正典を先に確定させることで、後続の移送タスクは正典を書き換えずに済み、互いに並行して進められる
  - 完了状態: 表を読むだけで「ある意味の情報が、どの実行面でどの名前になるか」と「その名前を変えられるか」が判定でき、移送で新しく生まれる事象名と項目名もすべて載っている
  - _Requirements: 4.1, 4.2, 4.5, 6.1, 6.2, 6.5_

- [x] 1.2 共有パッケージの器を用意する
  - 応答層の各面から利用でき、ビルド成果物を持つ形式で新しい共有パッケージを追加する
  - 型検査の実行口を必ず備える。既存の検査基盤は workspace の定義から対象を自動列挙するため、実行口が無いと検査が失敗する
  - 外部の実行時依存を追加しない
  - 完了状態: パッケージ単体でビルド・型検査・テストが通り、既存の一括実行コマンドがこのパッケージを含めて成功する
  - _Requirements: 7.1_

- [x] 1.3 記録してよい項目の型を定義する
  - 記録に載せてよい項目の集合を単一の場所で定義する。来店客の入力・生成物・オーナーを一意に識別する値は型として持たない
  - **正典に載る項目を、新規に生まれる行を含めてすべて登録する**。6 実行面が現に出している項目（診断の種別・状態コード・店舗識別子・外部プラットフォームのリクエスト識別子・配信ジョブの実行サマリーの業務項目など）に加え、移送で新設する識別子も含める。出力側は明示的な取り出ししか行わないため、登録し忘れた項目は移送した瞬間に黙って消える
  - 例外は自由文ではなく、種別と状態コードだけを持つ記述子として表現する
  - 相関識別子を受け入れる項目を用意する。この時点では値が入らなくてよい
  - 出力側が取り出す鍵の集合と型の鍵の集合が一致することを型で表明する。表明の基準は名前付きの型ではなく出力関数の実引数位置から導く
  - 後続の移送タスクが許可集合へ追記せずに済む状態にすることで、移送タスク同士の競合を無くす
  - 完了状態: 出力側の取り出しを 1 つ削ると型検査が失敗し、かつ正典に載るすべての項目が型に存在する
  - _Requirements: 1.4, 2.3, 2.4, 2.5, 2.6, 5.1, 5.3, 7.2_

- [x] 1.4 記録を書き出す経路を実装する
  - 渡された値を展開せず、許可された項目を 1 つずつ明示的に取り出して 1 行で書く
  - 重大度を集約基盤が解釈する項目名で出す。相関識別子は値が与えられていなければ項目ごと出さない
  - 集約基盤が本文として特別扱いする名前を項目名に使わない
  - いかなる入力に対しても例外を投げない。記録の出力が失敗しても呼び出し側へ伝播させない
  - 事象名を省略できない引数にする
  - 完了状態: 型を迂回して許可外の項目を渡しても、出力文字列の完全一致比較で許可項目のみが現れることをテストが示し、かつ出力先を失敗させても呼び出し側が正常に完了する
  - _Requirements: 1.1, 1.2, 1.3, 1.5, 2.1, 2.2, 3.2, 3.3, 5.2_

- [x] 1.5 共有パッケージを各実行面の依存として宣言する
  - 記録を出す応答層 5 面それぞれに、共有パッケージへの依存を宣言し、固定された依存関係の記録を更新する
  - 各面のコンテナ定義への追記は、その面を移送するタスクが自面分を負う。コンテナ定義は面ごとに独立しているため、まとめて持つ必要がない
  - 完了状態: 5 面それぞれから共有パッケージの型が解決でき、workspace 全体の型検査とビルドが通る
  - _Requirements: 7.1_

- [ ] 2. 検査の新設と赤の実測

- [x] 2.1 (P) 正典自身の構造を検証する仕組みを作る
  - 正典だけを読み、各行が必要な列をすべて持ち、該当なしが明示的に宣言されていることを確かめる
  - 新規に由来する項目が、実行面ごとに異なる名前で登録されていないことを確かめる
  - 相関識別子の行が正典から失われていないことを確かめる
  - 走査対象が 0 件・抽出が 0 件のときは失敗とする
  - 検査自身の自己テストを既存の流儀で追加し、相関識別子の行を削る・新規項目を実行面ごとに別名にする、の 2 通りで失敗することを実証する
  - 完了状態: 正典を意図的に壊すと失敗し、整った正典に対しては成功する
  - _Requirements: 4.5, 4.6, 5.4, 7.3_
  - _Boundary: GuardCanon_

- [x] 2.2 (P) 正典と実装を突き合わせる仕組みを作る
  - 正典の各行の出典が実在し、その出典に当該の項目名が現れることを確かめる
  - 実装に現れる項目名がすべて正典に登録されていることを、逆方向にも確かめる
  - 走査対象が 0 件・抽出が 0 件のときは失敗とする
  - 検査自身の自己テストを追加し、出典を実在しない場所へ変える・実装にだけ項目名を足す、の 2 通りで失敗すること、および正典と実装が揃った状態では成功することを実証する
  - 完了状態: 移送が済んでいない段階では失敗して移送対象の一覧になり、移送完了後には成功する
  - _Requirements: 4.3, 4.4, 6.3, 7.3_
  - _Boundary: GuardBinding_

- [x] 2.3 (P) 共有経路を通らない出力を検出する仕組みを作る
  - 応答層の**実行時ソース**から、共有経路を経由しない書き出しを検出する
  - 走査対象を実行時ソースに限る。運用者が手で叩く補助スクリプトの人間向け出力・テスト・ビルド成果物は記録ではないため対象外とする。この範囲を定義せずに走らせると、移送を終えても消えない赤が残る
  - オーナーを一意に識別する値が記録経路へ渡っていないことも同じ検査で見る。外部プラットフォームが付与するリクエスト識別子はこれに当たらず、記録し続けてよい
  - 走査対象が 0 件・抽出が 0 件のときは失敗とする
  - 検査自身の自己テストを追加し、実行時ソースへ逸脱を 1 箇所加えると失敗すること、および対象外と定めた場所の出力では失敗しないことを実証する
  - 完了状態: 移送前の実行面に対して失敗し、対象外と定めた場所の既存の出力では失敗しない
  - _Requirements: 2.4, 7.1, 7.3_
  - _Boundary: GuardUsage_

- [ ] 3. 実行面の移送

- [x] 3.1 (P) アンケート面の記録を共有経路へ移す
  - 既存の許可制の出力を共有パッケージのものへ差し替える。面に固有の事象ごとのヘルパは面に残す
  - 自面のコンテナ定義に、依存解決とビルドの 2 段を追記する。**standalone 形式で出力する面のため実行時配置の段は不要**であり、共有パッケージを写す行を足すと存在しないパスの複写になってビルドが落ちる
  - 事象名と項目名を移送前と同一に保つ。稼働中の集計指標がこの文字列を参照している
  - **重大度の項目名だけは例外**として変わる。集約基盤が解釈する名前へ改めるためであり、稼働中の集計指標は重大度を参照していないため安全である
  - 完了状態: 移送前後で事象名と業務項目の集合が変わらず重大度だけが集約基盤の解釈する名前で現れること。コンテナイメージのビルドは手元に実行環境が無いため、提出後の検証ジョブで確かめる
  - _Requirements: 1.1, 1.2, 6.1, 6.2, 6.5_
  - _Boundary: survey-web_
  - _Depends: 1.4, 1.5_

- [x] 3.2 (P) 店舗詳細面の記録を共有経路へ移す
  - 自前の組み立てを共有経路へ差し替え、自面のコンテナ定義に依存解決とビルドの 2 段を追記する（standalone 形式で出力する面のため実行時配置の段は不要）
  - 例外本文を載せている箇所を、種別と状態コードに置き換える
  - 事象名を移送前と同一に保つ
  - 完了状態: 例外の記録に自由文が含まれず種別で原因を切り分けられること。コンテナイメージのビルドは手元に実行環境が無いため、提出後の検証ジョブで確かめる
  - _Requirements: 2.5, 6.1, 6.5_
  - _Boundary: store-detail_
  - _Depends: 1.4, 1.5_

- [x] 3.3 (P) 配信ジョブの記録を共有経路へ移す
  - 自前の組み立てを共有経路へ差し替え、例外本文を種別と状態コードに置き換え、自面のコンテナ定義に依存解決・ビルド・実行時配置の 3 段を追記する（Node を直接実行する面のため 3 段すべてが要る）
  - 集約基盤が本文として特別扱いする名前で出している項目を別名へ改める。この項目は現状すでに項目検索から消えている
  - 実行サマリーの業務項目と事象名を保つ。既存のテストは関数の返り値を項目ごとに検証しており出力の完全一致ではないため、重大度の追加はテストを壊さない
  - 完了状態: 実行サマリーの業務項目と事象名が移送前と同一で本文として吸われる名前の項目が出力に残っておらず。コンテナイメージのビルドは手元に実行環境が無いため、提出後の検証ジョブで確かめる
  - _Requirements: 2.5, 6.1, 6.2, 6.5_
  - _Boundary: delivery-job_
  - _Depends: 1.4, 1.5_

- [ ] 3.4 (P) 受信面の記録を共有経路へ移す
  - 事象名を持たない出力に、正典が定める事象名を与えて共有経路へ載せ、自面のコンテナ定義に依存解決・ビルド・実行時配置の 3 段を追記する（Node を直接実行する面のため 3 段すべてが要る）
  - 例外本文を種別と状態コードに置き換える
  - 外部プラットフォームが付与するリクエスト識別子は、正典に登録した項目名で引き続き記録する
  - 完了状態: 出力が項目単位で絞り込める形式になり正典が定める事象名で該当の記録を引けること。コンテナイメージのビルドは手元に実行環境が無いため、提出後の検証ジョブで確かめる
  - _Requirements: 1.1, 1.2, 2.5, 6.5_
  - _Boundary: line-webhook_
  - _Depends: 1.4, 1.5_

- [x] 3.5 (P) ダッシュボード API の記録を共有経路へ移す
  - 事象名を持たない箇所に、正典が定める事象名を与え、自面のコンテナ定義に依存解決・ビルド・実行時配置の 3 段を追記する（Node を直接実行する面のため 3 段すべてが要る）
  - 識別子を 1 つも残していない箇所に、正典が定める識別子を与える
  - 完了状態: 失敗した記録からどの対象に対する操作が失敗したかを判定でき。コンテナイメージのビルドは手元に実行環境が無いため、提出後の検証ジョブで確かめる
  - _Requirements: 1.1, 1.2, 1.4, 6.5_
  - _Boundary: dashboard-api_
  - _Depends: 1.4, 1.5_

- [x] 3.6 (P) 日次バッチ層の重大度を集約基盤が解釈する形式にする
  - 標準のログ機構の属性置換の仕組みで、重大度の項目名を正典が定める名前へ差し替える
  - 業務上のメッセージと属性には一切手を入れない。実行サマリーの属性は既存 spec が要求仕様として名指ししている
  - 完了状態: 出力に重大度が正典の項目名で現れ、実行サマリーの属性集合が変わらないことをテストが示す
  - _Requirements: 1.3, 4.2, 4.4, 6.4_
  - _Boundary: BatchLogging_
  - _Depends: 1.1_

- [ ] 4. 補助的処理の成否を記録する（統合）
  - 会話処理の依存注入へ記録の手段を足す。注入の口は受信面の合成ルートにあるため、**この作業は会話処理の内側だけでは完結せず、受信面の組み立てにも触れる**
  - 完了メニューへの切り替えについて、成功と失敗を区別できる事象名でそれぞれ記録する。失敗のみを記録すると「記録が無い」が成功と未実行のどちらを意味するか判定できない
  - 記録を足しても業務処理の継続と利用者に見える振る舞いを変えない
  - 完了状態: 補助的処理が成功した場合と失敗した場合で、それぞれ 1 件ずつ区別できる記録が出ることをテストが示す
  - _Requirements: 3.1, 3.3, 3.4_
  - _Boundary: ConversationLogging, line-webhook_
  - _Depends: 1.4, 1.5, 3.4_

- [ ] 5. 統合と検証

- [ ] 5.1 監視設定の陳腐化した注意書きを掃討する
  - 監視設定に残る「アプリは重大度を集約側の名前で出していないので重大度で絞るな」という趣旨の注意書きは、応答層の移送と日次バッチ層の是正が着地した時点で虚偽になる
  - 該当箇所を、現在の出力形式に合った記述へ改める。記述を残したままにすると、後任が「重大度では絞れない」と誤って読む
  - 完了状態: 監視設定の記述が実際の出力形式と一致し、重大度による絞り込みが可能であることが読み取れる
  - _Requirements: 1.3_
  - _Depends: 3.1, 3.2, 3.3, 3.4, 3.5, 3.6_

- [ ] 5.2 移送の非後退を検証する
  - 稼働中の集計指標が参照する事象名と項目名が、移送後も同一であることを確かめる。基準は正典の該当行である
  - 移送前に記録されていた事象が、移送後もすべて記録され続けていることを確かめる
  - 完了状態: 上記 2 点がテストとして残り、以後の変更で退行したら失敗する
  - _Requirements: 6.1, 6.2, 6.5_
  - _Depends: 1.1, 3.1, 3.2, 3.3, 3.4, 3.5_

- [ ] 5.3 検査を継続的実行へ登録する
  - 新設した検査 3 本を、実行時依存を持たない走査群の位置へ登録する
  - 登録は移送の完了後に行う。移送の途中で登録すると、提出のたびに赤が出続け本物の異常と区別できなくなる
  - 完了状態: 変更の提出ごとに検査 3 本が実行され、緑になる
  - _Requirements: 7.4_
  - _Depends: 2.1, 2.2, 2.3, 3.6, 4, 5.1, 5.2_
