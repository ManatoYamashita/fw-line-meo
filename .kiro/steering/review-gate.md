# Review Gate

main へのマージは、CI が成功していることだけでは完了としない。CI と実装者が追加したガードは同じ前提を共有しており、カスケード・実行時解決・ガード自身の空振りのような欠陥を見逃すことがあるためである。

## マージ前の必須手順

PR のマージ前に、実装者の通常確認とは別の観点で独立検証を実施する。Kiro の仕様に紐づく変更では、次の順で実行する。

1. `/kiro-review` で、実装差分を仕様・受入条件・設計判断とは別の観点から批判的に確認する。
2. `/kiro-verify-completion` で、完了条件・テスト結果・成果物の実在を新しい証拠で確認する。
3. 指摘、検証範囲、未検証の軸、残るリスクを PR 本文へ記録する。

Kiro の仕様に紐づかない変更でも、同等の独立検証を省略してはならない。実施者が単独の場合は、検証者を増やせないことを理由にせず、通常の実装確認とは異なる手順・観点・証拠を用意する。

## 検証の最低限の観点

- UI・CSS変更は、ソースのクラス集合だけでなく、実際の描画結果を確認する。`color-mix()`、継承、レイヤ順序、子要素の自前スタイルなど実行時に値が解決される変更は、実ブラウザの計測を優先する。
- 新しいガードは、修正前のコードに対して意図どおり失敗することを確認してから修正を適用する。ガードが見ていない軸（色相、実描画、到達性など）を明記する。
- 受入条件は、満たしたものだけでなく、満たさず持ち越すものもPRに記録する。
- CIの必須チェックが緑であることを確認する。ただし、CIの緑を独立検証の代替にしない。

## PRへの記録

`.github/PULL_REQUEST_TEMPLATE.md` のチェック項目を埋め、独立検証の結果と残るリスクをレビュー可能な証拠として残す。実装後にテンプレートの項目を変更する場合は、この文書と受入条件の対応も同時に見直す。
