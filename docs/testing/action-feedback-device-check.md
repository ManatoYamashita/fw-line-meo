## 1. 準備

### 1-1. 確認する場所を選ぶ

本番を変えずに確かめられる場所と、本番でしか確かめられないものがある。

| 確認する場所 | 使えるもの | 本番への影響 | 決まっていること |
|---|---|---|---|
| A. ローカルの確認環境に携帯から接続する | 店舗設定 7 操作（LIFF はスタブ）・客向けの legacy と structured の両方・下書きの生成失敗 | なし | `docs/testing/structured-survey-local-preview.md` の手順をそのまま使う（下の 1-2） |
| B. 本番の検証用店舗（客向け） | 客向けの legacy のアンケート・下書き・再生成・コピー | 回答 1 件が匿名集計に加算される（取り消せない） | `docs/testing/e2e.md` の 4-1・4-2 と同じ扱い。実クライアントの店舗では試さない |
| C. 本番の検証用店舗（店舗設定・実 LIFF） | 実の LINE と LIFF での店舗設定 7 操作 | 検証用店舗のアンケート設定と監査ログ（`audit_logs`）が変わる | 承認が要る（下の 1-4 の D1）。承認が無い間は実施しない |

A で確かめられないのは、実 LIFF（`liff.init`・ID トークン）と、HTTPS でしか動かない Clipboard の成功の経路である。後者は B で確かめる。

### 1-2. A: ローカルの確認環境を携帯から開く

`docs/testing/structured-survey-local-preview.md` の 1.〜4. で DB・seed・ビルド・3 つのプロセスを用意する。差し替え口は E2E と同じ 2 つ（`E2E_STUB_IDP=1` の LIFF スタブと、ローカルの偽の ID トークン検証サーバー）で、本番の設定では効かない。

携帯から開くために、次だけを変える。

1. PC と携帯を同じ Wi-Fi につなぎ、PC の LAN 内の IP アドレスを調べる（Windows なら `ipconfig` の「IPv4 アドレス」）。以下 `<PC>` と書く。
2. (B) 店舗詳細と (C) 客向けアンケートを、全インターフェイスで待ち受けるよう起動する。`next start` の既定の待ち受けも全インターフェイスだが、明示する。

   ```bash
   # (B) の末尾を次に置き換える
   ... PORT=3121 pnpm -C ts --filter @fwlm/store-detail start -H 0.0.0.0
   # (C) の末尾を次に置き換える
   ... PORT=3100 pnpm -C ts --filter @fwlm/survey-web start -H 0.0.0.0
   ```

3. Windows のファイアウォールが 3121・3100 の受信を止めるときは、確認の間だけプライベートネットワークで許可する。終わったら戻す。
4. 携帯で次を開く。

| 画面 | URL |
|---|---|
| 店舗設定（legacy の店舗） | `http://<PC>:3121/store/survey-settings?storeId=44444444-4444-4444-4444-444444444444` |
| 店舗設定（structured の店舗） | `http://<PC>:3121/store/survey-settings?storeId=55555555-5555-4555-8555-555555555555` |
| 客向け（legacy） | `http://<PC>:3100/s/44444444-4444-4444-4444-444444444444` |
| 客向け（structured） | `http://<PC>:3100/s/55555555-5555-4555-8555-555555555555` |

注意:

- A は `http://` で開くので、ブラウザは Clipboard API を出さない（安全なコンテキストではない）。A で「コピーして投稿する」を押すと、必ず手動コピーへの復帰（失敗の経路）になる。これは A での期待どおりの結果であり、不具合と記録しない。成功の経路は B で確かめる。
- LINE 内ブラウザの描画だけを見たいときは、A の URL を自分宛ての LINE のトークに貼って開く。実 LIFF ではない（LIFF はスタブのまま）。
- 確認が終わったら、`structured-survey-local-preview.md` の 6. のとおり店舗詳細を通常のビルドへ戻す。

### 1-3. structured_enabled の扱い

`store_survey_configs.structured_enabled` を変える操作は、店舗オーナーの画面にも dashboard-api にも無い（`db/write-boundary.md`）。

- A では `ts/apps/survey-web/e2e/structured-seed.sql` が 55555555-… の店舗だけを有効にする。legacy の 44444444-… の店舗は無効のままで、店舗設定の画面の上部に次の案内が出る。

  > ここで登録した料理名・ドリンク名は、新しいアンケートの準備ができしだいお客様の画面に表示されます。今お客様が使っているアンケートは変わりません。

- 本番では有効な店舗が 0 件である（`infra/README.md` の確認の SQL）。本番で structured の客向け画面を確かめる手順はリポジトリに無い。行うには承認が要る（1-4 の D2）。

### 1-4. 承認が要る事項

次の 3 つは、本番の状態を変えるか外部のサービスを使うので、実施の前に承認が要る。承認した人と日付を 8-1 の記録に残す。

| # | 承認が要ること | 承認が無い間の扱い |
|---|---|---|
| D1 | 本番の検証用店舗で店舗設定を操作してよいか（C）。追加した料理名は削除できず、非表示にしかできない。操作は `audit_logs` に残る。structured_enabled が false の間は客の画面は変わらない | 実 LIFF の確認は未実施と記録する。店舗設定の操作は A で確かめる |
| D2 | 本番で structured の客向け画面を確かめるか。確かめるなら、検証用店舗の structured_enabled を誰がどの手順で変え、いつ戻すか | structured の客向け画面は A でだけ確かめる |
| D3 | A で HTTPS のトンネル（外部のサービス）を使い、Clipboard の成功の経路と structured の画面を同時に確かめてよいか | 使わない。コピーの成功の経路は B の legacy で確かめる |

C は D1 の承認を得てから行う。入口は `docs/testing/e2e.md` の 4-3 と同じで、検証用オーナーの LINE でリッチメニューの「詳細を見る」から店舗詳細を開き、「アンケート設定」を押す。名前は実在の料理名を避け、検証と分かる名前（例: `検証用料理A`）にする。終わったら追加した項目を非表示にし、予約・来店の表示を元に戻す。

### 1-5. 失敗と遅延を起こす方法

| 起こしたいこと | 方法 | 使える場所 |
|---|---|---|
| 通信失敗 | 画面を開いた後に機内モードにする（A では Wi-Fi を切る）。押した後に戻す | A・B・C |
| API のエラー（店舗設定） | 表示中の料理名と同じ名前を「料理名を追加」に入れる（409・`同じ名前がすでに表示されています。別の名前にしてください。`） | A・C |
| 入力の検証で止める（店舗設定） | 空欄のまま「追加する」、または 41 文字以上、または「絶品」などの評価の言葉を含む名前 | A・C |
| 入力の検証で止める（客向け） | 星を選ばずに送信する | A・B |
| 下書きの生成失敗（HTTP 200・`generation: 'failed'`） | A の (C) を、Gemini のモック（`NODE_OPTIONS`）を外し、`GEMINI_API_KEY` をダミーのままにして起動し直す。Google へは無効な鍵の要求が出るだけで課金は無い | A のみ |
| 遅延（8 秒以上） | iOS: 設定 > デベロッパ > Network Link Conditioner（デベロッパモードが要る）で「Very Bad Network」。Android: PC の Chrome の `chrome://inspect` から実機のタブを開き、DevTools の Network の速度制限を使う | A・B・C |
| Clipboard の失敗 | A で押す（1-2 の注意のとおり必ず失敗する）。B では、iOS で失敗させる確実な方法は確認していない | A |

遅延を起こせなかった端末では、8 秒後の案内の項目を「未実施（遅延を起こせない）」と記録する。実施していない項目を合格にしない。

## 2. 端末の設定

1 回の確認で設定を 1 つずつ切り替える。複数を同時に変えると、どの設定で崩れたか分からなくなる。

| 設定 | iOS | Android |
|---|---|---|
| 動き低減 | 設定 > アクセシビリティ > 動作 > 視差効果を減らす | 設定 > ユーザー補助 > 色と動き > アニメーションを削除（機種により名称が違う） |
| 読み上げ | 設定 > アクセシビリティ > VoiceOver | 設定 > ユーザー補助 > TalkBack |
| 200% ズーム | Safari のアドレス欄の「ぁあ」（ページ設定）で 200% | Chrome の 設定 > ユーザー補助 > ページのズーム（または文字の拡大縮小）で 200% |
| キーボード | Bluetooth キーボードをつなぐ。設定 > アクセシビリティ > キーボード > フルキーボードアクセス | Bluetooth キーボードをつなぐ |
| 狭い幅 | 画面幅が最も狭い端末を使う（iPhone SE など）。320px ちょうどは自動層が確かめている | 同左 |

## 3. 共通の期待結果

各操作で、次の 1〜6 を確かめる。文言はコードから写したもので、句点の有無まで画面と一致すること。`{名前}` は操作した料理名・ドリンク名が入る。「予約・来店」「40文字」「10件」は、コードがカテゴリ名・上限の値を差し込んだ結果を書いている。

1. 押した直後に、押したボタン（カテゴリの表示設定は選択肢の直下）が Spinner と処理中の文言に変わり、押せなくなる。2 回目の押下で要求が二重に送られない。
2. 動き低減の設定では Spinner が回らない。それでも処理中の文言が文字で読める。
3. 押してから 8 秒を過ぎても終わらないときは、処理継続中の案内に変わる（店舗設定: `保存に時間がかかっています。画面を閉じずにこのままお待ちください。`／客向け: `少し時間がかかっています。画面を閉じずにこのままお待ちください`）。
4. 終わったら、Toast が画面の右下（狭い画面では下端いっぱい）に 1 回だけ出る。成功は緑の印、失敗は赤の印。約 6 秒で消え、「通知を閉じる」でも閉じられる。Toast の領域の読み上げ名は「操作結果の通知」。
5. Toast が出ている間も、画面のほかのボタン・入力欄が押せる（Toast に覆われて押せない要素があれば記録する）。
6. 読み上げでは、処理中の文言が 1 回、結果が 1 回だけ読まれる。同じ結果の文が Toast と画面内の案内の両方から 2 回読まれたら不合格とする。

| 成功 | 成功 `口コミ文を作成しました。` | 下書きの画面（「コピーして投稿する」「別の文章を生成（残り3回）」「Google のクチコミを書く」）へ切り替わる。Toast は切り替えの後も残る |
| structured で下書きを作らない回答 | 成功 `回答を送信しました。` | 回答済みの画面（`{店名}へのご回答ありがとうございました。` と「Google のクチコミを書く」） |
| 下書きの生成失敗（A のみ） | 失敗 `下書きの生成に失敗しました。もう一度生成するか、そのまま投稿画面へお進みください。` | 画面内に `下書きの生成に失敗しました。再試行するか、そのまま投稿画面へお進みください。`、「もう一度生成する」「Google のクチコミを書く」が出る。成功の Toast は出ない |
| 通信失敗 | 失敗 `通信に失敗しました。入力内容は残っています。時間をおいて再度お試しください。` | 回答の画面のまま、同じ文が上部に残る。星・選んだ観点・一言が残っていて、そのまま送り直せる |
| 星を選ばずに送信 | 失敗 `満足度を選択してください。` | 要求を送らない。星の下に `満足度を選択してください` が残る |

B で行うときは、匿名集計に加算されるのは最初の送信 1 件だけになるよう、送信は 1 回にとどめる（`docs/testing/e2e.md` の 4-2 の 4）。通信失敗の確認は、送信が届かないので加算されない。

### 5-2. 再生成

下書きの画面で「別の文章を生成（残りN回）」を押す。下書きを手で 1 文字直してから押すと、失敗のときに編集が残ることも確かめられる。

| 結果 | 処理中 | Toast | 画面 |
|---|---|---|---|
| 成功 | ボタン `別の文章を作成しています…`、下に `回答内容をもとに文章を作成しています`。「コピーして投稿する」も押せない | 成功 `別の口コミ文を作成しました。` | 新しい下書きに置き換わり、残り回数が 1 減る |
| 生成失敗（A のみ） | 同上 | 失敗 `別の文章を作成できませんでした。今の文章はそのまま編集・コピーできます。` | 手で直した文章が残り、コピー・再生成・投稿導線が使える |
| 通信失敗 | 同上 | 失敗 `通信に失敗しました。文章は残っています。時間をおいて再度お試しください。` | 同じ文が上部に残る。文章が残る |

再生成は匿名集計に加算されない（B でも回数の上限まで試してよい）。

### 5-3. コピー

「コピーして投稿する」を押す。

| 結果 | 処理中 | Toast | 画面 |
|---|---|---|---|
| 成功（B・HTTPS） | ボタン `コピー中…`、下に `文章をコピーしています`（一瞬で終わることが多い） | 成功 `コピーしました。投稿画面に貼り付けてください。`（Toast はコピーが終わった後に出る） | 同じ文の案内が残る。メモ帳などに貼り付けて、表示中の文章（手で直した分を含む）と一致することを確かめる |
| 失敗（A・HTTP） | 同上 | 失敗 `自動コピーできませんでした。文章を選択して手動でコピーしてください。` | `自動コピーできませんでした。上の文章を選択して手動でコピーしてください。` が残り、下書きの欄にフォーカスが移って全文が選択される。そこから手動でコピーできる |

iOS Safari では、押した操作の中で `writeText` を呼ぶ流れになっている（`draft-panel.tsx` の `handleCopy`）。iOS Safari で成功の Toast が出て、貼り付けた内容が一致すれば、この流れが実機で効いている。許可のダイアログが出た場合は、その文言と選んだ結果を記録する。

## 6. 読み上げの確認の仕方

- 押す前に、ボタンへフォーカスを合わせて読み上げ名を記録する（例: `「刺身」を上へ移動する ボタン`）。
- 押した後は、何も触らずに 10 秒待ち、聞こえた文を順に書き取る。聞こえた回数も書く。
- 期待: 処理中の文言（例: `移動中…`）が 1 回、続いて結果の Toast の文が 1 回。成功の後に画面内へ残る文（例: S1 の追加の後に上部に出る文）は、二度目には読まれない。
- 失敗の後、画面内に残った誤りの文（入力欄の下・節の見出しの下・予約・来店の説明文の下）は、フォーカスを移して読める。自動では読まれない（Toast が 1 回読む）。
- 結果の Toast を読み上げの操作で開いて閉じられるか（「通知を閉じる」）。

## 7. キーボードの確認の仕方

- Tab で目的のボタンまで進み、Enter（ボタンは Space でも）で押す。
- 押した後、処理中・完了後のそれぞれで、フォーカスがどこにあるかを記録する（例: 押したボタン・ページの先頭・見えない）。そこから Tab を 1 回押したときに、どの要素へ進むかも書く。
- 処理中のボタンは押せなくなるので、ブラウザによってはフォーカスがボタンから外れる。S2 の保存の後は編集欄が閉じ、S5・S6 の後は項目が別の一覧へ移る。フォーカスの行き先は今の実装では決めていないので、観察した結果をそのまま記録する（合否は人が判断する）。
- コピーの失敗の後は、下書きの欄にフォーカスが移り、全文が選択されていること。
- Toast が出ている間も、Tab で画面の要素へ進めること。
