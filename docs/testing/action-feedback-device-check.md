## 1. 準備

### 1-1. 確認する場所を選ぶ

本書では確認する場所を L・P1・P2 の記号で呼ぶ。本番を変えずに確かめられるのは L だけである。

| 記号 | 確認する場所 | 使えるもの | 本番への影響 | 扱い |
|---|---|---|---|---|
| L | ローカルの確認環境に携帯から接続する | 店舗設定 7 操作（LIFF はスタブ）・客向けの legacy と structured の両方・下書きの生成失敗 | なし | `docs/testing/structured-survey-local-preview.md` の手順を使う（下の 1-2） |
| P1 | 本番の検証用店舗の客向け画面 | 客向けの legacy のアンケート・下書き・再生成・コピー | 成功の送信 1 回ごとに、回答 1 件が匿名集計に加算される（取り消せない） | `docs/testing/e2e.md` の 4-1・4-2 と同じ扱い。送信の回数は 5-0 の規律に従う。実クライアントの店舗では試さない |
| P2 | 本番の検証用店舗の店舗設定（実 LINE・実 LIFF） | 実の LINE と LIFF での店舗設定 7 操作 | 検証用店舗のアンケート設定と監査ログ（`audit_logs`）が変わる | 承認が要る（1-4 の D1）。承認が無い間は実施しない |

L で確かめられないのは、実 LIFF（`liff.init`・ID トークン）と、HTTPS でしか動かない Clipboard の成功の経路である。後者は P1 で確かめる。

P1・P2 の前には、本番のコミットが #450 の実装を含むことを確かめる（8-1）。本番のコミットは `PROJECT_ID=gen-fw-line-meo make e2e-prod-checks` の出力で読む。この装置は `PROJECT_ID` と、本番プロジェクトの閲覧・ログの閲覧ができる gcloud の認証を要するので、運用者が実行し、結果を実施者へ渡す（`docs/testing/e2e.md` の 3.）。

### 1-2. L: ローカルの確認環境を携帯から開く

`docs/testing/structured-survey-local-preview.md` の 1.〜4. で DB・seed・ビルドと 3 つのプロセス（偽の ID トークン検証サーバー・店舗詳細のプロセス・客向けのプロセス）を用意する。差し替え口は E2E と同じ 2 つ（`E2E_STUB_IDP=1` の LIFF スタブと、偽の ID トークン検証サーバー）で、本番の設定では効かない。

携帯から開くために、次だけを変える。

1. PC と携帯を同じ Wi-Fi につなぎ、PC の LAN 内の IP アドレスを調べる（Windows なら `ipconfig` の「IPv4 アドレス」）。以下 `<PC>` と書く。
2. 店舗詳細のプロセスと客向けのプロセスを、全インターフェイスで待ち受けるよう起動する。`next start` の既定の待ち受けも全インターフェイスだが、明示する。

   ```bash
   # 店舗詳細のプロセスの末尾を次に置き換える
   ... PORT=3121 pnpm -C ts --filter @fwlm/store-detail start -H 0.0.0.0
   # 客向けのプロセスの末尾を次に置き換える
   ... PORT=3100 pnpm -C ts --filter @fwlm/survey-web start -H 0.0.0.0
   ```

3. Windows のファイアウォールが 3121・3100 の受信を止めるときは、確認の間だけプライベートネットワークで許可する。終わったら戻す。
4. 携帯で次を開く。

| 画面 | URL |
|---|---|
| 店舗設定（legacy の店舗） | `http://<PC>:3121/store/survey-settings?storeId=44444444-4444-4444-4444-444444444444` |
| 店舗設定（structured の店舗） | `http://<PC>:3121/store/survey-settings?storeId=55555555-5555-4555-8555-555555555555` |
| 客向け（legacy） | `http://<PC>:3100/s/44444444-4444-4444-4444-444444444444` |
| 客向け（structured） | `http://<PC>:3100/s/55555555-5555-4555-8555-555555555555` |

注意:

- L は `http://` で開くので、ブラウザは Clipboard API（`navigator.clipboard`）を出さない（安全なコンテキストではない）。L で「コピーして投稿する」を押すと、すぐに手動コピーへの復帰（失敗の経路）になる。これは L での期待どおりの結果であり、不具合と記録しない。成功の経路は P1 で確かめる。
- legacy の seed の店名は実在の店名である。L のスクリーンショットでも店名を伏せる。
- LINE 内ブラウザの描画だけを見たいときは、L の URL を自分宛ての LINE のトークに貼って開く。実 LIFF ではない（LIFF はスタブのまま）。
- 確認が終わったら、`structured-survey-local-preview.md` の 6. のとおり店舗詳細を通常のビルドへ戻す。

### 1-3. structured_enabled の扱い

`store_survey_configs.structured_enabled` を変える操作は、店舗オーナーの画面にも dashboard-api にも無い（`db/write-boundary.md`）。

- L では `ts/apps/survey-web/e2e/structured-seed.sql` が 55555555-… の店舗だけを有効にする。legacy の 44444444-… の店舗は無効のままで、店舗設定の画面の上部に次の案内が出る。

  > ここで登録した料理名・ドリンク名は、新しいアンケートの準備ができしだいお客様の画面に表示されます。今お客様が使っているアンケートは変わりません。

- 本番で structured が有効な店舗は 0 件とされている。ただし確認日時は不明で、実測の記録は見つかっていない。出典は PR #443 の本文の「Rollout precondition」の 4.（merge の前に運用者が `infra/README.md` の確認の SQL で `structured_enabled` が 0 件であることを確かめる手順）で、Issue #460（2026-10-16 起票）も同じ記載を引いている。いずれも手順の期待値であり、誰がいつ確かめた値かは特定できない（2026-10-22 に PR #443・Issue #441・Issue #460 の本文とコメントを確認した）。
- 実機の確認を始める前に、運用担当者が本番の最新の状態（structured が有効な店舗の件数）を再確認し、結果を 8-1 の記録欄に残す。開発者と Claude は本番 DB に接続しない。
- 本番で structured の客向け画面を確かめる手順はリポジトリに無い。行うには承認が要る（1-4 の D2）。

### 1-5. 失敗と遅延を起こす方法

| 起こしたいこと | 方法 | 使える場所 |
|---|---|---|
| 通信失敗 | 画面を開いた後に機内モードにする（L では携帯の Wi-Fi を切る）。押した後に戻す | L・P1・P2（D1 承認後） |
| API のエラー（店舗設定） | 表示中の料理名と同じ名前を「料理名を追加」に入れる（409）。文言は 4. の失敗の経路の表 | L・P2（D1 承認後） |
| 入力の検証で止める（店舗設定） | 空欄のまま「追加する」、または 41 文字以上、または「絶品」などの評価の言葉を含む名前 | L・P2（D1 承認後） |
| 入力の検証で止める（客向け） | 星を選ばずに送信する | L・P1 |
| 初回の下書きの生成失敗（HTTP 200・`generation: 'failed'`） | 客向けのプロセスを、Gemini のモック（`NODE_OPTIONS`）を外し、`GEMINI_API_KEY` をダミーのままにして起動し直してから回答を送る。Google へは無効な鍵の要求が出るだけで課金は無い | L のみ |
| 下書きがある状態の再生成の失敗 | モックありの客向けのプロセスで回答を送り、下書きの画面を出す。その画面は閉じず再読み込みもせずに、客向けのプロセスを `SESSION_SIGNING_KEY` を同じ値のまま、モックを外して起動し直す。30 分以内に（下書きの画面の sessionToken の有効期間）同じ画面で「別の文章を生成」を押す | L のみ |
| 遅延（8 秒以上） | iOS: 設定 > デベロッパ > Network Link Conditioner で「Very Bad Network」。この項目はデベロッパモードを有効にした端末にしか出ず、デベロッパモードの有効化には Mac と Xcode が要る。Android: 端末の USB デバッグを有効にして PC へ USB でつなぎ、PC の Chrome の `chrome://inspect` から実機のタブを開き、DevTools の Network の速度制限を使う | L・P1・P2（D1 承認後） |
| Clipboard の失敗 | L で押す（1-2 の注意のとおり、すぐに手動コピーへ復帰する）。P1 では、iOS で失敗させる確実な方法は確認していない | L |

遅延を起こせなかった端末では、8 秒後の案内の項目を「未実施（遅延を起こせない）」と記録する。実施していない項目を合格にしない。

## 2. 端末の設定

1 回の確認で設定を 1 つずつ切り替える。複数を同時に変えると、どの設定で崩れたか分からなくなる。

| 設定 | iOS | Android |
|---|---|---|
| 動き低減 | 設定 > アクセシビリティ > 動作 > 視差効果を減らす | 設定 > ユーザー補助 > 色と動き > アニメーションを削除（機種により名称が違う） |
| 読み上げ | 設定 > アクセシビリティ > VoiceOver | 設定 > ユーザー補助 > TalkBack |
| 200% ズーム | Safari のアドレス欄の「ぁあ」（ページ設定）で 200% | Chrome の 設定 > ユーザー補助 > ページのズーム（または文字の拡大縮小）で 200% |
| キーボード | Bluetooth キーボードをつなぐ。設定 > アクセシビリティ > キーボード > フルキーボードアクセス | Bluetooth キーボードをつなぐ |
| 狭い幅 | 画面幅が最も狭い端末を使う（iPhone SE など）。320px ちょうどは自動層が確かめている | 同左 |

PC のブラウザでキーボードだけの確認をするときは、L の URL を PC で開いてよい（Tab・Shift+Tab・Enter・Space だけで操作する）。

## 3. 共通の期待結果

各操作で、次の 1〜6 を確かめる。文言はコードから写したもので、句点の有無まで画面と一致すること。`{名前}` は操作した料理名・ドリンク名が入る。「予約・来店」「40文字」「10件」は、コードがカテゴリ名・上限の値を差し込んだ結果を書いている。
ただし本番（P1・P2）でサーバーが返した失敗の文言には、文末に `（サポートコード: xxxxxxxx）`（8 文字の英数字）が付きうる。サポートコードは Cloud Run の要求ごとに決まるので、L では付かない。付いた部分を除いて一致すれば合格とし、サポートコードの値を記録する。

1. 押した直後に、押したボタン（カテゴリの表示設定は選択肢の直下）が Spinner と処理中の文言に変わり、押せなくなる。2 回目の押下で要求が二重に送られない。
2. 動き低減の設定では Spinner が回らない。それでも処理中の文言が文字で読める。
3. 押してから 8 秒を過ぎても終わらないときは、処理継続中の案内が出る。
   - 店舗設定: 画面の上部（店名の下）に `保存に時間がかかっています。画面を閉じずにこのままお待ちください。`。ボタンは処理中の文言のまま。200% ズームでは画面の上部が表示の外になりうるので、上へスクロールして確かめる
   - 客向け: ボタンの下に `少し時間がかかっています。画面を閉じずにこのままお待ちください`
4. 終わったら、Toast が画面の右下（狭い画面では下端いっぱい）に 1 回だけ出る。成功は緑の印、失敗は赤の印。約 6 秒で消え、「通知を閉じる」でも閉じられる。Toast の領域の読み上げ名は「操作結果の通知」。
5. Toast が出ている間も、画面のほかのボタン・入力欄が押せる（Toast に覆われて押せない要素があれば記録する）。
6. 読み上げでは、処理中の文言が 1 回、結果が 1 回だけ読まれる。同じ結果の文が Toast と画面内の案内の両方から 2 回読まれたら不合格とする。

| S2 | 名称変更の保存 | 「編集」（`編集：「{名前}」の名前を変更する`）→「保存する」 | `保存中…` | `名前を変更しました。` | 編集欄が閉じ、新しい名前で並ぶ |
| S3 | 上へ | 「↑ 上へ」（`「{名前}」を上へ移動する`） | `移動中…` | `並び順を保存しました。` | 1 つ上へ移る |
| S4 | 下へ | 「↓ 下へ」（`「{名前}」を下へ移動する`） | `移動中…` | `並び順を保存しました。` | 1 つ下へ移る |
| S5 | 非表示 | 「非表示」（`「{名前}」を非表示にする`） | `非表示にしています…` | `「{名前}」を非表示にしました。` | 「非表示にした料理名」の一覧へ移る |
| S6 | 再表示 | 「再表示」（`「{名前}」を再表示する`） | `再表示中…` | `「{名前}」を再表示しました。` | 表示中の一覧へ戻る |
| S7 | カテゴリの表示設定 | 予約・来店の「表示する」／「表示しない」 | 選択肢の直下に `保存中…` | `予約・来店をアンケートに表示します。`／`予約・来店をアンケートに表示しません。` | 選んだ側が選択された状態になる |

失敗の経路（1-5 の方法で起こす）:

| 起こすこと | 対象 | 期待結果 |
|---|---|---|
| 通信失敗 | S1〜S7 のどれか 2 つ以上 | 失敗の Toast `通信に失敗しました。電波の良いところで、もう一度お試しください。`。同じ文が、S1・S2 は入力欄の下、S3〜S6 はその節の見出しの下、S7 は予約・来店の説明文の下に残る。入力した名前は消えない。ボタンが押せる状態に戻り、通信を戻して押し直すと成功する |
| API のエラー | S1（同名の追加） | 失敗の Toast `同じ名前がすでに表示されています。別の名前にしてください。`（P2 では文末に `（サポートコード: xxxxxxxx）` が付きうる・3. の注記）。同じ文が入力欄の下に残り、入力は消えない |
| 入力の検証 | S1・S2（空欄） | 要求を送らずに、失敗の Toast `名前を入力してください。`。入力欄が誤りの状態になり、同じ文が欄の下に残る |
| 入力の検証 | S1・S2（41 文字以上） | `名前は40文字以内で入力してください。` |
| 入力の検証 | S1・S2（例: 絶品餃子） | `「絶品」「おすすめ」「リピート」のような、味の評価やおすすめの言葉は名前に使えません。お客様の口コミの文にそのまま入るため、料理名・ドリンク名だけを入力してください（例：「絶品餃子」なら「餃子」）。` |
| 上限（L のみ。P2 では行わない。本番に消せない料理名が 10 件残るため） | 料理を 10 件表示した状態 | 「追加する」が押せず、欄の下に `料理は10件まで登録できます。追加するには、どれかを非表示にしてください。`。非表示の一覧の「再表示」も押せない |

キーボードでの追加の確認: S1 で Enter を連打しても、追加は 1 回だけになる。

## 5. 客向けの操作（survey-web）

### 5-0. 送信の回数の規律（P1）

P1 では、成功した送信 1 回ごとに回答 1 件が本番の匿名集計に加算され、取り消せない。また送信に成功すると、その端末・ブラウザは 24 時間「回答済み」になり（`answered-flag.ts`・localStorage）、同じ店舗の回答画面を開き直しても回答済みの画面しか出ない。次を守る。

1. 失敗の経路（星を選ばずに送信・機内モードでの送信）を、成功の送信より先に行う。どちらも回答がサーバーに届かないので加算されない。回答の画面を開いてから 5 分を過ぎたら、送信の前に再読み込みする（回答の画面の pageToken の有効期間）
2. 成功の送信は、1 つのブラウザにつき 1 回だけにする。送信した回数を 8-1 に記録する
3. 下書きの画面は再読み込みせず、閉じず、その画面のまま OS の設定（2.）を切り替えて、再生成（5-2）とコピー（5-3）を繰り返す。再生成は加算されない
4. 5-1 を設定（動き低減・読み上げ・200%・キーボード）ごとに確かめるのは L で行う
5. プライベートタブや別のブラウザで送り直さない（2 件目が加算される）
6. Google に実際に投稿しない（`docs/testing/e2e.md` の 4-7）。投稿画面が開いたところで止める

### 5-1. 回答送信・口コミ文の作成

| 画面 | 押すボタン | 処理中の文言（ボタン） | 処理中の文言（ボタンの下・読み上げられる文） |
|---|---|---|---|
| legacy | 「送信する」 | `口コミ文を作成しています…` | `回答内容をもとに文章を作成しています` |
| structured | 「口コミ文を作る」（感想を 2 つ以上選ぶまで押せない） | `口コミ文を作成しています…` | `回答内容をもとに文章を作成しています` |

| 結果 | Toast | 画面 |
|---|---|---|
| 成功 | 成功 `口コミ文を作成しました。` | 下書きの画面（「コピーして投稿する」「別の文章を生成（残り3回）」「Google のクチコミを書く」）へ切り替わる。Toast は切り替えの後も残る |
| 初回の下書きの生成失敗（L のみ） | 失敗 `下書きの生成に失敗しました。もう一度生成するか、そのまま投稿画面へお進みください。` | 画面内に `下書きの生成に失敗しました。再試行するか、そのまま投稿画面へお進みください。`、「もう一度生成する」「Google のクチコミを書く」が出る。成功の Toast は出ない |
| 通信失敗 | 失敗 `通信に失敗しました。入力内容は残っています。時間をおいて再度お試しください。` | 回答の画面のまま、同じ文が上部に残る。星・選んだ観点・一言が残っていて、そのまま送り直せる |
| 星を選ばずに送信 | 失敗 `満足度を選択してください。` | 要求を送らない。星の下に `満足度を選択してください` が残る |

U1（`回答を送信しました。`）は通常の操作では出ないので、この表に入れない（0-3）。

### 5-2. 再生成

下書きの画面で「別の文章を生成（残りN回）」を押す。下書きを手で 1 文字直してから押すと、失敗のときに編集が残ることも確かめられる。

| 結果 | 処理中 | Toast | 画面 |
|---|---|---|---|
| 成功 | ボタン `別の文章を作成しています…`、下に `回答内容をもとに文章を作成しています`。「コピーして投稿する」も押せない | 成功 `別の口コミ文を作成しました。` | 新しい下書きに置き換わり、残り回数が 1 減る |
| 下書きがある状態の生成失敗（L のみ・1-5） | 同上 | 失敗 `別の文章を作成できませんでした。今の文章はそのまま編集・コピーできます。` | 手で直した文章が残り、コピー・再生成・投稿導線が使える。失敗専用の画面には切り替わらない |
| 通信失敗 | 同上 | 失敗 `通信に失敗しました。文章は残っています。時間をおいて再度お試しください。` | 同じ文が上部に残る。文章が残る |

初回の生成が失敗した画面（5-1）の「もう一度生成する」は、下書きがまだ無い状態の再生成である。期待結果を分けて確かめる。

| 結果 | 処理中 | Toast | 画面 |
|---|---|---|---|
| 「もう一度生成する」で成功 | ボタン `別の文章を作成しています…`、下に `回答内容をもとに文章を作成しています` | 成功 `別の口コミ文を作成しました。` | 下書きの画面（入力欄と「コピーして投稿する」）へ切り替わる |
| 「もう一度生成する」でも失敗（L のみ） | 同上 | 失敗 `下書きの生成に失敗しました。もう一度生成するか、そのまま投稿画面へお進みください。` | 失敗専用の画面のまま。「Google のクチコミを書く」が使える |

L で「もう一度生成する」の成功を見るときは、初回の失敗の後、客向けのプロセスを `SESSION_SIGNING_KEY` を同じ値のまま、モックありで起動し直してから押す（30 分以内）。

### 5-3. コピー

「コピーして投稿する」を押す。

| 結果 | 処理中 | Toast | 画面 |
|---|---|---|---|
| 成功（P1・HTTPS） | ボタン `コピー中…`、下に `文章をコピーしています`（一瞬で終わることが多い。見えなくても不合格にしない） | 成功 `コピーしました。投稿画面に貼り付けてください。`（Toast はコピーが終わった後に出る） | 同じ文の案内が残る。メモ帳などに貼り付けて、表示中の文章（手で直した分を含む）と一致することを確かめる |
| 失敗（L・HTTP） | 出ない。`navigator.clipboard` が無いので、押した直後に手動コピーへ復帰する（`コピー中…`・`文章をコピーしています` は描かれない） | 失敗 `自動コピーできませんでした。文章を選択して手動でコピーしてください。` | `自動コピーできませんでした。上の文章を選択して手動でコピーしてください。` が残り、下書きの欄にフォーカスが移って全文が選択される。そこから手動でコピーできる |

iOS Safari では、押した操作の中で `writeText` を呼ぶ流れになっている（`draft-panel.tsx` の `handleCopy`）。iOS Safari で成功の Toast が出て、貼り付けた内容が一致すれば、この流れが実機で効いている。許可のダイアログが出た場合は、その文言と選んだ結果を記録する。

## 6. 読み上げの確認の仕方

- 押す前に、ボタンへフォーカスを合わせて読み上げ名を記録する（例: `「刺身」を上へ移動する ボタン`）。
- 押した後は、何も触らずに 10 秒待ち、聞こえた文を順に書き取る。聞こえた回数も書く。
- 期待: 処理中の文言が 1 回、続いて結果の Toast の文が 1 回。処理中の文言が読まれる場所は、店舗設定では画面の上部（店名の下）の 1 行、客向けではボタンの下の 1 行である。成功の後に画面内へ残る文（例: S1 の追加の後に上部に出る文）は、二度目には読まれない。
- 失敗の後、画面内に残った誤りの文（入力欄の下・節の見出しの下・予約・来店の説明文の下）は、フォーカスを移して読める。自動では読まれない（Toast が 1 回読む）。
- 結果の Toast を読み上げの操作で開いて閉じられるか（「通知を閉じる」）。

## 7. キーボードの確認の仕方

- Tab で目的のボタンまで進み、Enter（ボタンは Space でも）で押す。
- 押した後、処理中・完了後のそれぞれで、フォーカスがどこにあるかを記録する（例: 押したボタン・ページの先頭・見えない）。そこから Tab を 1 回押したときに、どの要素へ進むかも書く。
- 処理中のボタンは押せなくなるので、ブラウザによってはフォーカスがボタンから外れる。S2 の保存の後は編集欄が閉じ、S5・S6 の後は項目が別の一覧へ移る。フォーカスの行き先は今の実装では決めていないので、観察した結果をそのまま記録する（合否は人が判断する・0-3 の U5）。
- コピーの失敗の後は、下書きの欄にフォーカスが移り、全文が選択されていること。
- Toast が出ている間も、Tab で画面の要素へ進めること。
