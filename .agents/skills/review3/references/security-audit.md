# セキュリティ観点

出典は Cloudflare `security-audit-skill`（github.com/cloudflare/security-audit-skill）。
そこから **PR 差分のレビューに効く知見だけ**を抜いてある。完全監査の 6 フェーズ、sandbox 要件、
coverage ledger、budget gate、findings.json の validator は入れていない。リポジトリ全体の監査を
頼まれたときは元スキルを直接使う。

読むタイミング: Phase 3 の「境界と影響」パスに入る前。下の発火表に 1 行でも当たるなら必ず読む。

---

## 1. 発火表 — 差分から走らせるクラスを選ぶ

差分に次が含まれるとき、対応するクラスを走らせる。当たらないクラスは走らせない（当たらないのに
「一応確認した」と書かない）。

| 差分に含まれるもの | 走らせるクラス |
|---|---|
| SQL、クエリ組み立て、HTML 出力、テンプレート、shell 実行、ファイルパス、リダイレクト、デシリアライズ | Injection |
| 認証、認可、ロール、テナント境界、所有者チェック、一括/バッチ/import/export の権限 | Access control |
| ファイル読み書き、アップロード、アーカイブ展開、外部 URL の取得、一時ファイル | Resource and file handling |
| トークン生成、鍵、署名、ハッシュ、乱数、秘密情報の受け渡し、比較 | Crypto and secrets |
| 状態遷移、再試行、部分失敗、数量・金額、期限・時刻、既定値、フィーチャーフラグ | Business logic |
| 検索、絞り込み、並び替え、エクスポート、インポート、復元、プレビュー、通知/webhook URL | Feature abuse and data leakage |
| コンポーネント間の受け渡し、委譲、キャッシュ、スコープ拡大、削除/失効の伝播 | Chained vulnerabilities and trust boundaries |
| 上のどれにも当たらないが、差分に「半端」「実験的」「互換のため」「legacy」「hack」が見えるもの | Wildcard |
| **常に（差分に含まれるファイルに対してだけ）** | Obvious things（第 7 章） |

### Injection
入口から危険な sink までを追う。直接経路で止めない。
- 一度安全に保存されたデータが、別のコードで危険な文脈へ取り出される**二次注入**
- 値ではなく**キー名・フィールド名・ヘッダ名・メタデータ**を経由する注入
- ログ・キャッシュ・検索インデックス・分析基盤といった**二次システム**への注入

### Access control
「チェックが在るか」ではなく「**正しい権限を・正しいリソースに・正しい仕組みで**見ているか」。
- 同じ状態変更に到達する別経路が、より弱い権限で通っていないか
- リクエストボディの 1 フィールドが、権限で縛ったはずのものを上書きできないか
- 認証は見ているが認可を忘れているエンドポイントは無いか
- 同じリソースに複数の到達経路があって、チェックが食い違っていないか
- 一括・バッチ・export・import は 1 件ずつの権限を守っているか

### Resource and file handling
パストラバーサル（シンボリックリンク・エンコード・NUL 経由を含む）、SSRF（リダイレクト・DNS リバインド・
URL パーサ差異を含む）、安全でないデシリアライズ、zip slip、一時ファイル、ファイル操作の TOCTOU。

### Crypto and secrets
セキュリティ上重要な値に弱い乱数、ハードコードされた秘密、ログ・エラー・URL・クライアントへ返る応答への
秘密の混入、鍵導出の破綻、HMAC 検証の欠落、nonce 再利用、秘密比較のタイミング差、
プリミティブの誤用（ECB、認証なし暗号、固定 IV）。**暗号処理が失敗したときの経路が
「暗号なし」へ落ちていないか**も見る。

### Business logic
スキャナでは出ない。主要フローごとに手で追う。
- **状態機械違反**: 手順を飛ばせるか、戻れるか、完了済みを再実行できるか、3 手順中 2 で失敗したとき 1 が巻き戻るか
- **業務影響のある競合**: 二重支払い・二重承認・更新の取りこぼし。check-then-act が非原子なところ
- **数量の細工**: 負数、ゼロ、オーバーフロー、精度落ち、文字列と数値の型強制
- **暗黙の信頼**: 「入口で検証済みだから安全」と見なしている保存済みデータ・設定・他コンポーネント由来の値。
  別経路がそこへ書いた場合はどうなるか
- **時間依存**: 期限、スケジュール、レート窓、時計ずれ。境界ちょうどの瞬間。コンポーネント間のタイムゾーン差
- **既定とフォールバック**: 設定が無いとき、フラグが off のとき、依存が落ちているとき、移行の途中のとき、
  セキュリティ姿勢はどちらへ倒れるか

### Feature abuse and data leakage
正規機能の意図しない用途。コードのバグではなく設計のバグを探す。
- **export がデータ持ち出しになる**: 低権限の利用者が、自分のアクセス権を超えるデータを含む
  エクスポート・スナップショット・バックアップを起動できないか。削除済み・下書き・非公開・改版履歴が混ざらないか
- **import が書き込みになる**: 既存データを上書きできないか、通常の検証を迂回するレコードを作れないか、
  書き込み権限の無い集合へ差し込めないか
- **検索・絞り込み・並び替えが存在判定になる**: 直接読めないものの存在を、検索結果・絞り込み条件・
  並び順から推測できないか
- **副作用による列挙**: 「存在しない」と「権限が無い」でメッセージ・応答時間・応答サイズ・
  ステータスコードが違わないか。パスワード再設定・招待・登録から利用者を列挙できないか
- **プレビュー・下書きの漏れ**: プレビュー用トークンの効く範囲が 1 件を超えていないか。
  下書きが一覧 API・検索・サイトマップから見つからないか。キャッシュヘッダで CDN が非公開を配らないか
- **通知・webhook が SSRF になる**: 利用者が指定した URL をサーバが取りに行くとき、内部ネットワークを
  弾いているか。リダイレクトの先はどうか

### Chained vulnerabilities and trust boundaries
単体では許容される挙動が、次の段が強い保証を前提にしていると脆弱性になる。
- **コンポーネント間の保証のずれ**: A が作る保証と B が仮定するものを突き合わせる。
  切り詰め、型強制、正規化、テナントのスコープ、拡張の権限
- **二次利用**: 保存時は安全だった値が、後でフィールド名 → JSON パス、slug → ファイルパス、
  エスケープ済みテキスト → 生描画、文字列 → URL / 正規表現 / テンプレート / ポリシー式 に化ける
- **スコープの成長**: 委譲・更新・キャッシュ・ロール変更・合成のあとでトークンや鍵の権限が広がる。
  結果として得られる主体が持つべきでない**具体的な操作**を名指しする
- **順序と時間差**: セットアップ、移行、論理削除、失効とキャッシュ期限、check と use、検証と消費の窓
- **巻き戻しと復元**: undelete・復元・改版ロールバック・取り消しが、現在の所有者・検証・認可を適用しているか。
  どの不正な状態が復元されるかを名指しする

### Wildcard
カテゴリを与えられない枠。退屈に見えるコード・切り離されて見えるコードを読む。
- このコードベースで一番おかしなコードは何か。なぜ存在するのか
- 半端・実験的・後付けに見える機能はどれか（レビューが一番薄い）
- フロントエンドが決してしない使い方で API を叩いたらどうなるか
- 設計時に組み合わせを想定していない機能同士を混ぜたらどうなるか
- テストは**何を**テストしていないか。開発者が考えた境界と考えなかった境界を比べる

## 2. 不変条件の 6 ステップ

候補を立てるときは毎回この順で書く。途中で止まったらそこが proof gap。

1. **低信頼の主体**と、その初期能力を名指しする
2. 受理される**値・操作・状態遷移・リソース指定子**を名指しする
3. それを拒否・束縛・隔離・制限・失効させるはずの**制御**の位置を特定する
4. その判断の**後ろ**の実コード経路をたどる
5. 最小の観測結果で止める（誤った戻り値、権限外のダミーレコード、ポリシーの差）。
   そこから先へ効果を広げない
6. その不変条件を強制する**最小の修正**と**回帰テスト**を書く

---

## 3. finding の必須 6 項目

確定 finding には次の 6 つが全部揃っている必要がある。1 つでも言えなければ finding にしない。

1. 低信頼の主体
2. 受理される入力または操作
3. 本来効くはずの制御
4. 越えた境界
5. 影響を受ける主体またはリソース
6. 具体的な結果（観測したもの、または所有者が観測できるもの）

---

## 4. 3 値と review2 語彙への写像

新しい語彙を増やさない。元スキルの 3 値は Phase 4 の verdict へそのまま写す。

| 元スキル | review3 の verdict | severity |
|---|---|---|
| `confirmed` | `KEEP` | 付ける |
| `needs_validation` | `REVIEW` | **付けない** |
| `rejected` | `REJECT` | — |

`needs_validation` は「確度の低い確定 finding」ではない。**source からも安全なローカル検証からも
決着が付かない特定の事実**が 1 つ足りない状態を指す。書くのは 2 つだけ:
欠けている事実は何か、それを埋める安全な確認手順は何か。

デプロイ設定、プロキシの挙動、プロバイダの設定、ブラウザが付けるヘッダ、IdP のポリシー、
ブローカーの ACL、パッケージング、トポロジは**実在する制御**である。必要なのにリポジトリに無いなら、
「有る」とも「無い」とも決めつけず `REVIEW` にする。

## 5. severity アンカー

| 元スキル | review3 | 基準 |
|---|---|---|
| critical | `High` | 未認証の攻撃者がコード実行・データストア全体へのアクセス・任意アカウントの乗っ取りを得る |
| high | `High` | 明示的なセキュリティ制御を**完全に破る**（認証バイパス、テナント跨ぎの読み書き、他利用者に影響する保存型スクリプト実行、認証済みコード実行、未認証で共有サービスを停止） |
| medium | `Middle` | 実在する境界違反だが、影響範囲が限定的・前提条件が珍しい・影響が狭いリソース集合に閉じる |
| low | `Low` | 秘密でない内部情報の開示、または継続的な労力に対して得るものが僅か |
| informational | `Nit` | 確認済みだが影響が最小。大きな finding の前提としてのみ意味がある |

**High と Middle の判別**: 実証した結果が、実害のある操作について明示的な制御を**完全に破った**のか、
**弱めた**だけなのか。具体的な被害を言えないなら、感じる severity より 1 段低い。

severity を決めてよいのは `KEEP` だけ。`REVIEW` には付けない。

## 6. 候補ゲートとアンチパターン

### 候補ゲート（全部通ったものだけ `KEEP` にする）

1. 主張する根本原因について、リポジトリ相対の完全な経路と証拠がある。**source から見える最も強い制御**を
   確認したうえで、それでも破れると言えている
2. 境界を越えた意味のある影響と、成立条件が全部揃っている。防いでいる層が見えていない
3. クラッシュをコード実行へ、通常の処理を共有資源の可用性障害へ、同一主体の操作を権限昇格へ**強化しない**
4. 必要な事実が source からも安全なローカル検証からも取れないなら `REVIEW`。欠けている事実を名指しし、
   severity も推測による穴埋めも付けない
5. 影響を受ける主体もリソースも言えないベストプラクティス欠如は finding ではない（対象外か、良くて hardening）。
   source で反証されたものは `REVIEW` ではなく `REJECT`
6. 同じ根本原因は、状態が変わっても同じ識別子で扱う
7. 全部落ちたら候補ゼロで返す。埋め合わせに弱い候補を昇格させない

### アンチパターン

1. チェックリストからの逸脱を脆弱性として出す
2. 到達可能な境界違反の無い多層防御の助言
3. ローカルで足りる証拠が取れるのに、本番や共有環境で試す
4. プロバイダ・プロキシ・ブラウザ・IdP・デプロイの挙動を、source に無いまま推測する
5. 同一主体が本来持つ権限の行使や、自分自身への影響を、境界を越えた結果として扱う
6. 観測した効果より強いパーサ・ランタイムの影響を報告する
7. 重複排除も検証もできない散文だけの候補を出す
8. 反証も検証もせずに書いた指摘を、そのまま報告に載せる
9. `REVIEW` に severity を付ける
10. 文章と構造化データが食い違ったまま出す

## 7. 「見落としがちな基本」

**差分に含まれるファイルに対してだけ**、機械的に全項目を確認する。創造性は要らない。網羅と literal。
当たらない項目は「差分に無い」と書いて閉じる。

- ソースにハードコードされたパスワード・API キー・トークン・秘密
  （`password` `secret` `apikey` `token` `Bearer` `BEGIN PRIVATE` を grep）
- セキュリティに言及する TODO/FIXME/HACK/XXX（`TODO: add auth` `FIXME: validate` `HACK: skip permission`）
- デバッグモード・開発モードのゲート。環境変数・クエリパラメータ・ヘッダで本番でも有効化できないか
- 本番でも通るテスト用・例示用・シード用の資格情報
- 保護されていない `/debug` `/admin` `/test` `/status` `/health` `/metrics` `/env` `/config` 系エンドポイント
- リポジトリにコミットされた環境設定ファイル・資格情報 JSON・秘密鍵ファイル
- `.gitignore` が秘密・アップロード・ローカル設定を実際にカバーしているか
- 依存がピン留めされているか。ロックファイルに既知の CVE が無いか
- 動的な入力が入る `eval()` `exec()` `child_process` `Function()` `vm.runInContext` 動的 `import()`
- CORS が `*`、または `Access-Control-Allow-Credentials` とワイルドカード Origin の併用
- Cookie の `HttpOnly` `Secure` `SameSite` の欠落
- オープンリダイレクト（`redirect` `return` `next` `url` `goto` `continue` がリダイレクトへ流れる）
- TLS の強制。HTTP のみのエンドポイントが無いか
- 本番のエラー応答にスタックトレース・内部パス・SQL エラーが出ていないか

**フラグは finding ではない。** 当たった項目は必ず経路を最後までたどってから出す。
`HttpOnly` が無い Cookie なら、中身がセキュリティ上重要か・設計上 JS が読む必要があるかを確認する。
エラーメッセージにフィールド名が出るなら、そのフィールドが実際に機微な値を持つか確認する。

## 8. 誤検知の抑制

上乗せの規則は置かない。review2 の既存規則をそのまま効かせる。

- `../../review2/references/review-rubric.md` 観点 B:
  脅威主体・入口・sink・既存 control・到達経路を示せない security finding は確定しない。
  既存 control を「あるはず」と仮定しない一方、diff だけで「無い」とも断定しない
- `../../review2/references/accuracy-playbook.md`:
  security 候補は `source -> processing/control -> sink -> observable impact` を追う。
  各辺を実コードで結べない場合は確定 finding でなく proof gap
