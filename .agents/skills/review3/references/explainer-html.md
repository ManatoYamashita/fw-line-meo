# 図解 HTML

**先に `../../pr-critical-review/VISUAL.md` を最後まで読む。** この文書はその差分だけを書く。
節構成・境界図・SRC プレースホルダ・自己完結・公開手順は VISUAL.md のとおり。
ここで上書きするのは次の 3 つだけ。

1. 節を 1 つ増やす（**0.5 この変更を画面で見ると**）
2. 説明の主従を逆にする規則（第 2 章）
3. 画像の扱い（VISUAL.md 第 7 章の「画像は使わない」を上書き）

---

## 1. 節構成

VISUAL.md 第 2 章の表に、節 0.5 を 1 つだけ足す。**それ以外の節は増やさない。**

| 節 | 内容 | 省略可否 |
|---|---|---|
| ヘッダ | PR 番号・タイトル・ブランチ・母数の 4 数字 | 必須 |
| 0 | このPRの前提 | 必須。埋め終わるまで先へ進まない |
| **0.5** | **この変更を画面で見ると** | **必須**。E2E 未実施でも文章と具体値だけで書く |
| 1 | トリアージ結果 | 必須 |
| 2 | 影響範囲の境界図 | 必須（`--strict` が欠落をエラーにする） |
| 3 | 指摘の詳細 | 指摘 0 件なら省略 |
| 4 | 経緯として確認した範囲 | 必須 |
| 5 | PR 作成者への確認事項 | 埋まらなかった問いがあるときだけ |

### 節 0.5「この変更を画面で見ると」の型

**この節が、このスキルの存在理由である。** 読み手が画面の動きを思い浮かべられなければ失敗。

変更ごとに 1 ブロック。1 ブロックは次の 4 つで構成する。

1. **見出し** — 利用者の言葉で 1 行（「使用量の画面に、いつリセットされるかが出るようになる」）
2. **具体例での対比** — 登場人物を役割名で置き、実在しうる数値・文字列で「前はこう → 後はこう」を書く
3. **スクリーンショット** — **各ブロックに最低 1 枚**（第 3 章）
4. **データとしては何が変わるか** — 1〜2 文。ここだけはテーブル名・カラム名・画面名・設定名を使ってよい

対比の書き方の例（形式だけを真似る。内容は PR ごとに書く）:

> 営業部のテナント管理者が使用量の画面を開くと、いまは「今月 480 件 / 上限 1200 件」とだけ出ます。
> この変更後は同じ場所に「12 月 1 日にリセット」が並び、年間の残りが「4800 件のうち 3200 件」と
> 内訳つきで出ます。一般ユーザーの画面は変わりません。

**やってはいけない**:
- 「`UsageSummary` が `resetAt` を返すようになる」のような、識別子で組み立てた説明
- 「使用量表示が改善されます」のような、具体値の無い要約
- 数字を書かずに「正しく計算されるようになる」と書く

## 2. 説明の主従（このスキルの核）

### 2-1. 第 1 文の規則

**どの節でも、説明の第 1 文は画面・データ・お金・人の言葉だけで書く。**
関数名・変数名・型名・コンポーネント名・ファイル名を 1 つも含めない。技術の言葉は第 2 文以降へ回す。

第 1 文が書けないときは、説明が足りていない。識別子で埋めずに、書けるようになるまで読む。

### 2-2. 識別子を置いてよい場所

技術用語をゼロにはしない。**上司や顧客へ説明するのに要る 4 種類だけ**を残す。

| 種類 | 例 | 残す理由 |
|---|---|---|
| テーブル名・カラム名 | `reports.summary_data_json` | 「どのデータが変わるか」が言えないと説明にならない |
| 画面名・URL | 使用量タブ、`/settings/usage` | 「どこの話か」を指せる |
| API のエンドポイント | `GET /api/v1/reports` | 外部連携への影響を指せる |
| 設定名・フラグ名 | 音声再生の許可、`USAGE_QUOTA_ENABLED` | 「誰が変えられるか」を指せる |

**置いてはいけない**: 関数名、変数名、型名、内部コンポーネント名、クラス名。
これらは節 3 の `<figure class="src">` のコード抜粋の中だけに置く。

### 2-3. 節ごとの上限（機械検査する）

| 節 | `<code>` の使用 |
|---|---|
| 0 このPRの前提 | **禁止** |
| 0.5 この変更を画面で見ると | **4 項目「データとしては何が変わるか」の中だけ可** |
| 1 トリアージ結果 | **禁止** |
| 2 影響範囲の境界図 | 外箱の `path:line` は可 |
| 3 指摘の詳細 | 「ひとことで言うと」は禁止。前提説明とコード抜粋は可 |
| 4 経緯として確認した範囲 | 可 |
| 5 確認事項 | 禁止 |

節の `id` は VISUAL.md のとおり `s0`〜`s5`、新設の節 0.5 は `s05` を使う。
検算（生成後に必ず走らせる。節 0.5 は部分的に可なので機械検査の対象外＝目視で確認する）:

```bash
python3 - <<'PY' fragment.html
import re,sys
h=open(sys.argv[1],encoding='utf-8').read()
ng=[]
for sid in ('s0','s1','s5'):
    m=re.search(r'<section[^>]*aria-labelledby="%s"[^>]*>(.*?)</section>'%sid,h,re.S)
    if m and '<code' in m.group(1):
        ng.append('節 %s に <code> がある'%sid)
m=re.search(r'<section[^>]*aria-labelledby="s05"[^>]*>(.*?)</section>',h,re.S)
if not m:
    ng.append('節 0.5 が無い')
elif m.group(1).count('<img') < m.group(1).count('<h3'):
    ng.append('節 0.5: ブロック %d 件に対しスクショ %d 枚（各ブロック最低1枚）'
              % (m.group(1).count('<h3'), m.group(1).count('<img')))
srcs=re.findall(r'src="(data:image[^"]+)"',h)
dup=len(srcs)-len(set(srcs))
if dup:
    ng.append('同じ画像が %d 回重複している（切り出しを分ける）'%dup)
print('\n'.join('NG: '+x for x in ng) or 'OK')
sys.exit(1 if ng else 0)
PY
```

### 2-4. 具体値と登場人物

- 登場人物は**役割名**で置く（テナント管理者 / 一般ユーザー / 同席者 / 非メンバー / 連携先のシステム）。
  実在の人名・顧客名を書かない
- 影響は**利用者に見える単位**で数える（何画面・何フォルダ・何ユーザー・取り込めるか否か・共有先が何件）
- 「エラーにならないので気づけない」「表示は成功のままで中身だけ古い」といった**運用上の見え方**も書く
- 数値は実在しうる値を使う。桁が分からないなら E2E か DB で実測してから書く

## 3. スクリーンショット

VISUAL.md 第 7 章は「画像は使わない。必要なら inline SVG にする」と書いているが、
**このスキルではスクリーンショットの埋め込みを許可する**。外部 URL の禁止と自己完結の要件は維持する。

### 3-1. 画面差分の有無に関係なく撮る

**節 0.5 の各ブロックに最低 1 枚入れる。** ロジックの説明は、画面を見せて
「ここがこうなる」と言えたほうが速い。読み手は差分ではなく画面で理解する。

**「画面側の変更が 0 行だから撮らない」は理由として認めない。** 画面が変わらない PR でも、
その処理がどの画面のどの操作から起きるのかは撮れる。撮るものは次のどれか。

| ブロックの性質 | 撮るもの |
|---|---|
| 画面の表示が変わる | 変更前と変更後を**対で**並べる。**変更後が本体**で、変更前は比較用 |
| 画面は変わらないが、保存されるデータや裏の挙動が変わる | **その操作をする画面**を 1 枚。`figcaption` で「この操作の結果だけが変わる」と言う |
| 画面からは到達しない経路（API 直叩き・バッチ・worker） | **画面側がその入力を作れないことを示す画面**を 1 枚（例: 一覧から選ばせる UI なので不正な値を送れない）。到達しないという主張の裏付けになる |
| 画面が存在しない（migration・内部ライブラリ） | ここだけは「未取得（画面が無い）」でよい |

**表示が変わるブロックで変更前だけを貼らない。** 読み手がいちばん見たいのは変更後で、
変更前だけ貼って変更内容を文章で補うと、対になっていないことすら伝わらない。
変更後を撮る手順は `screenshot-runbook.md` 第 3 章。

どうしても変更後が撮れないときは、`figcaption` の先頭を
**「変更前のみ（変更後を撮るには ◯◯ が要る）」** にして、何が足りないかを書く。
`◯◯` は「PR ブランチのビルドを別ポートで出すこと」「録音完了の通知」のように、
**次に誰かが撮るなら何をすればよいか**が分かる粒度で書く。「環境がないため」は不可。

### 3-2. 「未取得」と書いてよい場合

次の 3 つだけ。**理由は具体的に書く。**

1. 画面がそもそも存在しない変更
2. 再現に実データや外部サービスの完了通知が要り、レビュー環境で用意できない
3. ログインや環境の都合で開けない（何が足りないかを書く）

2 と 3 のときは、代わりに**何で担保したか**を 1 文添える（「この挙動を固定する自動テストを実行し、
実装を 1 行壊すと落ちることまで確認した」）。

### 3-3. 書き方

- `data:image/jpeg;base64,...` で埋め込む。外部ファイル参照にしない
  （`build-html.py validate` は `https?://` だけを弾くので `data:` は通る）
- `<figure>` に入れ、`figcaption` へ「誰が・どの画面で・何をしたら・何が見えるか」を 1 文で書く
- 対で並べるときは「変更前」「変更後」を `figcaption` の先頭に置く。片方しか撮れないときは
  「変更後のみ」または「変更前のみ（変更後を撮るには ◯◯ が要る）」と明記する
- 1 枚だけのときも `figcaption` で**何を示している画面か**を言う。ただ貼るだけにしない
- **同じ画像を 2 回埋めない。** 別の説明を付けたいなら、その説明が指す範囲へ切り出し直して別の画像にする。
  同じバイト列に違う `alt` を付けると、読み手は 2 枚目で何を見ればよいか分からない。
  埋め込む前に `md5` を突き合わせて重複を落とす
- 撮り方・サイズ・秘密情報の扱いは `screenshot-runbook.md`

並べ方（横幅が足りないときは縦積みに落ちるようにする）:

```html
<figure class="shots">
  <div class="shot">
    <img alt="変更前の使用量タブ" src="data:image/jpeg;base64,...">
    <figcaption>変更前: テナント管理者が使用量タブを開くと、今月の件数だけが出る</figcaption>
  </div>
  <div class="shot">
    <img alt="変更後の使用量タブ" src="data:image/jpeg;base64,...">
    <figcaption>変更後: 同じ場所にリセット日と年間の内訳が並ぶ</figcaption>
  </div>
</figure>
```

```css
.shots { display: grid; gap: 1rem; grid-template-columns: repeat(auto-fit, minmax(320px, 1fr)); margin: 1.5rem 0; }
.shot img { width: 100%; height: auto; border: 1px solid var(--line); border-radius: 6px; display: block; }
.shot figcaption { font-size: 13px; opacity: .75; margin-top: .4rem; }
```

## 4. 生成手順

`pr-critical-review` のスクリプトをそのまま使う。改修しない。

```bash
S={SKILL_DIR}/../pr-critical-review/scripts/build-html.py
python3 $S expand     fragment.html --ref origin/<PRのブランチ>
python3 $S validate   fragment.html --strict     # exit 1 なら公開しない
# → Artifact 公開ツールが使える場合だけ公開し、実際に発行された共有URLを記録する
python3 $S standalone fragment.html <出力先>/pr-<番号>-explainer.html
```

- `fragment.html` は `<title>` から書き始める（`<!doctype>` `<html>` `<head>` `<body>` は書かない）
- **`validate` は `fragment.html` にだけかける。** `standalone` の出力は骨格タグを持つので、
  かけると必ず `fragment に骨格タグ <!doctype が含まれています` で落ちる（成果物の不具合ではない）
- `--ref` を忘れるとベースブランチ側のコードが載る
- 出力先は `${XDG_STATE_HOME:-$HOME/.local/state}/pr-review/<owner>__<repo>/`
- HTML 全体で 16MB 未満。超えたらスクショの枚数を減らす（品質ではなく枚数で削る）
- **standalone の実在する成果物ファイル**を報告し、公開済みの場合だけ共有URLも併記する
